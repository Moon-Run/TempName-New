# MA11 之后的 5% 优化：固定线性层的原生执行计划

更新：2026-10-30。本文依据旧仓库的真实训练记录、八个 rank 的 MA11 trace，以及新仓库 MA14–20 的实现与设计。

**建议优先做一项新的机制实验：将 QKV、FC1、attention output、FC2 的线性层前后向，改为初始化时绑定的 C++ autograd 执行计划。保持 MA11 的设备计算、通信协议和梯度累加语义，减少这些路径反复进入 Python、构造调用参数及跨语言提交的成本。** 下文暂称 **N1**，不占用现有 MA 编号。

这是针对当前项目执行路径的新机制，并非新的 GEMM 算法，也不是把已有 MA15–20 改名。现有证据足以支持优先验证它，**尚不足以承诺 5% 必然实现**。本文只完成分析与方案设计；没有实现 N1，没有运行新 GPU 实验，也没有将预算写成实测收益。

## 1. 先固定基线和目标

采用旧仓库 [baseline.md](../../../../../TempName/docs/design/design-h100/New-Mechanism/baseline.md) 选用的首轮 MA11：

| 项目 | 已有事实或本次目标 |
| --- | --- |
| MA11 完整 optimizer step | **450.6624015 ms** |
| 同批 MA89 对照 | 459.6383128 ms |
| MA11 相对同期 MA89 | 节省 8.975911 ms；配对收益 **1.952%［95% CI：1.711%, 2.271%］** |
| 首轮样本 | 1 个 trial、8 个完整配对块；每臂 8 个窗口，每窗口 10 步预热＋50 步正式计时 |
| 本次 5% 口径 | 沿用仓库的**完整步时下降 5%** |
| 历史量级下需要净省 | **22.5331201 ms/step** |
| 历史量级下候选目标 | **428.1292814 ms/step** |

如果“性能提高 5%”专指吞吐，则对应 `450.6624015 / 1.05 = 429.2022872 ms`。本文采用更严格的步时下降口径；正式判定必须使用**新实验同期 MA11**，428.129 ms 只是历史预算换算。

原始证据：[MA11 实测说明](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-11.md)、[首轮 report.json](../../../../../TempName/logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/report.json)、[固定实验 plan.json](../../../../../TempName/logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/plan.json)。旧仓库另有较晚的 MA11 批次；本文不与首轮合并，也不声称历史只运行过一次 MA11。

固定工作负载为 H100 80GB、TP8、32 层、hidden size 4096、FFN 16384、序列长 2048、microbatch 1、每步四个 microbatch，即 8192 token/step；BF16、零 dropout、无 recompute。当前 MA11 已包含 MA8-v2 激活缓存、MA9 零统计、MA4-F 消费融合和 MA11 softmax。**它们已经兑现的收益不能再次计入 N1。**

## 3. MA11 还剩哪些值得处理的成本

### 3.1. 小 kernel 不是当前最有把握的 5% 来源

本次重新读取首轮 [MA11 八 rank 原始 trace](../../../../../TempName/logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/results/profile-F4-cache-zcount-csoftmax/)。以下均为**每 rank 单步先求 GPU kernel 时长之和，再取八 rank 中位数**：

| GPU 类别 | 次数／rank／step | 累计工作量中位数 |
| --- | ---: | ---: |
| NCCL AllGather，含各用途 | 524 | 223.543 ms |
| NCCL ReduceScatter，含各用途 | 260 | 175.520 ms |
| Flux IPC 发布屏障 | 256 | 105.661 ms |
| 全部 GEMM | 2316 | 95.636 ms |
| FP32 add 类 | 1568 | 17.988 ms |
| MA11 softmax forward／backward | 128／128 | 14.382／5.187 ms |
| LayerNorm 全部前后向 | 1040 kernels | 9.336 ms |
| Adam | 49 kernels | 9.078 ms |
| row decoder | 256 | 2.982 ms |
| GELU 前后向 | 256 | 2.608 ms |

其中 FP32 add 类不全是梯度累加；不能把 1568 次全部认作 DDP 可删工作。NCCL 和屏障包含到达偏差及等待，且不同 stream 的区间重叠。八 rank 的 GPU 首尾跨度中位数约 **738.285 ms**，明显高于无 profiler 的 450.662 ms。因此这些数据用于定位对象，**既不能相加成步时，也不能拿等待时间作为可回收预算**。

softmax 前后向的累计量级约 19.568 ms，本身已低于 22.533 ms 目标。它不是无 profiler 性能的严格上界，但结合 MA13 的负面证据，继续仅压缩 softmax 不是优先路线。LayerNorm、GELU、decoder 或参数回写单点的量级依据更弱。

### 3.2. 仍有 1,024 个重复的线性层提交区间

MA8 只改变了前向完整输入的生命周期，MA4-F 只融合了 row 消费端；两者外面仍是 Python 自定义 autograd Function。

本次从同一批八份 trace 提取四种**精确名称**的 CPU scope：

| 路径／trace 名称 | 次数／rank／step | CPU scope 总量 | 扣除内部子区间并集后剩余 |
| --- | ---: | ---: | ---: |
| column forward：`_MA8CachedRawLinear` | 256 | 75.309 ms | 19.702 ms |
| column backward：`_MA8CachedRawLinearBackward` | 256 | 105.485 ms | 32.620 ms |
| row forward：`ConsumerGemmRSFunction` | 256 | 28.435 ms | 16.904 ms |
| row backward：`ConsumerGemmRSFunctionBackward` | 256 | 91.479 ms | 22.343 ms |
| **四类在各 rank 内合并，再取中位数** | **1024** | **302.545 ms** | **91.724 ms** |

“内部子区间”限定为同一线程、严格嵌套的 `cpu_op`、`cuda_runtime`、`cuda_driver`，取区间并集以避免重复扣减；没有重复统计外层 `autograd::engine::evaluate_function`。合并结果按 rank 重算，不能由上面四个中位数直接相加获得。文末提供复算命令。

**91.724 ms 不是纯 Python 时间，也不是可节省时间。** 它含未被子事件标注的 native 工作、必要的对象管理、检查和 profiler 扰动；尤其 row forward 本就有 native 执行区间。这里尚无无 profiler 的 GPU 提交饥饿证据，不能据此宣布整步 CPU-bound。

这组数据支持一个比“小 kernel 再快一点”更值得验证的假设：**若减少频繁的主机组织工作，使某些关键 rank 更早提交原来的 GPU 工作，整组同步等待有可能一起下降。** 这个假设与 MA7、MA10 的主机开销反例相容，但必须由 N1 的同期完整训练验证。

## 4. 新机制 N1：固定计划＋原生 autograd 节点

### 4.1. 具体替换边界

为 32 个 QKV、32 个 FC1、32 个 attention output 和 32 个 FC2 建立实例级 native plan。不是生成整模型新调度器，而是替换这四类线性调用内部的执行方式：

```text
MA11：
Module.forward
  → Python Function.forward
  → Python 的尺寸／参数组织、多个 ATen／dist／Flux 入口
  → 原设备工作

autograd engine
  → Python Function.backward
  → 多个 Python→ATen／c10d 调用
  → 原 BF16 梯度返回 → 原 AccumulateGrad／DDP

N1：
Module.forward
  → 一次 native Function::apply(plan, input, weight, bias, residual...)
  → C++ 按固定顺序调用同一套 ATen／ProcessGroup／Flux 操作

autograd engine
  → C++ Function::backward
  → 同一套原操作 → 原 BF16 梯度返回 → 原 AccumulateGrad／DDP
```

减少的是 Function 内部解释执行、反向 Python callback、重复 Python→C++ 往返，以及可以在初始化确定的元数据组织。**前向仍有 Python Module 和 native 入口，autograd 节点数量也不要求减少。** 全部设备 kernel 和 collective 数量原则上保持；不能把“native plan”宣传成 GPU 工作量消除。

PyTorch 提供 C++ 自定义 autograd Function，支持保存前向 tensor、实现 backward 并接回原 autograd 图；参考 [官方 C++ autograd 文档](https://docs.pytorch.org/tutorials/advanced/cpp_autograd.html)。具体实现必须针对实验使用的 PyTorch 2.6.0 构建与验证，不从最新文档假定二进制兼容。通信沿用该版本的 [ProcessGroup C++ 接口](https://github.com/pytorch/pytorch/blob/v2.6.0/torch/csrc/distributed/c10d/ProcessGroup.hpp)，原 c10d dispatcher、Work 及通信事件仍然存在。这两个资料仅支持实现路径，不提供本项目的性能预测。

### 4.2. 初始化绑定什么，逐次仍要保存什么

| 初始化绑定到 plan | 每次调用必须独立处理 |
| --- | --- |
| 模块角色、合法 shape／stride 规则、TP rank／world | 实际 input、grad_output 及其布局检查 |
| 原 ProcessGroup 的强引用、原 collective options | 原 Work 生命周期、stream 依赖和 wait |
| row 原有两个 native GemmRS 槽及固定 option | 成功后推进槽号，失败后封锁实例 |
| 固定执行序列及配置约束 | `SavedVariable`／`save_for_backward`、版本检查及引用保活 |
| 稳定配置和源码／构建身份 | 当前 device／stream、权重与输出的实际地址 |

weight、bias、residual 必须仍作为 `Function::apply` 的显式可微 Tensor 参数；只藏进 plan 会丢失 autograd edge 和 DDP hook。plan 不缓存跨调用使用的裸激活指针，不建立共享输出池，不把 MA8 的完整输入改为可被下一层覆盖的 workspace。

MA8 保留的每次完整输入继续独立归该次 context 所有；row 输出继续是独立、无 view 的输出。保留原分配、`recordStream`、异常及重入保护。初始化时固化不变量，不等于删除运行期必要检查。

### 4.3. column 路径必须逐项保持

实际依据是 [ma8_adapter.py](../../../../tools/h100/phase6/ma8_adapter.py) 的 `cached_class_source()`，以及 [冻结 Megatron layers.py](../../../../../TempName/logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/megatron/megatron/core/tensor_parallel/layers.py) 的 `LinearWithGradAccumulationAndAsyncCommunication`。

前向仍为：独立完整输入分配 → 原 ProcessGroup AG／完成依赖 → 原 `matmul(total_input, weight.t())` → 原 bias 处理；保存原 MA8 缓存。

反向按当前启用分支保持：

```text
取回该次 retained_input（不重新 AG）
→ grad_input = grad_output.matmul(weight)
→ 原 prepare_input_tensors_for_wgrad_compute 的布局处理
→ 原异步 ReduceScatter(grad_input)
→ 原 grad_weight = grad_output.t().matmul(total_input)
→ 原 bias sum（仅原路径需要时）
→ 原 Work.wait
→ 返回 sub_grad_input / grad_weight / grad_bias
```

不能把 RS 挪到 wgrad 之后，不能变成同步通信，也不能删除 wait。保留原 `CUDA_DEVICE_MAX_CONNECTIONS=1` 和 stream 配置。调用同一 ATen 算术仍需核对实际 GEMM 后端、布局和数值，不能仅凭 API 名相同宣布逐位等价。

### 4.4. row 路径必须调用已有 native 实体

[ma4_f_adapter.py](../../../../tools/h100/phase6/ma4_f_adapter.py) 的 `consumer_autograd_source()` 明确给出当前顺序：

```text
前向：原 native producer → 原发布屏障 → 原 decoder＋bias＋residual
反向：grad_bias = grad_output.sum_to_size(bias_shape)
      grad_residual = grad_output
      full_grad = 原 AG(grad_output.contiguous())
      grad_input = full_grad.matmul(weight)
      grad_weight = full_grad.reshape(...).t().matmul(input.reshape(...))
```

原生入口已经由 [ma4_f_sources.py](../../../../tools/h100/phase6/ma4_f_sources.py) 引入 `GemmRS::ma4_consumer_forward()`；双槽与缓存来自 [ma2_cr2_sources.py](../../../../tools/h100/phase6/ma2_cr2_sources.py)。N1 应持有这两个已有 native 槽的类型化引用，将重复 Python 槽选择／状态管理放进对应 native plan，并保持原语义。

**不能让 C++ plan 再回调 Python `op.forward_consumer()`。** 那样主要的跨语言链仍存在。原 producer、decoder、量化 mask、source 累加顺序、两次 BF16 bias／residual 舍入、发布屏障及双槽复用证明全部沿用。

### 4.5. 与已有方案的实质区别

- **与 CR2：** CR2 已缓存 row native forward 的配置及算子选择；N1 不重新领取这些收益。新增范围是仍存在的 Python autograd 前后向、column 路径，以及多个原生调用之间的主机组织工作。
- **与 MA10：** 不排参数梯度队列，不重写 DDP hook，不直接写 `main_grad`；原 BF16 梯度物化、FP32 累加及四个 microbatch 顺序保留。
- **与 MA15：** 不捕获 CUDA Graph，不引入固定输入地址、边界 clone 或 graph replay；目标是线性层前后向，不是 attention core。
- **与 MA17：** 使用同一个 ProcessGroup、原 NCCL stream 和交接方式，不新建 communicator，不切换为同流直接 NCCL。
- **与 MA16、MA18、MA20：** 不拆 GEMM、不换 transport、不改量化选择或 tile 顺序。

这些限制也让结果更易解释：如果 kernel、通信和数值均相同而完整步时下降，证据才支持主机执行路径优化有效；不能把剥离 profiler 标注获得的表面速度写成训练提速。

## 5. 5% 的预算是否站得住

最直接的门槛为：

```text
22.5331201 ms / 1024 个前后向提交区间 = 22.005 μs/区间
若只优化 512 个 backward 区间，则需要 44.010 μs/区间。
```

这里是**整步净兑现**的均摊难度，不是每个 scope 缩短 22 μs 就必然成功。对已被 GPU 计算覆盖的 CPU 工作，缩短后可能没有任何步时收益；对拖慢 collective 到达的 rank，较小改动也可能影响后续等待。

可用以下敏感性关系解释目标，但不能把它当作拟合模型：

`整步净节省 ≈ 实际减少的主机工作 H × 关键路径兑现比例 e − 新增成本 C`

| 假设情景，均非实测 | H | e | C | 预算净节省 |
| --- | ---: | ---: | ---: | ---: |
| CPU 缩短大多仍被覆盖 | 40 ms | 30% | 3 ms | 9 ms，达不到 5% |
| 较多缩短发生在暴露的提交链 | 40 ms | 70% | 3 ms | 25 ms，有机会超过目标 |

不能从 91.724 ms 的 profiler 剩余区间推出 H 或 e。选择 N1 的理由是其覆盖频率高、存在实际可删除的跨语言组织工作、对原数学和通信的侵入较小；**不是已经证明有 22.53 ms 可回收**。若正式实验只有 1–2%，就应记录为小增量，不通过叠加其他未测方案来包装成 5%。

## 6. 实现与验证顺序

### 6.1. 先做原生 backward，再接入 forward

第一步以两个 C++ Function 承接 row／column backward，前向与保存 tensor 的行为逐项对照原实现。优先减少 512 次反向 Python callback，不动原 DDP。

第二步把两个 Function 的 forward 及 row 双槽提交接入原生计划，覆盖完整 1024 个区间。仍保留外层 TransformerLayer 的调用结构和原训练循环。两步属于同一个机制的实现过程，最终主实验比较完整 N1 与完整 MA11。

候选可规划 `native_linear_plan` 扩展、实例安装 adapter 和独立实验 harness；**这些是待实现项，当前没有可运行的 N1 启动命令**。编译需使用现场 PyTorch 的 ABI 和 C++ 头文件，冻结扩展、原 MA11 动态库及配置身份。对照不安装候选包装或额外逐次检查。

### 6.2. 正确性先行

先做固定配置下前向、input／weight／bias／residual 梯度的逐字节对照，包括梯度实际 stride、连续化分支、正负零和多次调用的生命周期。随后沿用完整模型每 rank 全部 **389 个参数**的梯度、更新指纹，以及 loss／grad_norm／最终参数轨迹检查。

必须验证：

1. MA8 的 256 次目标反向输入 AG 仍为零，缓存不串层、不串 microbatch。
2. MA9 仍为两个零统计 kernel；MA11 仍为 128 次前向＋128 次反向 softmax。
3. 原 BF16 梯度返回与 DDP 累加保留，不用 `beta=1` GEMM、FP32 直写或合并 microbatch 改写舍入顺序。
4. row 残差梯度的别名语义、无 view 输出及双槽失败状态保留。
5. 每个 collective 的数量、尺寸、顺序、ProcessGroup、stream 依赖和 wait 保留；仅名称消失不算通信已经验证。

任何数值或生命周期差异都停止该候选，不以放宽容差来维持“等价的执行机制”这一结论。

### 6.3. 用最小消融判断收益来自哪里

预先定义四个配置：MA11、仅 native column、仅 native row、两者都启用的 N1。消融用于判断哪条链值得迁移，以及组合是否互相抵消；不将两项单独收益相加。

正式 5% 验收使用 **MA11 对 N1 两臂、至少两个独立 trial**。每个 trial 沿用 8 个完整 AB/BA 平衡块，每窗口 10 步预热＋50 步正式，八 rank 最大窗口墙钟／50；按完整块对数耗时比进行 10,000 次 bootstrap。不同 trial 独立报告，保留所有慢窗口与负结果。

| 结论 | 必要条件 |
| --- | --- |
| 验证正增量 | 每个 trial 点估计和 95% CI 下界都大于 0，且正确性／路径通过 |
| 观察到 5% 点估计 | 点估计达到 5%，但区间下界可能不足；不能称稳定达标 |
| 验证本次 5% 目标 | 每个 trial 的点估计和 95% CI 下界均至少 5%，且正确性／路径通过 |

完整 step 包含前后向、通信、optimizer 和清梯度。native guard、分配和异常状态检查都留在正式计时中；初始化和必要预热按两臂相同规则处理，并记录初始化成本与显存峰值。

### 6.4. 单独诊断主机提交是否影响关键路径

无 profiler 的完整步时是最终证据。另开诊断进程，通过 CUDA correlation 关联原生 scope、launch 与设备工作，逐 rank 检查：后继操作是否已提前排队、是否存在主机尚未提交导致的空档，以及减少 CPU 区间后慢 rank 的到达是否提前。

不要只看 rank0 或八 rank 中位数；完整步时受最慢 rank 影响。不要在每次调用后加设备同步来“测纯 Python”，这会改变原重叠。若使用低开销主机计时，应采样、单独报告测量扰动，并保持正式窗口无逐次 instrumentation。

**否证条件：** 只有 profile scope 变短、只有单层 microbenchmark 变快、只有 kernel 数量／名称变化，或正式置信区间跨零，都不足以支持 N1 改善整步。若 CPU 减少而 GPU 提交一直提前排队，应接受该方向无法达到 5%，转向通信依赖层面的结构改动。

## 7. 其他优化空间及优先级

| 优先级 | 方向 | 判断 |
| --- | --- | --- |
| 第一优先 | 本文 N1：固定线性层原生执行计划 | 有新的、未被 MA15–20 覆盖的执行边界，覆盖 1024 次调用；先验证主机缩短能否兑现 |
| 并行取得已有证据 | MA15、MA17、MA18 的独立实验 | 都针对局部计算以外的执行／通信链，值得先拿结果；它们不是本文的新方案 |
| 第二阶段探索 | 把 sequence-parallel 边界移过 LayerNorm，减少反向通信交接 | 机制空间较大，但重复计算、显存和归约等价性风险明显，见下文 |
| 小增量备选 | MA19、LayerNorm／GELU／参数发布等局部优化 | 可单独积累收益；现有数据不支持直接承诺一项达到 5% |
| 需独立数值协议的路线 | FlashAttention／改变 GEMM 累加方式／提高量化覆盖等 | 会涉及现有逐位等价约束或已有 MA20 范围；不能混入本次等价执行机制实验 |

值得保留的第二阶段想法是**重定位序列分片边界**。当前局部链为：

```text
column dgrad → ReduceScatter → 本地 LayerNorm backward／残差加法
             → row backward AllGather → 原 row dgrad／wgrad
```

理论上可让归约后的完整梯度在各 rank 保持复制，执行全序列 LN 输入梯度和残差链，直接供下一 row backward 消费；前向相应将 AG 从归一化后移到归一化前，保存完整 pre-LN 状态。LayerNorm gamma／beta 和 row bias 的参数梯度仍只能统计本 rank 原先负责的 256 行，再走原有 TP 归约，否则会重复计入八次。

这要求整个 attention／MLP 两条残差支路都维持正确的完整梯度所有权，不能只替换一个 collective。按 32 层、四 microbatch 推算，保留每 microbatch 末端入口的一次 seed AG，内部最多可消去 **252 次 row backward AG**，同时把对应 column dgrad 的 RS 改为完整归约结果。这是设计计数，不是已测删除。

它的吸引力是减少反复的主机交接；风险也具体：

- `RS + AG` 与 `AllReduce` 在 collective 语义上等价，但原链中还隔着 LN 和残差，必须先重构所有权；两者并非可直接替换。[NCCL collective 定义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)
- **同为 Ring 也不保证 BF16 逐位相同。** 固定 NCCL 2.21.5 的 [ReduceScatter](https://github.com/NVIDIA/nccl/blob/v2.21.5-1/src/device/reduce_scatter.h) 与 [AllReduce](https://github.com/NVIDIA/nccl/blob/v2.21.5-1/src/device/all_reduce.h) 对 chunk／rank 的映射不同；必须验证每个元素的归约顺序，而非只固定算法名称。
- Ring 数据量基本不减：16 MiB 完整梯度的 RS 与 AG，理想每 rank 发送量分别约 14 MiB，AR 约 28 MiB。不能宣称通信字节减半。
- LN forward 与输入梯度需要处理约八倍行数，残差加法也扩大；参数梯度还必须保留原局部归约。按每个同时存活 microbatch 最多 64 份完整 pre-LN 状态做保守容量预算，比局部分片约多 `64 × 14 MiB = 896 MiB`；若保留首个 input-LN 的原分片路径，仅 63 个内部边界全量驻留，则约 882 MiB。这些不是实测峰值，也未包括其他新增工作区；MA8 的归一化输出应复用，避免重复缓存。

因此本次把它放在 N1 之后：先做半层的严格数值与完整依赖计时验证，证明通信交接节省足以覆盖额外 LN／残差成本，再考虑整模型。没有这种证据时，不把“少 252 次调用”写成 5% 预测。

## 8. 本次新增 CPU 数据的复算方法

下面命令在 **TempName-New 仓库根目录**执行，只读取旧 trace 并向标准输出打印数据，不修改历史日志。它复算第 3.2 节；第 3.1 节 GPU 分类数据仍应按 kernel 类别单独解释，不能混用两种口径。

```bash
python3 - <<'PY'
import bisect
import collections
import gzip
import hashlib
import json
from pathlib import Path
from statistics import median

base = Path('../TempName/logs/h100/phase6/'
            'ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/'
            'fullstep/results/profile-F4-cache-zcount-csoftmax')
names = ('_MA8CachedRawLinear', '_MA8CachedRawLinearBackward',
         'ConsumerGemmRSFunction', 'ConsumerGemmRSFunctionBackward')

def union_length(spans):
    total, end = 0.0, float('-inf')
    for left, right in sorted(spans):
        if right > end:
            total += right - max(left, end)
            end = right
    return total

ranks = []
for rank in range(8):
    path = base / f'rank{rank}-profile.json.gz'
    raw = path.read_bytes()
    events = json.loads(gzip.decompress(raw))['traceEvents']
    by_thread = collections.defaultdict(list)
    for event in events:
        if event.get('ph') == 'X' and event.get('cat') in (
                'cpu_op', 'cuda_runtime', 'cuda_driver'):
            by_thread[event['tid']].append(event)
    for values in by_thread.values():
        values.sort(key=lambda event: event['ts'])
    starts = {tid: [event['ts'] for event in values]
              for tid, values in by_thread.items()}
    result = {}
    for name in names:
        scopes = [event for event in events if event.get('ph') == 'X'
                  and event.get('cat') == 'cpu_op' and event.get('name') == name]
        assert len(scopes) == 256, (rank, name, len(scopes))
        duration, remainder = 0.0, 0.0
        for scope in scopes:
            left, tid = scope['ts'], scope['tid']
            right = left + scope['dur']
            children = by_thread[tid][
                bisect.bisect_right(starts[tid], left):
                bisect.bisect_left(starts[tid], right)]
            covered = union_length([
                (event['ts'], event['ts'] + event['dur']) for event in children
                if event['ts'] + event['dur'] <= right + 0.001])
            duration += scope['dur']
            remainder += scope['dur'] - covered
        result[name] = (duration / 1000, remainder / 1000)
    result['combined'] = tuple(sum(result[name][i] for name in names)
                               for i in range(2))
    ranks.append(result)
    print('input', rank, hashlib.sha256(raw).hexdigest())
for name in (*names, 'combined'):
    print(name, {'scope_ms': median(row[name][0] for row in ranks),
                 'unattributed_ms': median(row[name][1] for row in ranks)})
PY
```

预期合并输出约为 `scope_ms=302.5449185`、`unattributed_ms=91.7242027`。这两个数字仍是 profiler 下的观测；N1 是否达到 5%，只由第 6 节定义的同期完整训练决定。
