# MA10：CR3 的有界批量梯度累积

**更新：2026-10-27，MA10-v1 八卡实验已完整完成并离线复核，当前候选显著退化。** 同期原 CR3（`F4`）与 `F4-gacc` 平均为 **504.544 / 536.320 ms/step**，候选增加 **31.775 ms/step**；完整块配对收益为 **−6.299%［95% CI：−6.809%, −5.768%］**，8 个配对块全部更慢，未达到 2% 目标。数值和执行路径检查均通过，批次状态为 `completed/done`；保留 CR3，不将本配置作为加速方案启用。详见[第 9 节](#9-ma10-v1-八卡实测合批执行成功但完整训练退化)。

本方案改变 DDP 将参数梯度写入 FP32 `main_grad` 的提交粒度；梯度计算、通信、优化器统计及更新保持原路径。第 1–7 节保留设计、实验协议和上机前验证，第 8 节为接口导出修复记录，第 9 节记录本次实测结果。

## 1. 与已有机制的区别

| 已有方案 | 改动位置 | MA10 的处理 |
| --- | --- | --- |
| MA6 tile / mask / warp layout | 前向接收端 decoder | 使用原 CR3 decoder、mask、几何布局 |
| MA6 bias / AllGather 重叠 | row projection 反向调度 | 使用原 bias→AG→dgrad→wgrad 顺序 |
| MA7 异步 wgrad | 将 wgrad 及其累积移至辅助 stream | wgrad 仍在原 backward、原 stream 上完成；没有辅助 stream |
| MA8 激活缓存 | 保存前向完整输入，删除反向 AllGather | 不缓存激活、不删除任何原 collective |
| MA9 零梯度统计融合 | optimizer 的 `count_zeros` | 原逐参数统计及原 AllReduce 完整保留 |
| **MA10** | **DDP hook 的参数梯度写入** | **若干已经生成的 BF16 梯度，共用一次混合类型 CUDA 累积提交** |

MA10 不是把 MA7 的 wgrad 延迟队列换一个名字：这里所有 dgrad/wgrad GEMM 的调用、返回和计算流都不变；仅将不同参数的独立 `main_grad.add_(param.grad)` 合批。也不启用 `gradient_accumulation_fusion=True`，因为直接让 GEMM 累加到 FP32 会绕过 CR3 已有的 BF16 梯度舍入。

## 2. 原 CR3 有一条未覆盖的重复工作链

原始批次 `ma4-f-1x-50steps-20261025-115124-977713` 的 [DDP hook](../../../../logs/h100/phase6/ma4-f-1x-50steps-20261025-115124-977713/fullstep/megatron/megatron/core/distributed/distributed_data_parallel.py) 在叶参数的梯度生成之后执行：

```python
if param.grad is not None and (
    not param.grad_added_to_main_grad or getattr(param, 'zero_out_wgrad', False)
):
    param.main_grad.add_(param.grad.data)
param.grad = None
```

本实验有 389 个可训练参数、每步四个 microbatch。八份**原始 CR3** trace 均确认每步 **1,556 次**上述加法，每次独立提交一个 GPU kernel。关联方法是从外层 `autograd::engine::evaluate_function: torch::autograd::AccumulateGrad` 定位 hook 内的 `aten::add_`，再经 CUDA runtime correlation 找到 GPU kernel。内层 `torch::autograd::AccumulateGrad` 已在 hook 前结束，不能只用内层范围；optimizer 零统计中的浮点 add 也没有算入本表。

| 原 CR3 profile 指标，每 rank 每 optimizer step | 八 rank 结果 |
| --- | ---: |
| 归属到 DDP hook 的 add kernel | 各 1,556 次 |
| add kernel 的 GPU 工作量之和 | 17.824–18.074 ms；中位 17.926 ms |
| CPU `aten::add_` 时长之和 | 中位 22.939 ms |
| 外层 AccumulateGrad（含 hook）时长之和 | 中位 55.689 ms |
| 整步 profile GPU span | 中位 821.750 ms |

可复算证据为 [analyze.py](../../../../outputs/h100/phase6/ma10-validation-20261027/baseline-analysis/analyze.py) 和 [analysis.json](../../../../outputs/h100/phase6/ma10-validation-20261027/baseline-analysis/analysis.json)，记录八份 trace 与原 DDP 源码的 SHA256。分析没有使用 MA8 包装后的 F4，也没有跨 rank 相减绝对时间。

这些数据说明存在大量细粒度提交，**不意味着可以删除 17.926 ms 或 55.689 ms**。合批仍须读取 BF16 梯度、读取和写回 FP32 梯度；CPU 与 GPU 工作重叠，profile 也将整步从正式约 501 ms 扰动到约 822 ms。MA10 的假设是减少提交次数、改善小张量累积效率后，收益能覆盖排队、描述表构造和延迟释放带来的成本。

原 rank 记录的参数 shape 合计每 microbatch 849,207,296 个元素。按每元素 BF16 读 2 字节、FP32 读写各 4 字节，四个 microbatch 共 **31.635 GiB/rank/step 的逻辑读写**，两臂均须保留；这是从 shape 推算的工作量，不是 HBM 实测流量。最大源梯度张量为 33 MiB，本配置未触发超大单张量例外。

## 3. 机制：有界队列，同流提交，逐 microbatch 清空

```text
原 CR3：
  参数1的 backward → BF16 grad1 → add_(main_grad1, grad1)
  参数2的 backward → BF16 grad2 → add_(main_grad2, grad2)
  ……每个参数单独提交……

MA10：
  参数1的原 backward → BF16 grad1 → 队列持有 grad1
  参数2的原 backward → BF16 grad2 → 队列持有 grad2
  ……达到张量数或字节上限……
  一个 CUDA kernel：分别执行 main_grad[i] += float(grad[i])
  ……microbatch 的原 backward 返回……
  提交剩余梯度 → 下一 microbatch / 原梯度同步 / 原 optimizer
```

### 3.1. 队列规则

- 每 rank 一份队列，固定最多 **32 个张量、64 MiB BF16 源梯度逻辑容量**，不做参数扫描或自动调参。入队将超过边界时先提交已有队列；单张量大于字节上限时独立提交，不与其他张量合批。它本来就必须存在；若梯度是较大 storage 的 view，引用还可能延长整个 storage 的寿命。因此这里的“64 MiB”约束的是多张量暂存的逻辑容量，不能据此声称总峰值增量严格不超过 64 MiB。
- 对同一个参数，每个 microbatch 仍只执行一次原来的 FP32 加法。不同参数写入互不重叠的目标，允许同批并行；四个 microbatch 的同参数累积顺序保持不变。
- hook 持有本次 `param.grad.data` 的实际 tensor 引用后，再像原实现一样清掉 `param.grad`。不能只保存裸指针，也不能把未来 microbatch 的梯度加入当前批。
- 每个 `schedules.backward_step` 先执行原 backward，再提交本 microbatch 剩余队列；后继梯度同步、grad norm、裁剪、零统计、Adam 和清梯度必须在全部写入之后。
- 所有提交使用原 compute stream。没有逐层设备同步、辅助 stream、跨 microbatch 的延迟累积或新的 NCCL 操作。

### 3.2. 混合类型原生 kernel

实现位于 [ma10_grad_batch.cuh](../../../../tools/h100/phase6/ma10_grad_batch.cuh)。CPU 将一批的源地址、目标地址、长度和 block 映射作为小型 CUDA kernel 参数按值提交；不在每批创建 GPU 描述表，不额外提交 descriptor H2D 或清零 kernel。各 CTA 覆盖互不重叠的目标片段，不使用浮点 atomic。

算术严格保留：

```text
原 GEMM/autograd 生成 BF16 grad
→ 将这个已舍入的 BF16 值精确扩展为 FP32
→ FP32 main_grad 与该值相加并舍入
```

不把 BF16 舍入移到 FP32 累积之后，不合并四个 microbatch 的 GEMM，也不重写优化器。

这里不能直接以 `torch._foreach_add_(FP32_targets, BF16_sources)` 替代：冻结 PyTorch 2.6 的 [ForeachUtils.h](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/native/ForeachUtils.h) 要求这条快速路径的张量列表具有相同 dtype，混合列表会退回逐张量计算。因此专门实现混合类型累积，并用实际 GPU kernel 数确认合批执行。

### 3.3. 安装与失败边界

[ma10_adapter.py](../../../../tools/h100/phase6/ma10_adapter.py) 仅在候选进程初始化时启用。原 DDP 初始化注册 hook 时没有保留可供后续统一替换的 handle，所以在 `setup_model_and_optimizer` **之前**短暂替换 hook 工厂；模型初始化完成后恢复原工厂，保留已经绑定到该候选模型的闭包，再绑定当前模型的实际参数和 native library。

只支持当前固定 TP8、PP/CP/DP=1、32 层、四 microbatch、BF16 参数与 FP32 梯度缓冲、零 dropout、无 recompute/CUDA Graph、无梯度/参数通信重叠、无 gradient accumulation fusion 的实验。绑定时核对源码身份、参数覆盖和缓冲区关系；不支持的 dtype/layout、重复累积、存储或 stream 漂移、残留队列和 native launch 失败均拒绝继续。失败后不静默退回原路径，也不重复发起累积。

## 4. 对照必须是原 CR3

- 原生对照从注册的 MA4-F 构建变换生成，F4 的全部 source hash 与原实现相同。候选只追加本机制的 header/include 及四个接口的显式导出项；原 GEMM、packet、barrier、decoder、mask、归约顺序和两次 BF16 消费舍入保持。
- 两臂生成的 `adapter.py`、`taco_support.py` 均核对原 MA4-F 批次 SHA256；八个原 worker 函数和正式计时/profile 循环核对 AST 指纹。
- 候选初始化分支在模型创建前后安装 MA10；**F4 不导入或安装 MA10 adapter，不增加 DDP hook 包装、每层计数或 marker。** 不能为了“两臂包装对称”而把 CR3 改慢。
- 所有候选排队、边界检查、kernel 提交和显存压力都包含在正式计时中。正确性逐批对照和自定义 profile marker 仅在独立 smoke/profile 中执行。

旧 ma6～ma9 文件及结果保留，本实验不将它们的机制叠加到候选上。MA10 复用的是已校验的配对实验框架，不是 MA9 的统计融合实现。

## 5. 2% 预算与可否证条件

[baseline.md](baseline.md) 的历史 CR3 均值为 501.433 ms，仅用于量级换算：

```text
2% × 501.433 ms = 10.02866 ms / step
10.02866 ms ÷ 1556 = 6.445 μs / 原逐参数提交
```

这是有压力的目标：GPU 的数据读写仍然存在，原来的大梯度加法也可能已经很高效。若无 profiler 环境中提交开销已被其他工作隐藏、kernel 合批粒度不足，或 Python/ctypes、排队内存和 cache 压力抵消收益，整步可能只改善少量，甚至变慢。不得以“kernel 数下降”代替 2% 的完整步时目标。

真实验收使用**本轮同期 F4**，不拿历史 501.433 ms 或最快 498.478 ms 与候选相减。每个请求 trial 分别给出：

| 字段 | 条件 |
| --- | --- |
| `increment_over_F4_validated["F4-gacc"]` | 配对点估计 >0 且 95% CI 下界 >0，并通过数值和路径验证 |
| `target_point_observed` | 每 trial 点估计 ≥2%；不等于稳定达标 |
| `target_validated` | 每 trial 点估计及 95% CI 下界均 ≥2%，并完成所有路径验证 |

若 CI 跨零或为负，保留全部窗口，完成实验并报告未验证收益；数值、覆盖或执行路径失败则停止并保留现场。一次 trial 的前后半程不能算作独立复现。

## 9. MA10-v1 八卡实测：合批执行成功，但完整训练退化

### 9.1. 完成范围与对照身份

### 9.3. 数值一致，梯度队列确实执行

[算子预检](../../../../logs/h100/phase6/ma10-v1-gacc-1x-50steps-20261027-094702-220204/operator/preflight.json)通过前向逐位、input／weight／bias／residual 四类梯度与三步更新检查；[完整模型预检](../../../../logs/h100/phase6/ma10-v1-gacc-1x-50steps-20261027-094702-220204/fullstep/preflight.json)及冻结控制器的复算通过每 rank 全部 **389 个可训练参数**的梯度／更新指纹检查。候选 native 边界自测和 smoke 逐批原加法审计通过，正式窗口未执行这些数值审计。

同块同 rank 的两组正式 loss／grad_norm 轨迹及最终参数指纹一致。两组 mean loss 均为 **3.793363792030723**，final loss 均为 **0.00030573460389859974**，final grad norm 均为 **0.01800245891878419**。这是固定合成输入上的短程等价性证据，不是长期收敛结果。

候选全部 64 份正式 rank 记录一致：每窗口含预热共 60 个 optimizer step，执行 **240 个 microbatch、93,360 次 hook／张量累积、8,160 次 flush／native kernel**，即每步 **1,556 个梯度、136 次合批提交**。窗口末尾 pending tensor／byte 均为 0，原 DDP 工厂已恢复，无失败或逐参数回退；队列实测最多 **12 个张量、49.027 MiB 逻辑容量**，最大源梯度 33 MiB，未超过固定上限。

两组的 64 个原 row projection 模块也全部覆盖：每模块每窗口含预热 240 次 projection／bias-residual 消费，每个双工作区槽初始化一次并成功执行 120 次，K 分别为 512／2048，无槽失败。

### 9.4. Kernel 少了 91.26%，GPU 局部节省仍未兑现为整步收益

[完整训练 profile](../../../../logs/h100/phase6/ma10-v1-gacc-1x-50steps-20261027-094702-220204/fullstep/profile-summary.json) 的 16 份 trace 均通过冻结路径校验：每 rank 原 Attention／MLP 各 128 次消费链完整，候选每步 136 个新 kernel 都由 flush 标记及 launch correlation 唯一归属，提交张量数仍合计 1,556；同 compute stream、四个 microbatch 边界、原零统计及 optimizer 的消费顺序均通过。

下表每项先在单个 rank 的一整步内统计，再取八 rank 中位数；未跨 rank 相减绝对时间。

| 独立 profile 指标，每 optimizer step | F4 | F4-gacc |
| --- | ---: | ---: |
| 梯度累积 kernel 数 | 1,556 | 136 |
| 原 hook 内逐参数 `aten::add_` 数 | 1,556 | 0 |
| 梯度累积 GPU 工作量之和 | 17.897 ms | 14.575 ms |
| 外层 AccumulateGrad（含 hook）CPU 时长之和 | 55.586 ms | 75.929 ms |
| 整步 profile GPU span | 828.359 ms | 853.656 ms |

合批使提交次数减少 **91.26%**，但该组 GPU 工作之和只减少约 **3.321 ms**；原来大量梯度读写仍需执行。与此同时，候选 CPU hook 区间之和增加约 **20.343 ms**。结合实现中的逐 hook 状态／stream／shape／存储检查、队列维护和批次描述表构造，这提示主机侧开销值得优先检查。

**上述数值不能相加减来分解正式计时的 31.775 ms 退化。** 两组 profile 的整步均明显长于无 profiler 窗口，候选还带有仅在 profile 打开的 flush／microbatch 标记；CPU 区间与 GPU 工作重叠，hook 区间也不包含所有尾部 flush。当前证据证明“确实减少提交，局部 GPU 工作略降，但完整训练显著变慢”，尚不能定量归因于某一项检查、ctypes 或 cache 变化。

正式窗口显存峰值按每窗口八 rank 最大值再取均值：allocated 为 **16.428934 / 16.448376 GiB**，reserved 为 **16.638672 / 16.685547 GiB**。候选分别增加约 **19.91 / 48 MiB**，本轮没有 OOM；这与队列逻辑容量不同，不能互相替代。

原 row projection 算子前向平均为 Attention **93.018 / 93.211 μs**、MLP **139.875 / 140.243 μs**；对应配对收益为 **−0.208%［−0.501%, +0.055%］**、**−0.263%［−0.510%, −0.045%］**。该阶段两组均未安装 DDP 合批，不能将这些小差异归因于 MA10 梯度队列，或用于替代完整训练结论。
