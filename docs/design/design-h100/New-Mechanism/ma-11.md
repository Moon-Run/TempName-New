## 1. 选择这个机制的依据

[MA89](ma-8&9.md) 已在同批实验达到 **459.8060027899919 ms/step**；2% 对应 **9.196120 ms/step**，历史量级对应约 **450.610 ms/step**。实际验收只使用本次新跑的 MA89 对照，不拿历史 459.806 ms 与新候选跨批次相减。

剩余路径中，注意力分数仍经过下面的链条：

```text
QK baddbmm（已有原来的缩放）
→ BF16 scores 的 view
→ masked_fill_（原位写 mask 值）
→ 原 PyTorch BF16 softmax
→ PV bmm

反向：PV 梯度
→ BF16 grad × probability 的临时张量
→ 原 softmax backward 归约
→ AsStridedBackward / CopySlices 重建原位修改的 view 梯度
→ masked_fill 的反向及拷贝
→ 原 QK backward
```

这不是只看 kernel 名字作出的猜测。原 MA89 八份 trace 均确认每步 **32 层×4 microbatch＝128 次前向和128次反向**；掩码在 `baddbmm` 结果的 view 上原位写入，反向确实有 128 次 `AsStridedBackward0` 和注意力所属的 128 次 `CopySlices`。全模型另有 4 次 LM-head `CopySlices`，应保留。

从原八 rank 的一整步 trace 分别求工作量，再取 rank 中位数：

| 原注意力操作 | 次数／rank／step | GPU 工作量之和的八 rank 中位数 |
| --- | ---: | ---: |
| 前向 mask | 128 | 6.203 ms |
| 原 softmax forward | 128 | 14.391 ms |
| 反向 BF16 乘积临时张量 | 128 | 4.576 ms |
| 原 softmax backward | 128 | 4.819 ms |
| 反向 mask | 128 | 6.655 ms |
| AsStrided 回放中的 DtoD | 128，合计4 GiB | 3.165 ms |
| CopySlices 回放中的 DtoD | 512，合计16 GiB | 11.908 ms |
| AsStrided 回放中的清零 | 128 | 1.405 ms |

原 view 梯度重建每rank每步确有 **640次／20 GiB DtoD复制**，按launch归属统计，已剔除上表单独计算的masked-fill。CPU 区间中位数为 `AsStridedBackward0` **8.178 ms**、注意力 `CopySlices` **13.946 ms**。**这些是 profiler 下的工作量／区间，不是正式计时的关键路径净耗时；CPU、GPU 和通信可能重叠，不能把它们相加当作可节省时间。** 后续只用无 profiler 的完整 optimizer step 判定收益。

可复算证据：[baseline-analysis.json](../../../../outputs/h100/phase6/ma11-validation-20261027/baseline-analysis.json)、[分析脚本](../../../../outputs/h100/phase6/ma11-validation-20261027/baseline-analysis.py)。来源为 `ma89-v1-cache-zcount-1x-50steps-20261027-104719-859382/fullstep/results/profile-F4-cache-zcount`，保留各 trace 哈希及逐 rank 记录。

## 2. 新机制：让掩码在 softmax 内消费，让分数梯度直接产生

MA11 使用一个独立 autograd 节点替换这 32 个注意力模块的 `scale_mask_softmax.forward`。前向读入 scores 时根据**原来的实际 bool mask**选择数值，直接生成概率；反向直接生成 scores 梯度。没有原位修改 scores 的 view，因此也无需重建原位修改带来的 view 梯度。

```text
原 QK baddbmm
→ MA11 forward：读 scores／mask → 原归约树 → BF16 probability
→ 原 PV bmm

原 PV backward
→ MA11 backward：BF16 乘积舍入 → 原归约树 → 掩码后 BF16 scores gradient
→ 原 QK backward
```

收益来源有三项，属于同一个中间态消除机制：

1. 前向不再单独写回整张掩码后的分数矩阵。
2. 反向将 `grad × probability` 的 **BF16 舍入值**留在寄存器中，减少临时矩阵的存取；归约后直接写掩码后的梯度。
3. 删除注意力原位 view 的 `AsStridedBackward`／`CopySlices` 清零、复制及主机提交。

现有五段 mask／乘积／softmax 计算从每步 **640 个 kernel 变为256个**，并删除128次注意力 view 梯度重建。每张注意力矩阵为 `[1,4,2048,2048]`、BF16 **32 MiB**。仅三项独立中间态的写回＋再读，其逻辑访问量就约为 `128×3×2×32 MiB＝24 GiB/step/rank`。这不是实测 HBM 流量：L2 命中和实现重叠会影响实际成本；它说明该方向有足够大的处理对象，而不能证明2%必然实现。

仍保留 QK／PV 和其反向 GEMM、原通信、原权重梯度、MA8 缓存、MA9 零统计、梯度裁剪与 Adam。没有改变 attention 的计算范围、量化 mask、训练步数或模型精度。

## 3. 为什么不是重试 MA6／MA7／MA10

| 已有尝试 | 已有结果／风险 | MA11 的区别 |
| --- | --- | --- |
| MA6 decoder tile／反向 gather 重叠 | v2 两项均退化；v3 layout 仅约0.251%，mask整步区间跨零 | 不修改 decoder tile、接收端布局、gather 调度或 CUDA stream |
| MA7 更换 wgrad 实现 | 完整步约 −9.378% | 保留原 QK／PV、线性层与权重梯度 GEMM |
| MA10 Python 梯度队列合批 | kernel数减少但整步约 −6.299%；hook主机区间增加 | 不安装 DDP hook、不排梯度队列、不逐参数收集描述符；直接删除注意力密集临时态及原位view重建 |
| MA8／MA9 | 已验证成功，组合成为 MA89 | 两组共同保留原实现，用于测量 MA11 的独立增量 |

MA11 也不是打开 Megatron 的 `--masked-softmax-fusion` 开关或换成 FlashAttention。它固定当前 attention 路径的归约与舍入，再改变中间态的存放位置和 autograd 图。这样本次实验可以继续沿用完整梯度／参数更新一致性的强门禁。

## 4. 数值与实现边界

实现：[ma11_adapter.py](../../../../tools/h100/phase6/ma11_adapter.py)、[ma11_softmax.cuh](../../../../tools/h100/phase6/ma11_softmax.cuh)。原路径依据冻结的 Megatron `FusedScaleMaskSoftmax.forward_torch_softmax`，归约依据 PyTorch **v2.6.0** 的 [SoftMax.cu](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/native/cuda/SoftMax.cu) 与 [block_reduce.cuh](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/native/cuda/block_reduce.cuh)。随代码保留上游许可证。

- 当前原路径是 BF16 输入／输出、内部 FP32 归约，`scale=None`，没有 FP32 临时矩阵转换。QK 的缩放已经由原 `baddbmm(alpha=...)` 完成，MA11 不重复缩放。
- mask 值保留 `BF16(-10000)`，实际表示为 **−9984**；不能替换成负无穷。使用传入的实际掩码，而非忽略掩码只按三角位置推算。
- 前向沿用原 1024-thread、8-element vector 的归约树；反向沿用原128-thread、8-element vector的另一种归约树。两者不是任意可交换的“数学等价”归约。
- 反向先形成并舍入 `BF16(grad × probability)`，再扩展至 FP32 做归约；保留尾部乘加与最终BF16舍入，masked位置写正零。
- 前向生成独立输出，反向只保存自己的 probability 和 mask，不保存共享 scores 工作区，不存在跨层覆盖复用。
- 每次 native 调用使用 PyTorch 当前 stream；没有新增 collective、辅助 stream、CPU同步或主机描述符队列。候选新增的 Python／ctypes 提交、布局检查和分配均包含在正式计时中。
- 初始化核对原 Megatron class／mask函数SHA256、PyTorch 2.6.0、32个模块及固定配置；只支持当前 TP8、PP/CP=1、四microbatch、2048序列、BF16、零dropout、无recompute／CUDA Graph。没有静默回退。

为防止原 Flux `--use_fast_math` 改变非规格化数及指数行为，候选将 MA11 放在**独立 CUDA 编译单元**，仅该文件追加 `--ftz=false --prec-div=true --prec-sqrt=true`；原 MA89 的 runtime 源码与编译选项保持。新增三个 C ABI 接口显式加入导出表，并在构建／复用／在线worker初始化前检查真实ELF导出，避免重现MA9首次缺符号的问题。

**逐位等价是必须验证的条件，不是仅凭源码推导就宣布成立。** 候选 smoke 先运行六类确定性 GPU／ATen 前后向字节对照：普通分数、全零ties、全mask、非三角mask、未掩码分数低于有限sentinel、subnormal概率；不推进训练RNG。随后完整模型 smoke 的每一次softmax前向／反向也与原ATen逐字节核对，包括正负零。任何差异立即停止，不放宽容差。

## 5. 2% 预算与否证条件

每步128次注意力调用，9.196 ms相当于每次前后向合计节省约 **71.84 μs**。该目标需要中间态存取、view重建及提交开销的合计净下降；仅减少384次kernel提交不足以直接判定达标。

该方案仍可能失败：原工作量可能部分被通信隐藏，融合后寄存器／共享内存压力可能降低吞吐，Python调用开销可能抵消收益，或者新kernel与服务器安装的ATen编译行为存在数值差异。数值／路径失败时停止；正确但不足2%时完整保留结果，不挑最快窗口。

| 验收字段 | 条件 |
| --- | --- |
| `increment_over_MA89_validated` | 每个trial配对点估计>0且95% CI下界>0，正确性及路径通过 |
| `target_point_observed` | 每个trial点估计≥2%；单独满足不代表稳定达标 |
| `target_validated` | 每个trial点估计与95% CI下界均≥2%，且最终独立profile通过 |

MA89历史量级下约450.610ms只是预算换算；本次同期MA89若发生整体漂移，目标随其配对结果计算。一次trial仍属于探索性证据。

### 8.3. 数值一致，审计没有进入正式计时

[算子预检](../../../../logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/operator/preflight.json)通过原row projection的前向逐位、input／weight／bias／residual梯度及更新检查。[完整模型预检](../../../../logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/preflight.json)通过每rank全部 **389个可训练参数**的三步梯度／更新指纹检查。

### 8.5. 显存与算子阶段的解释

正式窗口显存按每窗口八rank最大值再求均值：两组allocated峰值相同，均为 **17.423663 GiB**；reserved为 **17.509766 / 17.478516 GiB**，候选少 **32 MiB**。删除累计20GiB复制不等于释放20GiB驻留显存，两者不能混用。

原row projection算子阶段平均前向为Attention **101.270 / 92.732 μs**、MLP **150.342 / 140.086 μs**。对照的第2号块（从0编号）分别出现 **161.503 / 223.393 μs** 的慢窗口，已全部保留；对应配对结果为Attention **+6.641%［−0.250%, +18.793%］**、MLP **+5.563%［+0.005%, +15.595%］**。这一阶段并不调用MA11注意力softmax，两臂row投影代码相同，**不能将这些差值解释为MA11算子收益或用于替代完整训练结论**。

### 8.6. 离线复核与本轮结论

新增只读复核 [audit.py](../../../../outputs/h100/phase6/ma11-results-audit-20261027/audit.py)、[audit.json](../../../../outputs/h100/phase6/ma11-results-audit-20261027/audit.json) 和 [audit.log](../../../../outputs/h100/phase6/ma11-results-audit-20261027/audit.log)。使用回传批次自己的冻结控制器，核对 **48份冻结脚本／配置文件及1,383份Megatron文件**，从原始rank记录和trace重算算子／完整训练的两份report及两份profile-summary，四份均与保存值完全一致；另独立复算全部窗口、前后半程与整体bootstrap、显存和最终验收字段。原报告、计划、预检及批次状态文件哈希不变。

回传目录没有服务器 `build/` 及动态库本体，本地复核依据冻结源码、构建／加载身份记录及真实trace，没有重新加载服务器二进制，也没有重新运行GPU。上机前验证文件保持历史状态。

**本轮结论：MA11在完整MA89上获得已验证的正增量，450.662ms／+1.952%；原定2%目标尚未达成。** 机制路径与数值均通过，可作为后续独立复测的候选；目前不能将一个trial的结果表述为稳定达到2%，也不据此挑选窗口或放宽验收门槛。
