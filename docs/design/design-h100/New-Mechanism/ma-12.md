## 1. 新的优化对象是跨 GPU 的完成依赖

[baseline.md](baseline.md) 中 MA89 的历史均值为 **459.8060027899919 ms/step**。此前成功的 MA8 删除反向重复输入 AllGather，MA9 删除逐参数统计提交；两者都没有改变 row projection 中的这个顺序：

```text
本 GPU 的原 GEMM / packet 写入
→ CudaIpcBarrierAll：等待整个 TP 组到达发布点
→ 原有序 decoder + bias + residual
→ 原 LayerNorm
```

对应实现为 [ma2_cr2_sources.py](../../../../tools/h100/phase6/ma2_cr2_sources.py) 的 `cr2_forward`，以及 [ma4_f_sources.py](../../../../tools/h100/phase6/ma4_f_sources.py) 的消费者融合。即使本 rank 下一段计算只需要某些已经写完的数据，原路径也要等待其他 rank 的整个 producer 完成。

MA12 改变这一依赖：**消费者等待自己下一次读取的来源片段，而不是整个 TP 组当前调用完成；生产者覆盖旧工作区前，单独等待旧消费者读完。** 这是发布与复用协议的改变，不是调 decoder 的 tile/warp 参数，也不是把原屏障搬到 GEMM 前面。

| 原 MA89 profile 指标 | 数值 |
| --- | ---: |
| producer GPU 工作量之和 | 22.669 ms |
| 整轮发布屏障 GPU 区间之和 | 100.678 ms |
| decoder＋bias/residual GPU 工作量之和 | 2.954 ms |

**100.678 ms 不是可删除的通信成本，也不是候选的预期收益。** 其中含 rank 到达偏差和 profiler 扰动；消费者最终仍要等到所需数据。本方案只可能回收“等待无关片段、整轮汇合和后继启动”造成的额外串行区间。不能将 CPU/GPU 区间相加，也不跨 rank 相减绝对时间。profile 整步约 743 ms，而无 profiler 历史步时约 460 ms，已说明二者不可直接换算。

## 2. 从 mKernel 借鉴什么

[mKernel: Fast Multi-GPU, Multi-Node Fused Kernels](https://arxiv.org/html/2609.13585v1) 的 §3.1、§3.2 和 §4 将数据就绪、消费及通信资源分配分开处理：已就绪的局部工作可以前进，不必等整个计算结束；就绪通知必须对应已经可见的数据，而不能仅表示请求已提交。其[官方实现](https://github.com/uccl-project/mKernel)采用持久 kernel 和不同计算／通信角色。

**MA12 是对就绪交接思想的本地适配，不是移植 mKernel 的整套 kernel。** 当前为单节点 TP8，保留原 Flux GEMM、量化 packet 和计算 stream，只重构现有 producer→decoder 的跨卡依赖；不引入 RDMA、host proxy、NVLS 求和、动态 SM 分区或新的通信库。论文的多节点 H200 加速比不作为本项目的预测。当前版本也没有让同一 GPU 的 producer 与 decoder 并发；它允许本 GPU 的 decoder 与其他 GPU 尚未完成的 producer 尾段重叠。

## 3. 机制：发布片段、消费片段、确认旧槽完成

每个既有双工作区槽增加一份独立 IPC 整数缓冲区：

```text
ready[source][local_tile][fragment]：8 × 64 × 8 个 int32 epoch
done：1 个 int32 epoch
总计 4097 × 4 = 16,388 字节 / rank / slot
```

64 个 row 模块各有两个槽，逻辑 flags 容量合计约 **2.0005 MiB/rank**；实际 allocated/reserved 增量仍以运行记录为准。

`ready` 放在接收 rank 的本地显存；每个 source 写自己的区域。`done` 表示这个 rank 对该槽本轮全部数据的读取已经结束，其他 rank 只读它。每个槽独立递增 epoch，从 1 开始，初值 0；达到上界时拒绝继续，不能回绕后误认旧数据。

### 3.1. 当前调用的发布与消费

原 producer 的 128×128 物理 tile 分八次 epilogue fragment 写回。每片包含两段各 8 行，分别位于 tile 的上、下半区，共 16 行；**不是连续 16 行**。量化字节及两个 scale、或未量化 BF16 数据写完后，全体 writer 先完成 system fence，再经 CTA 同步，由一个线程 system-release 写入该片的 epoch。

decoder 每个 warp 继续处理原来的一行 128 元素。读取某 source 前，先 system-acquire 等待对应片的当前 epoch，再进入原加载及归约逻辑。其映射为：

```text
row = group / 32
local_tile = (row / 128) * 32 + group % 32
fragment = (row % 64) / 8
index = (source * 64 + local_tile) * 8 + fragment
```

保留原 source 顺序；不能为了“先到先算”重排 BF16 加法。mask、到达表、选择性量化预算、packet 编码、decoder 几何、bias/residual 的两次 BF16 舍入均保持。发布包含本地及未量化贡献，不是只给 FP8 packet 加标记。

在 `end_step` 发布而非假定 `end_epilogue` 已完成整个 tile，是为了兼容原 CUTLASS Stream-K 的片段回调：一次回调可能只负责一个 reduce fragment。不得用一片的结束去宣布整个 tile 就绪。

### 3.2. 删除原屏障后如何防止覆盖

仅有 ready 不够。快 rank 如果提前复用 packet，慢 rank 可能读到下一轮数据。因此 MA12 将原屏障承担的工作区复用责任单独表达：

```text
首次初始化：分配 IPC flags → 本地清零 → 一次原全组屏障

稳态，同一计算 stream：
  wait_reuse(epoch e)：所有 receiver 的该槽 done ≥ e−1
  → 原 GEMM，逐片发布 ready=e
  → decoder 逐 source acquire ready≥e，并按原序计算
  → publish_done：本 rank 的 done=e
  → 原 LayerNorm
```

`publish_done` 是 decoder 后的独立小 kernel，利用 stream 的 grid 完成依赖；不使用不安全的“最后一个 CTA”计数或 kernel 内全 grid 自旋屏障。`wait_reuse` 等待的是**这个槽的前一次使用**，不是当前轮 producer。两个既有槽轮换，前次使用通常已经隔开一次投影调用；是否仍会等待要实测。

稳态原来的 `GEMM→全组屏障→decoder` 三个 kernel，变为 `reuse wait→GEMM→decoder→done publish` 四个 kernel。两个协议 kernel 均为 **1 block×32 threads**；原 producer 为 512×128，decoder 为 2048×128。flags 不逐调用清零，不在正式步中反复分配 IPC 缓冲区。

### 3.3. 进展与安全约束

- 每个 rank 都先提交本地 producer，再提交本地 decoder。decoder 的轮询只依赖对端已经排在 decoder 前面的 producer；没有等待同 GPU 尚未获得 SM 的未来 producer，也不占用辅助 stream。
- 复用等待只依赖较早 epoch 的 done。当前 producer 不能覆盖仍被旧 decoder 使用的数据；ready 的新 epoch 不能替代旧轮完成确认。
- release 必须晚于该片全部 payload 和 scale 的可见性；acquire 必须早于实际加载。不能把普通 `volatile` 标志当作发布协议。
- 32 层、64 个 row 模块的两个槽各自持有 flags，不能跨模块共用 epoch；原输出仍独立分配，禁止重试失败实例或异步释放缓冲区。
- 固定 TP8、单节点 NVLink、原形状及原调用次序。出现 rank 失败可能让对端等待，沿用 worker 超时终止整个实验，不能静默退回旧路径。

system fence 和 warp 同步的作用范围参见 [CUDA 12.8 Memory Fence Functions](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-c-programming-guide/index.html#memory-fence-functions) 与 [Synchronization Functions](https://docs.nvidia.com/cuda/archive/12.8.0/cuda-c-programming-guide/index.html#synchronization-functions)。本实现将这些原语组成上述协议；原设计要求通过八卡数值、反复复用和超时检查后再判断性能。本轮实际验证范围见第 8 节，不将有限步数实验视为所有交错的形式化证明。

实现：[ma12_sources.py](../../../../tools/h100/phase6/ma12_sources.py)、[ma12_tile_ready.cuh](../../../../tools/h100/phase6/ma12_tile_ready.cuh)。变换仅用于新实验的 candidate 源树；MA89 对照的 native 来源继续是原 F4＋MA9。新增 C ABI 显式加入导出表，构建、复用和在线 worker 检查源码、二进制和实际导出符号。

## 5. 2% 预算与可以推翻本假设的结果

以历史 MA89 量级计算：

```text
459.8060027899919 × 2% = 9.196120 ms / optimizer step
9.196120 ms ÷ 256 projections = 35.922344 μs / projection
历史量级下的目标步时 ≈ 450.610 ms
```

以上是预算，不是预测。达到目标需要每次投影平均净省约 35.92 μs，已经扣除新增 flags、system fence、acquire 轮询、两个小 kernel 和主机提交的成本。尤其片段发布每次有 512×8 个交接，writer fence 与 CTA 同步可能拖慢 producer；decoder 也可能仍被原有 source 顺序阻塞。这些都是本实验要测的成本，不应以“屏障 kernel 消失”宣称成功。

如果时间只是从原 barrier 移入 decoder／reuse wait，或者 producer 新增开销超过解耦收益，机制即使正确也可能无收益或退化。保留全部结果；不继续扫 tile 参数或挑选最快窗口来补足 2%。

实际验收只比较**本次同期 MA89**与候选，按每 trial 的完整配对块计算收益：

| 判定 | 条件 |
| --- | --- |
| 正增量验证 | 点估计及 95% CI 下界均 >0，数值与路径通过 |
| 观察到 2% 点估计 | 点估计 ≥2%；单独满足不等于稳定达标 |
| `target_validated` | 每个请求 trial 的点估计及 95% CI 下界均 ≥2%，完整正确性和最终独立 profile 通过 |

## 8. MA12-v1 八卡实测：发布协议执行成功，但未验证整步收益

### 8.1. 批次、完成范围与对照

批次为 [`ma12-v1-tile-publication-1x-50steps-20261027-133258-366517`](../../../../logs/h100/phase6/ma12-v1-tile-publication-1x-50steps-20261027-133258-366517/batch-state.json)。在八张 H100 80GB、每卡 132 SM 上完成构建、算子预检／计时／profile、完整模型预检／计时／profile，最终为 **`completed/done`**。启动记录的 `ma12_build=null`，即本批重新构建，没有直接复用旧 build。

本轮只有 **1 个独立 trial**：8 个完整平衡配对块、16 个正式训练窗口、128 份正式 rank 记录、800 个正式 optimizer step。两组各 8 个窗口、64 份 rank 记录、400 个正式步骤；每窗口另有 10 步预热，正式计时 50 步。前后各四块只是同一 trial 的两个区段，不能当作两次独立复测。

对照为完整 MA89（`F4-cache-zcount`），候选为 `F4-cache-zcount-tilepub`。两组共同保留原 MA8-v2 和 MA9；原 Python 适配器、训练函数及计时循环的身份检查通过。候选只增加片段发布／完成确认协议，量化 mask、source 顺序、GEMM 计算和 decoder 几何仍按原协议执行。

| 1 | 457.391 | 459.702 | −0.505 |

仅第 3、7 块更快。第 7 块的对照偏慢，必须保留；也不能单独取该块的 +2.154% 宣称达标。前四块配对收益为 **−0.421%［−1.099%, +0.146%］**，后四块为 **+0.010%［−1.185%, +1.524%］**，两段均未验证正收益。

**本次结论是“未验证加速，未达 2%”，不是“整步显著退化”，也不是“证明两组性能完全等价”。** 分母使用本轮 MA89 的 459.554 ms，不与历史 459.806 ms 跨批次相减。

### 8.3. 独立算子明确变慢

[算子报告](../../../../logs/h100/phase6/ma12-v1-tile-publication-1x-50steps-20261027-133258-366517/operator/report.json) 测量完整 projection＋bias＋residual API。每项均使用八个同期配对块：

| 算子 | MA89 平均 μs | MA12 平均 μs | 候选增加 μs | 配对收益 %［95% CI］ |
| --- | ---: | ---: | ---: | --- |
| Attention，K=512 | 93.201 | 190.698 | 97.497 | −104.612［−105.221, −103.936］ |
| MLP，K=2048 | 140.088 | 248.367 | 108.279 | −77.292［−78.131, −76.618］ |

候选独立算子耗时分别约为对照的 **2.046 倍、1.773 倍**，与原来希望减少发布尾部的方向相反。这个结果不能乘以 256 后直接当作整步损失；完整模型中的 rank 到达、主机提交和后继依赖不同，最终仍以第 8.2 节的完整步时为准。

### 8.4. 路径已改变，等待与发布开销没有消失

[完整训练 profile](../../../../logs/h100/phase6/ma12-v1-tile-publication-1x-50steps-20261027-133258-366517/fullstep/profile-summary.json) 的两组共 16 份 trace 全部通过冻结解析器。每 rank 每步的 256 次 row projection 中：

- MA89 保留 256 个发布屏障、256 个原 decoder。
- MA12 没有稳态整轮发布屏障，执行 256 个 reuse wait、256 个新 decoder、256 个 done publish；各调用的 producer、工作区清零、decoder 和完成发布均满足同 stream 顺序。
- producer 均为 512×128，decoder 均为 2048×128，两个协议 kernel 均为 1×32；后继仍为原 LayerNorm，无独立 bias/residual add 回退。
- 两组目标 QKV／FC1 的反向输入 AllGather 均为 0，保留 256 次前向输入 AllGather 和 256 次 dgrad ReduceScatter；MA9 的两个统计 kernel、原标量 AllReduce，以及原 row backward 均通过检查。

下表先在各 rank 内取同角色 128 次调用的中位数，再取八 rank 中位数，单位 μs。**这些是有 profiler 的区间，包含等待；各列中位数不可相加作为某次调用或正式步时。**

| 角色／组别 | producer | 原发布屏障 | decoder | reuse wait | done publish | 整条投影链 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Attention／MA89 | 65.336 | 494.576 | 11.232 | 0 | 0 | 575.208 |
| Attention／MA12 | 160.392 | 0 | 489.640 | 2.080 | 2.800 | 663.168 |
| MLP／MA89 | 111.304 | 236.224 | 11.776 | 0 | 0 | 364.576 |
| MLP／MA12 | 214.096 | 0 | 243.504 | 2.160 | 2.785 | 471.632 |

结果支持两个诊断：**producer 本身变慢，原屏障的一部分等待转入了 decoder 内部。** Attention／MLP 的 producer 中位区间分别增加约 **95.056／102.792 μs**；原来的大块发布等待虽然从 kernel 列表消失，新 decoder 却变成数百 μs。reuse／done 各约 2–3 μs，不能仅优化这两个小 kernel 就假定能追回目标。

源码中的逐片 system fence、CTA 同步和 ready 发布是 producer 新增工作；这些是优先怀疑的成本来源，**当前没有单独关闭 fence 或改变发布粒度的消融，不能把全部增加精确归因于某条指令**。同样，decoder 区间还包含原加载、归约和轮询，不能全部称为“通信时间”。

profile 证明新协议确实运行，不能证明移除的旧屏障区间等量转化为收益。它与无 profiler 整步结果的差异也不构成矛盾：profile 改变了主机开销和 rank 到达时序，局部路径工作量不等于完整训练的净关键路径。

进一步按“各 rank 的 256 次投影工作量先求和，再取八 rank 中位数”复算，producer 从 **22.651 增至 47.960 ms/step**；原屏障的 **99.552 ms** 消失，但 decoder 从 **2.966 增至 96.847 ms**，另有 reuse wait **0.552 ms**、done publish **0.723 ms**。两组整步 profile GPU span 为 **744.131／752.439 ms**，明显高于正式步时。这些总量支持上述诊断，仍不能相加减来分解正式计时中仅约 0.924 ms 的差异。

### 8.5. 数值一致性与显存口径

算子预检、完整模型 smoke 和正式窗口的数值门槛均通过。完整模型覆盖每 rank 全部 **389 个可训练参数**的梯度和更新指纹；同块、同 rank 的正式 loss／grad_norm 轨迹与最终参数指纹一致。两组平均 loss 均为 **3.793363792030723**，末步 loss 均为 **0.00030573460389859974**，末步 grad norm 均为 **0.01800245891878419**。这是固定合成输入下本次短程实验的一致性证据，不是长期收敛证明。

按“每窗口八 rank 最大值，再跨窗口平均”统计，PyTorch allocated 峰值为 **17.423713／17.423663 GiB**，reserved 峰值均为 **17.509766 GiB**。这说明本轮 PyTorch allocator 记录基本相同，**不能据此声称 MA12 不增加 GPU 显存**：新增 flags 的逻辑容量仍约 2.0005 MiB/rank，[IPC 分配实现](../../../../src/ths_op/flux_shm.cc) 使用 CUDA 直接分配并包装为 tensor，不能完整反映在 PyTorch allocated/reserved 计数中；该源码哈希与本批两组构建身份记录一致。本轮没有报告覆盖全部外部分配的独立设备总显存峰值。

### 8.6. 复核与当前选择

使用本批回传的冻结控制器对原始记录和 trace 做只读重算，产物为 [audit.py](../../../../outputs/h100/phase6/ma12-results-audit-20261027/audit.py)、[audit.json](../../../../outputs/h100/phase6/ma12-results-audit-20261027/audit.json) 和 [audit.log](../../../../outputs/h100/phase6/ma12-results-audit-20261027/audit.log)。原批次报告、计划和预检文件保留原样；上机前验证记录也不回写为 GPU 已通过。

复核校验了 **49 份冻结脚本／配置及 1,383 份 Megatron 文件**，从原始记录重算的两份 report 和两份 profile-summary 均与保存值完全一致；128 份正式 rank 记录的最大墙钟步时、前后区段及全八块的 bootstrap、显存汇总也独立重算一致，所有受保护原证据哈希不变。构建身份记录中的 candidate 新增一个 header、修改六个既有文件，与注册的 MA12 原生变换范围一致。

回传目录没有服务器 `build/` 和动态库本体，因此本地复核使用冻结源码、构建／加载身份记录与真实执行 trace，**没有重新加载服务器二进制，也没有重新运行 GPU**。服务器批次的完整构建与实测记录、上机前本地检查、本次离线复核三者分开保留。

**当前继续使用 MA89，停止把这版逐片发布配置作为已验证加速方案。** 本实验验证了发布／复用协议能够执行并维持本轮数值一致性，却没有兑现至少 2% 的关键路径缩短。若继续研究，应先证明发布成本和等待成本能同时下降，再发起新的同期完整步实验；不能从本轮已移除 256 个屏障、个别正收益块或历史 100.678 ms 屏障区间推导出成功，也不能据此否定所有细粒度通信方案。
