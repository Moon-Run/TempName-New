# MA14：在 MA11 上以单调 epoch 替换二值 GPU 发布握手

更新：2026-10-29。**MA11 尚未实现这里的单调 epoch 发布屏障；本次将其实现为 MA14。它针对实际存在的 GPU 二值 CAS 握手，不宣称删除 MA11 中不存在的逐调用 CPU 同步。当前尚无 MA14 八卡性能结果，不能宣称已经低于 450 ms。**

## 1. 先核对：图片中的机制与 MA11 实际路径

MA11 的实测完整步时为 **450.6624015 ms/step**，同期 MA89 为 459.6383128 ms，完整八块配对收益 +1.952456%［95% CI：+1.711198%, +2.271447%］。这是一轮独立 trial；本次仍须重新测同期 MA11，不能拿旧结果与 MA14 跨批次相减。参见旧仓库 [MA11 实验记录](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-11.md)及[原始报告](../../../../../TempName/logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/report.json)。

源代码链是 `ma11_sources → ma9_sources → MA4-F → CR2`。实际路径见 [CR2 原始提交](../../../../tools/h100/phase6/ma2_cr2_sources.py)、[MA4-F 消费者融合](../../../../tools/h100/phase6/ma4_f_sources.py)和 [GPU 二值屏障](../../../../src/cuda/cudaipc_barrier_all.cu)。

| 图片中的描述 | MA11 实际情况 | MA14 的处理 |
| --- | --- | --- |
| 每轮 ready 清零，再做 GPU→CPU 同步与主机跨 rank 屏障 | 已不在 CR2 稳态 forward 路径；已有双槽和 GPU 流上发布屏障 | 不虚构这部分收益 |
| `ready=0/1` 不能区分轮次 | GPU 发布屏障确实使用二值状态：每个 peer `atomicCAS_system(0,1)`，随后 `atomicCAS_system(1,0)` | 用单写者、单调递增的 64 位 epoch 替换 CAS 置位／复位 |
| 新一轮不能覆盖还在读取的 payload | 现有双槽覆盖整套 BF16 工作区、FP8 payload 和 scale；中间一次全 rank 发布屏障隐式确认前一轮读完 | 保留该证明所需的完整屏障、双槽交替和固定 stream |

因此，MA14 不是“给 MA11 删除 host barrier”的补丁，而是将图片中**轮次标识和缓冲区安全复用**的思路落实到当前真正存在的 GPU 握手。把 ready 改成 epoch、却不证明旧数据已经读完，是不安全的；本设计使用已有双槽顺序提供这个证明。

## 2. 为什么不是重复失败的 MA6／7／10／12／13

旧仓库的 [baseline](../../../../../TempName/docs/design/design-h100/New-Mechanism/baseline.md)、[MA6](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-6.md)、[MA7](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-7.md)、[MA8](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-8.md)、[MA9](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-9.md)、[MA89](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-8&9.md)、[MA10](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-10.md)、[MA12](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-12.md)、[MA13](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-13.md)共同决定本次边界：

- MA8-v2 激活缓存、MA9 零统计融合和 MA11 causal softmax 在两组完整保留；不能用 MA89 作为本次对照。
- 不扫描 decoder 的 CTA／warp／grid 参数，不改变 Hadamard、量化比例、source 累加顺序或 BF16 舍入，不加入 MA10 的其他 autograd 改写，也不重做 MA13 softmax。
- **MA12 已经做过片段级 epoch 发布与 done 确认。** 它在 GEMM epilogue 每片段加系统 fence 和 ready 发布，让 decoder 按 source／fragment 轮询，并加入独立 reuse/done kernel；同期 MA89 459.554 ms，MA12 460.477 ms，配对收益 −0.205%［−0.889%, +0.584%］，没有验证整步正增量。
- MA14 **不提前消费未完成 GEMM 的片段**。producer、packet ABI、decoder 代码及几何不变，仍是 `GEMM → 一个发布 kernel → decoder`。GPU 热路径唯一替换是屏障内部的二值远端 RMW／复位协议改成单写者 epoch store/load；没有 MA12 的片段发布、decoder 轮询和额外完成 kernel。候选另有 Python 双槽／stream guard 和 C++ epoch 参数提交，它们的成本全部进入正式计时。

这是一个可以独立证伪的 GPU 同步协议实验。它没有提出新的矩阵数学算法，也不保证 epoch 一定比当前 CAS 屏障快。

## 3. 协议与复用证明

每个现有 native slot 拥有独立 IPC epoch 空间。每个接收 rank 的空间包含八个 64 位字，`ready[receiver][source]` 只有对应 source 写入。初始化时一次性清零，并用原屏障确认全部空间已初始化；初始化不计入稳态窗口。

每个 slot 的本地 epoch 从 1 递增。一次调用在同一 CUDA stream 上执行：

```text
原 GEMM、Hadamard、FP8 编码及 BF16／packet 写入
    ↓ stream 顺序
MA14 epoch 发布 kernel（1 CTA）
    向各 receiver 的 ready[receiver][my_rank] release-store 本 slot epoch
    本地 acquire-load 各 ready[my_rank][source]，等待 >= 本 slot epoch
    ↓ 全 CTA 完成、stream 顺序
原 decoder／按 source 有序归约／两次 BF16 bias+residual 加法
```

只对单写者标志做 system-scope release/acquire，不使用远端 atomicCAS，不清零旧 epoch，不改变通信 payload 字节数。内存排序依据 [NVIDIA PTX 的 memory synchronization 与 CUDA API synchronization 定义](https://docs.nvidia.com/cuda/parallel-thread-execution/#memory-synchronization)：同流前一 kernel 完成、系统域发布／获取、后一 kernel 开始共同建立可见性。CPU 上的计数值不能代替这些 GPU 内存序操作。

对逻辑调用 `k`，使用 `slot = k % 2`。若任意 rank 要在 `k+2` 覆写该 slot，它在本地 stream 上必须先完成 `k+1` 的全 rank 发布屏障。每个 peer 只有在自己的 `decode(k)` 完成后才能发布 `ready(k+1)`，所以此时**所有 peer 已读完调用 k**。该证明同时覆盖 BF16 工作区、FP8 payload 和两组 scale。

这里没有新增逐消费者 `done_epoch`：`k+1` 的完整发布屏障已经充当 `k` 的完成确认。若以后删除完整屏障、改成单槽或跨 stream 提交，这个证明就失效，必须重新设计显式消费确认，不能继续沿用 MA14。

使用 `>= epoch` 避免把单调进度错误当成二值状态；不允许计数回绕。所有 rank 必须以相同顺序调用双槽 wrapper；异常后实例失效，禁止重试。CUDA graph、改变设备／stream 和越过 wrapper 直接复用内部 slot 均不属于支持路径。新 metadata 独立于 `FluxTacoConfig`，避免仅为同步而增加 GEMM 的参数尺寸或改变其资源占用。

实现入口为 [ma14_sources.py](../../../../tools/h100/phase6/ma14_sources.py) 和 [ma14_epoch.cuh](../../../../tools/h100/phase6/ma14_epoch.cuh)。生成器保持对照与原 MA11 candidate 完全一致，仅向候选添加协议；[ma14_build.py](../../../../tools/h100/phase6/ma14_build.py) 冻结两组源码与二进制身份，拒绝修改过的候选、旧实验 build 和未编译源码。没有覆盖原 MA11 实现。

## 4. 可期待什么，如何判断失败

历史 MA11 每个训练 step 有 256 次目标发布屏障。其 profile kernel 时长包含等待其他 rank 的 GEMM、主机提交差异和 profiler 扰动，**不是可全部消除的开销**。MA14 保留等待慢 rank 的语义，只试图减少协议自身的远端原子操作、复位握手与串行依赖。

历史 450.662 ms 下，2% 约为 9.013 ms/step，均摊 256 次发布约需净省 35.2 μs/次。这只是目标难度估算：如果实际 CAS 协议自身成本达不到这个量级，epoch 即使更快也可能远低于 2%。新增 metadata、轮询方式、主机 guard 开销或通信竞争也可能抵消收益。

任一输出／梯度不一致、协议路径回退或失去双槽保护都应使实验失败。完整步时的置信区间跨零则没有验证收益；只有 profile kernel 变短也不能宣布关键路径缩短。保留慢窗口和负收益，不追加配置扫描来挑选最好结果。

在 **TempName-New 仓库根目录、已配置的 H100 八卡环境**执行：

```bash

# 默认一轮：同期 MA11 对照与 MA14
bash tools/h100/phase6/run_ma14.sh --execute

# 前台运行，便于直接观察失败
bash tools/h100/phase6/run_ma14.sh --foreground --execute

# 需要两个独立 trial 时显式指定
bash tools/h100/phase6/run_ma14.sh --trials 2 --execute
```

两组为：

| arm | 实际实现 |
| --- | --- |
| `F4-cache-zcount-csoftmax` | 原 MA11 candidate，作为本次对照 |
| `F4-cache-zcount-csoftmax-epoch` | 同一 MA11，加 MA14 epoch 发布屏障 |

启动器依次准备并编译两组、执行算子数值与双槽错位复用检查、算子计时／profile、完整模型 smoke、完整训练配对计时、独立完整训练 profile。默认每 trial 八个平衡配对块、16 个窗口；每窗口 10 步预热＋50 步计时，共 800 个正式 optimizer step。计时使用完整窗口 wall time，不能用 CUDA kernel 求和取代。

数值检查保留 MA11 的训练梯度／参数更新指纹、loss／grad norm 轨迹以及共同 MA8／MA9／MA11 路径。新增协议检查关注连续提交、rank 人为延迟、两个 slot 反复复用、保留旧输出的独立性和 epoch 计数。候选 profile 必须证明原发布 kernel 被 MA14 kernel 替换，producer 与 decoder 的顺序和数量不变。

主要结果位于启动器打印的 `logs/h100/phase6/ma14-v1-epoch-reuse-…/` 目录：`batch-state.json`、`operator/report.json`、`operator/profile-summary.json`、`fullstep/preflight.json`、`fullstep/report.json` 和 `fullstep/profile-summary.json`。`completed` 仅表示实验完整，正增量与 2% 门槛需分别检查；相对 MA11 的 2% 目标要求每个请求 trial 的配对点估计及 95% CI 下界都达到 2%。

[run_ma14.sh](../../../../tools/h100/phase6/run_ma14.sh) 沿用 MA11 的 H100 recovery 环境查找。解释器不在默认位置时可设置 `MA14_PYTHON=/path/to/python`；CUDA 路径和 NCCL 开发库可用 `--cuda-home`、`--build-cuda-home`、`--nccl-root` 显式传入。复用时只接受 `--ma14-build /absolute/path/to/verified-ma14-build`，不接受旧 MA11 build 充当两组实验。
