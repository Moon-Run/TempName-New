# MA15：在 MA11 上重放注意力计算图，缩短主机提交链

更新：2026-10-31。**MA15 将每层本地 attention core 的前向和反向录制成 CUDA Graph，保留 MA11 的数学运算。新服务器解除内部单核绑核后，本轮同期 MA11 为 344.230 ms/step，MA11＋MA15 为 315.552 ms/step；八块配对收益 +8.109%，bootstrap 95% CI 为 [+4.137%, +13.595%]，达到本轮 2% 增量目标。** 这是一个独立 trial，不能作为跨机器或长期稳定收益的保证。

本轮原始 `batch-state.json` 仍为 `failed`：训练与 profile 已完成，最后的监督器验收受到 tuple/list 序列化比较问题影响。2026-10-31 的只读离线复核已重现正式报告及全部 16 份 profile 的持久化内容，未改动原始证据或状态。结果、显存代价和状态说明见第 7 节。历史约 450 ms → 当前约 344 ms 的环境变化另见 [CPU 启动修复分析](../New-Mechanism-v2/kernel_launch.md)，不能计入 MA15 的算法收益。

## 2. 新的切入点：固定计算的重复提交

MA11 已消除了 mask／softmax 的若干中间张量，但注意力仍由 eager autograd 每次重新遍历和逐算子提交：

```text
列投影产生 Q、K、V
    ↓
Python／ATen：reshape → QK baddbmm → MA11 softmax → PV bmm → 布局复制
    ↓
原 row projection／通信／后继层

反向：原 row backward
    ↓
autograd：布局反向 → PV 两个梯度 GEMM → MA11 backward → QK 两个梯度 GEMM
    ↓
原 QKV split backward／column backward／DDP
```

固定实验中，序列长 2048、microbatch 1、TP8、本地四个注意力头、head dimension 128，且 attention dropout 为零。每个 optimizer step 有 32 层 × 4 microbatch，即 **128 次 core forward 和 128 次 core backward**；这些局部计算的拓扑重复，但普通 eager 执行仍支付每次调度成本。

历史 MA11 中，MA13 大幅缩短 softmax 内核却未带来可信整步收益；MA7／MA10 增加主机调度后反而退化。这些现象**与主机提交成为部分限制相容，但不足以证明整步 CPU-bound**。MA15 将这个假设变成独立实验：GPU 数学工作保持，改变其提交方式，检查整步是否真正变快。

历史八 rank 的 MA11 trace 已逐份重放验证。每 rank 分别统计，再取八 rank 中位数：

| 每 optimizer step 的局部 attention 指标 | 前向 | 反向 |
| --- | ---: | ---: |
| 选定 CPU 算子／autograd scope 的非重叠并集 | 38.655 ms | 54.422 ms |
| 包围这些操作的 CPU 区间并集，含其间提交间隙 | 50.498 ms | 65.819 ms |
| 按 CUDA correlation 归属的 GPU 工作量 | 19.625 ms | 15.910 ms |
| 原 GPU kernel 数 | 512 | 896 |
| 原 cuBLAS 四字节 workspace clear 数 | 128 | 256 |

前后向合并后重新按 rank 统计的 CPU scope 并集中位数为 **93.349 ms**，包围区间为 **116.266 ms**，GPU 工作量为 **35.545 ms**；“合并后的中位数”不要求等于两个中位数之和。前向选取 QK、MA11 softmax、PV、context contiguous；反向选取 PV backward、MA11 backward、QK backward，详细定义和 trace SHA256 均已留存。

可复算分析见 [analyze_ma15_baseline.py](../../../../tools/h100/phase6/analyze_ma15_baseline.py) 和 [baseline-analysis.json](../../../../outputs/h100/phase6/ma15-validation-20261029/baseline-analysis.json)。这些是 **profiler 扰动后的局部工作证据**。CPU 区间、GPU 工作量和含等待的 NCCL／IPC 时长不能相加，不能直接称为可删除的关键路径。正式性能指标始终是无 profiler 的完整 optimizer step 墙钟。

## 3. 机制：每层一对图，保留原始算术

**MA15 的新意是本项目中的提交与生命周期机制，不是声称发明 CUDA Graph，也不是另一种 softmax 数学算法。** [PyTorch 2.6 的 CUDA Graph 文档](https://docs.pytorch.org/docs/2.6/notes/cuda.html#cuda-graphs) 描述了固定地址的图重放及局部网络捕获；本方案将捕获边界限定在无参数、无 collective 的 `DotProductAttention`。

```text
首次预热：真实 layout → 固定输入缓冲 → 捕获原 core forward／backward

每次 forward：Q/K/V、实际 bool mask 复制到静态缓冲
             → 一次 forward graph replay → 输出独立副本

每次 backward：输出梯度复制到静态缓冲
              → 一次 backward graph replay → dQ/dK/dV 独立副本
```

前后向图内仍调用原 `torch.baddbmm`／`torch.bmm`、原 MA11 native softmax，以及原布局操作。保留 BF16 张量边界、QK 的原 alpha、实际 mask 的有限哨兵、反向 BF16 乘积舍入和归约顺序；不改用 FlashAttention、SDPA、近似 GELU 或另一种 softmax。

源代码保持不等于已经证明运行时逐位一致：cuBLAS 的捕获行为与输入 layout 也可能影响实际路径。因此安装时核对固定源码和配置，H100 smoke 再比较实际输出和三个输入梯度的全部字节；不等价就停止，不放宽容差。

### 3.1. 捕获边界与原 MA11 兼容

原 CR2／MA4-F 明确拒绝将其 IPC forward 放进 CUDA Graph。MA15 遵守这个限制：**不捕获列投影、row projection、任何 NCCL／IPC、DDP、optimizer 或整个训练 step**，也不改 `enable_cuda_graph`／`external_cuda_graph` 配置来绕过现有检查。

MA15 仅实例绑定 32 个 attention core。两臂先原样安装 MA8、MA9、MA11，候选随后安装 graph adapter。录制时临时使用原 MA11 的无审计 softmax 包装，避免把 CPU 数值检查录入图；录制后立即恢复原包装。实际 smoke 的 eager oracle 仍经过原 MA11 审计，正式计时不执行 oracle。

### 3.2. 地址、布局与所有权

- Q/K/V 按实际 shape／stride 创建静态输入，保留原非连续布局。不能擅自 `.contiguous()` 后宣称仅改变提交。
- mask 内容每次复制，不把第一次观察到的 causal mask 当成永不改变的常量。
- 32 层分别持有图及其内存池；同一层 forward 后必须先完成对应 backward，才允许下一次 forward。当前每 microbatch 的 `32F → 32B` 顺序满足此条件。
- 图输出和输入梯度返回独立副本，避免后一次重放覆盖外部仍持有的结果。所有副本都计入候选时间和显存。
- capture 的辅助流只用于初始化；训练重放在原 compute stream 上提交，原通信与消费者依赖保持。
- stream／device／layout 漂移、重复 forward、重复 backward、未完成调用、异常后重试均拒绝继续。不支持高阶梯度、recompute、非零 dropout、不同形状或全局图嵌套。

实现见 [ma15_adapter.py](../../../../tools/h100/phase6/ma15_adapter.py)。两臂 native source 直接使用同一个原 MA11 注册变换，见 [ma15_sources.py](../../../../tools/h100/phase6/ma15_sources.py)；无需新增 CUDA kernel 或导出 ABI。独立构建目录仍各自编译、记录源码和二进制身份。

## 4. 收益预算与失败条件

MA15 试图缩短的是 **CPU 遍历／提交 → GPU 工作到达 → 后继通信到达** 的依赖链。它不删除注意力 FLOPs，不减少原通信字节数，不把 NCCL 等待时间全部算作收益。

复制开销必须正面计算。当前简单实现每次 core 调用，Q/K/V 共 6 MiB、mask 4 MiB、输出 2 MiB、输出梯度 2 MiB、三个输入梯度副本共 6 MiB，合计 **20 MiB 逻辑复制量**；每 step 128 次即 2.5 GiB，若分别计读写则为 5 GiB。这不是 HBM 实测流量，也不包含原来就在图中的布局复制。非连续布局的实际 storage 与图池占用会更大。

还必须保留 PyTorch 自身的重放开销：固定的 [PyTorch 2.6 CUDAGraph::replay](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/cuda/CUDAGraph.cpp) 无条件调用 [generator replay_prologue](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/cuda/CUDAGeneratorImpl.cpp)，即使图中没有随机操作，也会写入 seed／offset 两个 int64 元素。每次重放多两个 fill kernel，每 step 共 **512 个**；RNG offset 增量为零不等于没有这两次设备写入。profile 对它们单独归属和计时。

前向的边界复制和这些 fill 甚至可能增加提交次数；不能仅凭“一次 graph launch”宣布 launch 总数减少。收益需要反向 autograd／ATen 调度的减少覆盖这些副本、保护检查和固定图池成本。静态 Q/K/V 按原 stride 独立分配时每层约 18 MiB，加 mask 后 32 层仅输入面约 **704 MiB**，还不含输出、梯度和图池。正式报告同时记录 allocated／reserved 显存峰值，不能把 capture 后常驻内存排除在资源比较之外。

历史 450.662 ms 的 2% 为约 9.013 ms/step，平均到 256 个前／反向边界约需净省 **35.2 μs／边界**。这只是目标难度，不是预测。若 CPU 提交本来已被 GPU 工作隐藏，或复制与图池压力抵消收益，本方案应判为没有验证收益并保留负结果，不继续扫描复制策略挑最好点。

`run_ma11.sh --execute` 的历史比较对象是 MA89／MA11，不能直接代替本入口。新 [run_ma15.sh](../../../../tools/h100/phase6/run_ma15.sh) 与 [detach_ma15.py](../../../../tools/h100/phase6/detach_ma15.py) 保留独立进程、冻结源码、两臂库隔离及监督器。

流程为：构建两臂 → 原 row projection 数值／计时／profile → 完整模型 smoke → 完整训练配对计时 → 独立完整训练 profile。row 阶段只检查共同投影路径，**不触发 attention graph，不能用其性能评价 MA15**。

每 trial 固定八个 AB/BA 平衡配对块、16 个 fresh-process 窗口。每窗口 10 步预热＋50 步正式，共 800 个正式 optimizer step；capture 发生于首次预热，并报告初始化状态，不能在正式窗口重新捕获。完整步包含四个 microbatch 的前后向、通信、梯度处理、优化器更新与清梯度；按八 rank 最大窗口墙钟／50 统计。

验证要求：

1. 两臂原 389 参数的梯度、更新指纹、loss／grad norm 轨迹一致；MA8／MA9／MA11 原路径检查保留。
2. 候选 smoke 每次用真实 Q/K/V、mask 和输出梯度，比对 eager core 与图的输出、dQ/dK/dV；检查 32 层覆盖、每层调用配对和图复用。审计不进入正式计时。
3. 候选 profile 每步必须有 128 次 forward、128 次 backward 重放，各 marker 恰有一次图启动；图内仍有各 128 次原 MA11 前／反向内核，原 attention eager 提交已消失。复制开销、原 GEMM 与 softmax 路径、同流顺序一并检查。
4. profiler 必须提供可核对的图启动／GPU 工作归属。缺少证据时拒绝给出“路径验证通过”，不能仅按 kernel 名字计数或把缺事件当加速。
5. 保留所有慢窗口与负收益。配对点估计和 bootstrap 95% CI 下界均大于零，才验证正增量；两者均至少 2%，才达到沿用的 2% 目标。每个请求 trial 分别满足，不能把一轮切成两轮。

独立 profile 进程在候选图实例化**之前**先启动、结束一次短 CUDA profiler 会话，并保持 `TEARDOWN_CUPTI=0`、`DISABLE_CUPTI_LAZY_REINIT=1`。这是为了规避 [CUPTI late attach 对图内 memcpy／memset 的记录限制](https://docs.nvidia.com/cupti/main/main.html#late-attach-limitations)，并沿用 [PyTorch 2.6 的图与 CUPTI teardown 兼容处理](https://github.com/pytorch/pytorch/blob/v2.6.0/torch/profiler/profiler.py)。这一步只在 profile 进程执行并记录状态；smoke／正式计时进程不连接 profiler，原正式 profile 循环保持。实际 H100 trace 仍须通过节点归属检查，初始化成功本身不代表路径已经验证。

输出目录为启动器打印的 `logs/h100/phase6/ma15-v1-attention-graph-…/`，重点查看 `batch-state.json`、`fullstep/preflight.json`、`fullstep/report.json`、`fullstep/profile-summary.json`。只有完整阶段全部通过才标为完成；完成不等于正增量或达到 2%。

解释器默认沿用 H100 recovery 环境；自定义环境可设置 `MA15_PYTHON=/path/to/python`，并传入 `--cuda-home`、`--build-cuda-home`、`--nccl-root`。已有构建只能通过 `--ma15-build /absolute/path/to/verified-ma15-build` 复用，不能将旧实验目录冒充两臂新结果。

### 7.4. 为什么 batch 仍显示 failed

原 [batch-state.json](../../../../../Load/logs/ma15-v1-attention-graph-1x-50steps-20261031-132153-299757/batch-state.json) 停在 `stage="fullstep-profile"`，错误为 `ValueError: Full-model attention graph execution evidence missing`。但算子阶段、正式训练、报告生成和 profile 子进程均已有产物；问题出在监督器将保存的 JSON 与重新解析出的 Python 对象直接比较。

冻结的 [ma15_profile.py](../../../../../Load/logs/ma15-v1-attention-graph-1x-50steps-20261031-132153-299757/fullstep/scripts/ma15_profile.py) 用 `(name, grid, block)` tuple 生成 `kernel_signatures`。JSON 保存再读回后变成 list，Python 中 tuple 与 list 不相等。因此监督器的 `evidence == full.profile_summary(root)` 为假，即使所有字段在 JSON 表示下完全一致，也会抛出上面的笼统错误。

本次只读复核验证了冻结源码哈希，重算正式报告与两臂共 16 份 profile：正式报告精确相等，profile 的 Python 直接相等检查为假，按 JSON 表示归一后精确相等。记录和证据 SHA256 见 [validation.json](../../../../../Load/analysis/20261031-ma15-affinity/validation.json)。这里没有修改旧 trace、报告、manifest 或 batch 状态，也没有重新运行 GPU。**因此可以总结已完成的训练与已复核的执行证据，但不能把原启动器状态写成 completed。**

### 7.5. 与解除单核绑核的关系

同一新服务器此前 [04:43 批次](../../../../../Load/logs/ma15-v1-attention-graph-1x-50steps-20261031-044305-267152/fullstep/report.json) 仍使用单逻辑 CPU 强绑，MA11／MA15 分别为 **597.170／545.655 ms**，配对收益 **+8.622%［+8.070%, +9.252%］**。当前 inherit 批次为 **344.230／315.552 ms**，配对收益约 8.109%。两臂的绝对时间都降低约 42%，说明绑核修复改善了共同的运行环境；MA15 仍是在同一环境下额外减少 attention 的 CPU 提交成本。

将历史约 450 ms 直接减去当前 315.552 ms 会混合服务器、CPU affinity 与 MA15 三个因素。MA15 本轮应引用同期 **344.230 → 315.552 ms** 及配对区间。CPU affinity 的源码差异、同机对照、跨 rank 等待和归因边界见 [kernel_launch.md](../New-Mechanism-v2/kernel_launch.md)。本节派生数字及原始文件哈希可用 [analyze.py](../../../../../Load/analysis/20261031-ma15-affinity/analyze.py) 复算，结果保存于 [metrics.json](../../../../../Load/analysis/20261031-ma15-affinity/metrics.json)。
