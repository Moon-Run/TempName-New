# MA16：在 MA11 上让本地列投影与输入 AllGather 重叠

更新：2026-10-29。**MA16 已实现为独立候选：QKV／FC1 前向先启动异步 AllGather，同时计算本 rank 已有的 256 行输入；通信完成后再计算远端行。它改变计算与通信的依赖关系，计算量和通信量不减。当前尚未执行 H100 八卡实验，不能宣称已将 MA11 的 450.662 ms 进一步缩短。**

在新仓库中运行同期 MA11／MA16 对比：

```bash

bash tools/h100/phase6/run_ma16.sh --execute
```

## 1. 先区分已有机制与新的机会

此前并非完全没有尝试 overlap：MA6 做过 row 反向 bias–AllGather 重排，MA7 做过辅助流 wgrad。它们失败的结果必须纳入选择，而不能简单把已有 overlap 改名为 MA16。

## 2. MA11 里确实存在这条串行依赖

原 MA8 缓存函数的前向仍为：

```text
每 rank 本地 X：[256, 1, 4096]
  → 同步接口 AllGather：[2048, 1, 4096]
  → 完整 torch.matmul(X_full, Wᵀ)
  → 原 bias／后继运算
```

这里的“同步接口”指在当前 compute stream 上建立整个 gather 完成依赖，不表示 CPU 一直阻塞到 GPU 通信结束。每个 rank 原本已经拥有自己那 256 行，计算这些行并不依赖远端数据；MA11 仍让它们等待整个 gather。

已逐份重放历史 MA11 八个 rank 的真实 trace，按自动 autograd sequence 和 CUDA launch correlation 归属，全部通过原 MA11 路径检查。每 rank 每步有 **128 次 QKV、128 次 FC1**；八 rank 合计 **2048 次**目标前向全部先完成 AG 再启动 GEMM，实际重叠为零。

| 指标：先求 rank 内中位数，再取八 rank 中位数 | QKV | FC1 |
| --- | ---: | ---: |
| 前向 AllGather kernel 区间 | 279.744 μs | 323.968 μs |
| 前向完整 GEMM | 45.280 μs | 46.912 μs |
| AG end → GEMM start 间隔 | 2.400 μs | 2.368 μs |

将两种投影先在每 rank 合并、再取八 rank 中位数，前向 GEMM 工作量为 **11.792865 ms/step**，AG 区间总和为 **81.472510 ms/step**。后者包含等待其他 rank 和 profiler 扰动，**绝不是可以全部隐藏的 81 ms**。

同样的分析还确认 column backward 已有 `dgrad → async ReduceScatter → wgrad → wait`：2048 次中 1776 次观察到 RS／wgrad 交叠，按 rank 合并后的 wgrad 工作量中位数为 16.732713 ms，交叠区间为 16.373929 ms。因此，再“打开 column backward overlap”不构成新机制。

可复算证据：[分析脚本](../../../../tools/h100/phase6/analyze_ma16_baseline.py)、[baseline-analysis.json](../../../../outputs/h100/phase6/ma16-validation-20261029/baseline-analysis.json)。JSON 保留八份 trace 的 SHA256、逐 rank 统计和全部 2048 条目标前向记录。上述数值都是 profile 局部观测，正式收益由无 profiler 的完整步墙钟决定。

## 3. 机制：移除本地 token 对远端输入的假依赖

设 TP rank 为 `r`，本地行区间为 `[256r, 256(r+1))`。候选每次只发起**一次原 AllGather**，并分配与 MA8 相同的独立完整输入缓存；另分配一个完整输出。执行顺序为：

```text
NCCL stream：  ├──────── AllGather(X_local → X_full) ────────┤
compute stream：  ├ GEMM(X_local) ┤  wait(AG)  ├ GEMM(prefix) ┤ ├ GEMM(suffix) ┤ → bias
                     写本 rank 输出行             写前方行           写后方行
```

图仅表示依赖，不表示预测时长。核心实现相当于：

```python
handle = all_gather(X_full, X_local, group=tp_group, async_op=True)
matmul(X_local, W.T, out=Y[lo:hi])
handle.wait()
if lo:
    matmul(X_full[:lo], W.T, out=Y[:lo])
if hi < 2048:
    matmul(X_full[hi:], W.T, out=Y[hi:])
```

`r=0/7` 是两次 GEMM，中间六个 rank 是三次 GEMM。直接写连续输出切片，不做 `cat`、pack、重排或输出 DtoD 复制。每个 token 只计算一次；每个 GEMM 的 K 始终为 4096，不拆 K、不累加 partial product。QKV 输出宽度 1536，FC1 为 2048；原 bias 仍在完整输出形成后单独执行。

这是一项本项目此前未测过的**输入依赖调度机制**，不是声称发明了 AG–GEMM overlap。它也不是缩减 GEMM FLOPs：有用工作完全相同，只把无需远端输入的部分移入通信窗口。

实现见 [ma16_adapter.py](../../../../tools/h100/phase6/ma16_adapter.py)。候选仅绑定 64 个 QKV／FC1 实例，未修改全局 Megatron 函数、LM head 或 row projection。两臂 native 源码完全等同原 MA11 candidate，见 [ma16_sources.py](../../../../tools/h100/phase6/ma16_sources.py)；没有新增 CUDA kernel、通信协议或编译参数扫描。

### 3.1. 为什么没有读取正在通信写入的缓冲区

本地 GEMM 读取调用者原有的 `X_local`，**不是**正在被 NCCL 写入的 `X_full[lo:hi]`。NCCL 和 GEMM 对原输入都是只读，输出地址互不重叠。`handle.wait()` 在本地 GEMM 提交之后、任何远端 GEMM 之前建立当前 compute stream 的完成依赖；依据 [PyTorch 2.6 Work.wait 文档](https://docs.pytorch.org/docs/2.6/distributed.html#torch.distributed.Work.wait)，这通常是流依赖，不是新增 CPU 全设备同步。

完整 `X_full` 由原 autograd context 独立持有，继续供原 MA8 wgrad 使用；没有借用易被下层覆盖的全局 gather buffer。前后向传参、bias 梯度、dgrad／RS／wgrad 顺序和已有反向 overlap 都保持。生成的候选 backward 与原 MA8 backward 的 AST SHA256 必须一致。

安装和调用检查固定 TP8、PP/CP=1、32 层、序列 2048、BF16、microbatch 1、原 stream／device／布局，以及无重计算和 CUDA Graph。异常后实例失效，不能继续重试。新增 Python 守卫、计数、切片、提交和分配成本全部进入正式计时。

### 3.2. 数学等价不能代替逐位验证

只拆 M 仍可能改变 cuBLAS 选用的实现，因此不能仅凭 K 未拆就宣布逐位等价。候选 smoke 的**每次列投影**均执行原完整 `torch.matmul(X_full, W.T)` oracle，逐字节比较整个输出，同时核对 gathered 本地行与实际本地输入；任意差异立即失败，不放宽 BF16 容差，也不静默回退。

随后沿用完整模型的全部 389 个参数梯度／更新指纹、loss／grad norm 轨迹和最终参数指纹检查。原 MA11 softmax 自测与逐调用 smoke 也在两臂保留。oracle、字节检查和 profile marker 均不进入正式计时；运行时必要守卫和计数仍计时。

## 4. 收益预算与明确的失败条件

把原整块投影记为 `G_full`，本地投影为 `G_local`，远端投影之和为 `G_remote`，AG 为 `A`。理想无竞争时，局部依赖链从：

```text
MA11： A + G_full
MA16： max(A, G_local) + G_remote + 新增提交开销
```

实际 NCCL 与 GEMM 会竞争 SM／HBM，拆 M 也会降低 GEMM 效率，因此 `G_local + G_remote` 未必等于 `G_full`，新 AG 时长也未必等于旧 AG 时长。候选 profile 必须同时报告交叠量、local／remote GEMM 工作量、AG 长度及前向包围区间。

本次两臂测量的是“本地行先算”这一完整调度的净效果；即使观察到 overlap 和整步正增量，也不能把全部收益定量归因于交叠，因为 GEMM 的 M 形状同时改变。profile 交集只是机制证据，不用于这种因果分摊。

本地行仅为总行数的 **1/8**。假设耗时严格随行数线性变化，旧前向 GEMM 11.792865 ms 的八分之一仅约 **1.474108 ms/step（历史步时的 0.327%）**；这只是理想缩放的量级算例，既不是实测候选耗时，也不是严格上界。真实小 GEMM 的固定成本、额外 launch 和 Python 开销可能把它全部吃掉。

因此，**本方案不承诺 2%**。它优先验证一个边界清楚、无需修改通信协议的 overlap 假设；若只获得小幅可信正增量，也应如实报告。沿用现有 harness 的 2% 字段只是额外目标：450.662 ms 的 2% 约为 9.013 ms，不能从上述证据推导它能够实现。

失败情形包括：拆 M 数值不同；GPU 实际仍串行；远端数据提前读取；NCCL／GEMM 竞争增加；中间 rank 三次 GEMM 成为慢 rank；提交开销超过隐藏时间。保持原 `CUDA_DEVICE_MAX_CONNECTIONS` 等环境，两臂不偷偷采用不同设置，也不把 MA7 的失败无证据归因于某个环境变量。

[启动脚本](../../../../tools/h100/phase6/run_ma16.sh)与[监督器](../../../../tools/h100/phase6/detach_ma16.py)沿用 H100 recovery 环境，默认 CUDA 12.8 构建、12.4 运行。可以用 `MA16_PYTHON=/path/to/python` 指定解释器，并用 `--cuda-home`、`--build-cuda-home`、`--nccl-root`、`--megatron` 指定环境路径。只复用当前协议验证通过的两臂 build：`--ma16-build /absolute/path/to/verified-ma16-build`。

完整顺序为：构建两臂 → 原 row projection 算子数值／计时／profile → 完整模型 smoke → 配对完整训练计时 → 独立完整训练 profile。row 算子阶段不调用 column forward，仅检查共同基线，不能以其计时评价 MA16。

每 trial 使用 **8 个 AB/BA 平衡配对块、16 个独立进程窗口**，每窗口 10 步预热＋50 步正式，合计 **800 个正式 optimizer step**。完整步包含四个 microbatch 的前后向、通信、optimizer 更新和清梯度；以八 rank 最大窗口墙钟／50 计时，保留所有慢窗口、负收益和显存峰值。按完整块对数耗时比作 10,000 次 bootstrap；一轮 trial 仍是探索性证据。

[MA16 profile 检查器](../../../../tools/h100/phase6/ma16_profile.py)按真实 CUDA launch 归属检查：

1. 每 rank 的 256 次候选前向各有一个原 NCCL AG，以及与 rank 对应的两／三个 GEMM；local 提交在 wait 之前，wait scope 内必须有实际 CUDA stream wait 事件，远端 kernel 只能在 AG 完成后执行。
2. 本地 GEMM 与 AG 位于不同 GPU stream，且两类投影都实际观察到时间交集；报告每类 128 次中的重叠次数和交叠总量。异步 API 存在但 GPU 零重叠时，路径验收失败。
3. 没有额外 GPU 拼接／复制；只允许有明确 cuBLAS 所属关系的原 workspace 清零；完整 bias 位于所有投影之后。
4. 原 MA8 backward、四次原 LM head、row forward／backward、MA9 零统计和 MA11 attention 路径继续通过检查。不会删掉新事件再交给旧解析器冒充原路径。

`increment_over_MA11_validated` 要求每个 trial 的配对收益点估计与 95% CI 下界均大于零；`target_validated` 则要求两者均至少 2%。最终监督器还必须等独立 profile 通过，才提交完整验收。Profile 中看到重叠不能替代完整步变快；完整步变快也不能单凭异步调用推断机制已成立。

输出目录为启动器打印的 `logs/h100/phase6/ma16-v1-local-first-…/`，主要文件：

- `batch-state.json`、`handoff/container-supervisor.log`：阶段、失败原因及最终状态。
- `fullstep/preflight.json`：完整模型正确性。
- `fullstep/report.json`：配对完整步收益、区间、轨迹和显存。
- `fullstep/profile-summary.json`：原路径与新增 `column_overlap` 证据。

`report.json` 可能早于最终 profile 产生；`completed` 也只表示实验完成，不能替代正增量字段。数值不一致或实际零重叠时保留原始证据，不把失败写成性能成功。
