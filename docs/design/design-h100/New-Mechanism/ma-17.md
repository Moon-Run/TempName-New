# MA17：在 MA11 上把必等的 AllGather 直接提交到计算流

更新：2026-10-29。**MA17 改变列投影前向的通信提交机制：用同一个进程已加载的 NCCL，在原计算流上直接执行 AllGather，然后执行原完整 GEMM。它省去这些调用的 ProcessGroup Work 对象及跨流交接，不减少计算量，也不减少通信量。当前已实现独立对比入口，尚无 MA17 的 H100 八卡结果，不能宣称已经缩短 450 ms。**

```bash
cd TempName-New
bash tools/h100/phase6/run_ma17.sh --execute
```

## 1. 为什么选择通信提交，而不再缩短计算内核

旧仓库 [MA11](../../../../../TempName/docs/design/design-h100/New-Mechanism/ma-11.md) 的首轮完整 optimizer step 为 **450.6624015 ms**，同期 MA89 为 459.6383128 ms，配对收益 +1.952%［95% CI：+1.711%, +2.271%］。[baseline](../../../../../TempName/docs/design/design-h100/New-Mechanism/baseline.md) 是历史汇总，不能拿其中不同批次的值代替本实验的同期对照。

MA11 的 QKV／FC1 前向仍有一条重复 **32 层 × 2 列投影 × 4 microbatch＝256 次／step** 的依赖链：

```text
原计算流：输入就绪 ──记录事件──┐                         ┌──等待完成事件──完整 GEMM
                            ↓                         ↑
ProcessGroup NCCL 流：    等待输入 → AllGather → 记录完成
CPU：                    创建／提交 Work → Work.wait → 提交 GEMM
```

这里的 `Work.wait` 一般是在计算流上放入依赖，不等于 CPU 等待整个通信完成。关键在于：**这个前向调用收齐所有 rank 的输入之后，才能进行原完整 GEMM；中间没有可以利用通信流并行的独立计算。** 跨流交接维持了正确顺序，但不是这条依赖链不可替代的一部分。

MA8 已删除反向中重复的输入 AllGather，却仍需保留前向这一次；MA17 在这个保留的调用上减少软件提交路径。它不改变 MA8 的缓存算法，也不把本地 GEMM 拆出来重叠。

### 1.1. 来自真实 MA11 trace 的依据

已复核旧批次 `ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643` 的八份完整 MA11 trace，2048 次目标调用全部满足：每次发送 **1,048,576 个 BF16 元素＝2 MiB**，得到 rank 顺序的 **16 MiB** 完整输入；AllGather 和 GEMM 使用不同的 stream，完整 GEMM 在 gather 完成后开始。四次 vocabulary head 前向不在这 256 次中。

先在每 rank 内求和，再取八 rank 中位数：

| 每 optimizer step 的目标路径观测 | 时间 |
| --- | ---: |
| `c10d::_allgather_base_` CPU 区间 | 26.616 ms |
| 显式 `Work.wait` CPU 区间 | 0.992 ms |
| 从 gather 开始到 wait 结束的 CPU 包围区间 | 30.553 ms |
| collective 内 CUDA API 子区间 | 5.655 ms |
| 其中 kernel launch API | 2.669 ms |
| 其中 event record／wait API | 2.494 ms |
| 显式 Work.wait 内 stream-wait API | 0.324 ms |
| AllGather GPU 区间总和 | 81.473 ms |
| 后继完整 GEMM GPU 工作量 | 11.793 ms |
| gather 完成到 GEMM 开始的 GPU 间隙总和 | 0.612 ms |

每 rank 的 collective 区间内有 1280 次 `cudaEventRecord`、768 次 `cudaStreamWaitEvent`，显式 Work.wait 中另有 256 次 `cudaStreamWaitEvent`。**其中一部分可能属于 NCCL 内部的提交协议，MA17 不承诺全部删除这些事件。** 新解析器允许并单独记录 native NCCL 内部事件，检查删除的是 ProcessGroup 及外部交接。

可复算脚本：[analyze_ma17_baseline.py](../../../../tools/h100/phase6/analyze_ma17_baseline.py)；逐 rank、逐调用、输入 trace SHA256 和聚合口径：[baseline-analysis.json](../../../../outputs/h100/phase6/ma17-validation-20261029/baseline-analysis.json)。

这些区间有嵌套，也受到 profiler 及 rank 到达偏差影响。`c10d` 的 profiler 通信标注本身也有成本，native 路径省去这类标注不能算作正式收益。**不能相加上述数字，更不能声称“可节省 30.553 ms”或把 81.473 ms 当成纯传输时间。** 特别是显式 Work.wait 不足 1 ms，单独删除它不支持 2% 的预算；MA17 需要整个重复提交链和后继工作到达时间的净改善。

## 2. 新机制：保持通信依赖，用同流顺序承接它

```text
MA17 原计算流：输入就绪 → ncclAllGather → 原完整 GEMM → 原 bias
CPU：                   native NCCL 调用 → 原 GEMM 提交

反向：原 MA8 retained_input → 原 dgrad／异步 ReduceScatter／wgrad
```

这是本项目中新的 **collective 提交机制**，不是新的 NCCL 算法。NCCL API 接受调用者的 CUDA stream，返回表示已提交而非已经执行完成；同一 stream 的顺序保证输入生产、AllGather 和消费 GEMM 的依赖。[NCCL CUDA stream 语义](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/streams.html)；AllGather 的接收布局按 communicator rank 排列。[NCCL AllGather API](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/colls.html#ncclallgather)

原 PyTorch 2.6 ProcessGroupNCCL 的实现使用专门的 NCCL stream、输入事件同步及 Work 的 stream 等待；这与本次历史 trace 中的事件相符。[固定版本 ProcessGroupNCCL.cpp](https://github.com/pytorch/pytorch/blob/v2.6.0/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp)

实现：[ma17_adapter.py](../../../../tools/h100/phase6/ma17_adapter.py)。从原 MA8 的固定源码生成 `_MA17DirectAllGatherLinear`，除了类名，只把前向 `dist_all_gather_func(...)` 换成模块绑定的 native gather。分配完整输入、保存 `input／weight／total_input`、原完整 `torch.matmul`、bias 和整个 backward 均保留；源码及 backward AST 有身份检查。

### 2.1. 初始化和运行边界

- 在预热前创建一个专用 TP8 communicator，64 个 QKV／FC1 模块共用。通过原 TP group 交换 unique ID，使用 TP rank 顺序；不把全局 rank 随意当成子组 rank。
- 从 `/proc/self/maps` 选取**唯一已加载的** `libnccl`，用 `RTLD_NOLOAD` 打开；核对 `ncclGetVersion` 和 PyTorch 编译时的 `torch.cuda.nccl.version()`，还检查从 `libtorch_cuda.so` 依赖解析得到的两个 NCCL 函数地址与该库一致。跨 rank 核对库 SHA256 和 group 映射，后续所有候选窗口必须与首个 smoke 身份相同。缺库、多个库、静态或不同符号实现、版本或映射不一致直接停止。
- 每次仍发送原 BF16 元素个数、使用 `ncclBfloat16`，目标直接是原 MA8 独立分配的完整输入。没有 staging、额外输入／输出 clone、压缩、GEMM 拆分或新 CUDA kernel。
- 原输入保存到 autograd context，完整输入保留给 wgrad；原同流分配和消费维持张量生命周期。不会把上一层临时共享缓冲冒充 retained input。
- 固定设备、计算流、形状、连续布局及每 microbatch 的 32 组 QKV→FC1 调用顺序；异常、重入、错误顺序或 CUDA Graph 请求停止执行。正式计时包括 ctypes、这些检查及计数器的成本。
- 原 row backward AllGather、column backward 异步 ReduceScatter、vocabulary head、optimizer 标量 collective 仍使用原路径。MA17 不在这些原本有重叠的地方强制改成同流。

专用 communicator 与原 communicator 的调用顺序必须在所有 rank 一致。当前固定训练拓扑、原 PG 的输入／输出流依赖，以及 MA17 的同流顺序共同保持这一点；不把该实现泛化到任意多线程、多 pipeline 或多个并发计算流。NCCL 官方也明确要求多个 communicator 的调用顺序和同步一致，否则可能死锁。[NCCL 2.21 communicator 指南](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2215/user-guide/docs/usage/communicators.html#using-multiple-nccl-communicators-concurrently)

native API 返回错误时终止并 abort；报告阶段核对异步错误，正常结束在同步后显式 destroy。raw communicator 没有接入 PyTorch 的 watchdog；初始化或设备通信挂起仍依靠原实验监督器的 `--worker-timeout` 结束整个 worker 进程组，不能把超时窗口丢弃后继续统计。这里不增加训练时的逐次 CPU 同步。

## 4. 收益目标、资源成本和否证条件

沿用 2% 门槛。历史量级下，`450.6624015 × 2% ≈ 9.013 ms/step`，分摊到 256 次目标调用，需要平均净省约 **35.2 μs／次**。若同期 MA11 恰为历史值，对应约 441.649 ms；这只是预算换算，不是 MA17 的预测或已测结果。

该目标并不容易：CPU 提交可能已经被设备工作覆盖；ctypes、参数检查和顺序保护可能抵消省下的成本；新 communicator 的缓冲区、通道选择和资源竞争也可能造成回退。AllGather 的传输字节和跨 rank 同步没有消失。若只有 CPU profile 区间缩短、整步区间跨零，结论应为“未验证正增量”。

两臂 native MA11 源码相同，见 [ma17_sources.py](../../../../tools/h100/phase6/ma17_sources.py)。使用同一已加载的 NCCL 并不保证新 communicator 的算法／协议选择完全一样：历史目标内核为 `AllGather_RING_LL`，新 profile 按角色记录全部 AllGather kernel 名称。若发生变化，完整实验收益仍是整个候选的结果，不能全部归因于删除 Work／事件；需要单独说明这个混杂因素。默认不扫描或强制另一套 `NCCL_PROTO`／`NCCL_ALGO`。

报告保留两臂 allocated／reserved 显存峰值；native NCCL 分配不全部受 PyTorch allocator 统计覆盖，因此还记录专用 communicator 初始化前后和窗口执行完成后的 `cudaMemGetInfo` 观测，覆盖首次通信可能发生的延迟分配。它们是设备快照，受共享设备活动影响，也不代表稳定峰值。初始化、销毁在计时之外，通信器常驻资源与正式调用成本留在候选中。

| `F4-cache-zcount-csoftmax` | 完整原 MA11，原 ProcessGroup column forward AllGather |

原 `run_ma11.sh --execute` 比较的是 MA89／MA11；本次应运行 [run_ma17.sh](../../../../tools/h100/phase6/run_ma17.sh)。[监督器](../../../../tools/h100/phase6/detach_ma17.py)沿用 fresh-process 窗口、两臂库隔离、源码冻结、构建身份验证及失败状态记录。

完整流程：构建两臂 → 原 row projection 算子预检／计时／profile → 完整模型 smoke → 配对完整训练计时 → 独立完整训练 profile。算子阶段只检查两臂共同的 row 路径，**不触发 MA17，不能用它评价 MA17 收益**。

每 trial 固定 **8 个 AB/BA 平衡块、16 个独立进程窗口、128 份正式 rank 记录、800 个正式 optimizer step**；每窗口 10 步预热＋50 步正式。完整步仍包含四个 microbatch 的前后向、通信、梯度处理、optimizer 更新和清梯度。采用八 rank 最大窗口墙钟／50，按完整配对块对数耗时比作 10,000 次 bootstrap，保留全部慢窗口与负结果。两个 trial 共 1600 正式步，不能把一轮的前后半程当成两次独立实验。

解释器默认沿用 H100 recovery 环境；可设 `MA17_PYTHON=/path/to/python`，或传入 `--cuda-home`、`--build-cuda-home`、`--nccl-root`。复用只接受 `--ma17-build /absolute/path/to/verified-ma17-build`，旧 MA11/15/16 build 不能冒充本次两臂构建。

### 5.1. 正确性和实际路径门禁

1. 两臂安装同一 MA8／MA9／MA11；只有候选安装 MA17。原 8 个训练函数与正式计时循环 AST 固定。
2. 候选 smoke 对每次实际 gather 输出与原 ProcessGroup gather 的输出做全字节比较，核对远端数据及 rank 顺序。每 rank 为 `(2 预热＋3 检查) × 256＝1280` 次；正式计时／profile 的 gather oracle 次数必须为零。
3. 完整模型继续核对每 rank 全部 389 参数的梯度／更新指纹、loss／grad norm 轨迹和最终参数指纹。保留 MA11 自测及每次 softmax 前后向审计，不放宽数值门槛。
4. [MA17 profile 解析器](../../../../tools/h100/phase6/ma17_profile.py)要求 128 QKV＋128 FC1 的 native marker 各自唯一关联实际 AllGather launch；候选 gather 与完整 GEMM 同流，gather 完成在消费之前，每次仍只有一个完整前向 GEMM。缺少 launch、旧 PG 回退、额外 DtoD、错误流或提前消费均拒绝。
5. 原 column backward 的两次 GEMM、异步 ReduceScatter、bias 以及调用顺序完整；原 row backward、四个 vocabulary head、MA9 和 MA11 路径分别继续检查。NCCL 内部事件不误判成未删除的 PG 交接。
6. 每个请求 trial 的配对点估计和 95% CI 下界均大于零，才有 `increment_over_MA11_validated`；两者均至少 2%，且最终路径验证通过，才满足本轮 2% 验收门槛。单 trial 仍属于探索性证据。

输出为启动器打印的 `logs/h100/phase6/ma17-v1-direct-allgather-…/`。主要文件：`batch-state.json`、`fullstep/preflight.json`、`fullstep/report.json`、`fullstep/profile-summary.json`，新增路径字段为 `column_direct_allgather`。`report.json` 写出时独立 profile 可能还没结束；必须结合最终 batch 状态。`completed` 表示实验完成，不等于候选更快。
