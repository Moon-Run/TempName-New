## 2. 实际存在的串行边界与数据规模

MA8 删除了反向中重复的 input AllGather，但保留每层 QKV／FC1 前向的一次 AllGather。固定配置是 TP8、序列长 2048、microbatch 1、hidden size 4096、32 层、每 step 四个 microbatch：

```text
MA11：本 rank 输入 [256,1,4096] BF16
          ↓ ProcessGroup / NCCL AllGather
      完整输入 [2048,1,4096] BF16，按 TP rank 排列
          ↓ 原完整 torch.matmul
      QKV 或 FC1 输出
          ↓
      完整输入继续保留，供原 MA8 backward 的 wgrad 使用
```

从旧 MA11 的八份完整 profile 重新解析得到：每 rank 每 optimizer step 有 **256 次目标 gather**，合计 2048 次，全部是 `AllGather_RING_LL`；后继完整 GEMM 均在对应 gather 完成后启动。四个 vocabulary head 不在目标范围。

| 原 MA11 指标 | 每 rank 先统计，再取八 rank 中位数 |
| --- | ---: |
| 每次本地 input | 1,048,576 个 BF16 元素＝2 MiB |
| 每次完整 gathered input | 16 MiB，其中远端数据 14 MiB |
| 256 次目标 NCCL kernel 区间总和 | 81.473 ms |
| 后继 256 次完整 GEMM 工作量 | 11.793 ms |
| gather 完成至 GEMM 开始的间隙总和 | 0.612 ms |

可复算脚本为 [analyze_ma18_baseline.py](../../../../tools/h100/phase6/analyze_ma18_baseline.py)，结果及原始 trace SHA256 在 [baseline-analysis.json](../../../../outputs/h100/phase6/ma18-validation-20261029/baseline-analysis.json)。它重读八份原 trace，并复核 autograd 配对、CUDA launch correlation、输入尺寸和原 MA11 组合路径。

**81.473 ms 包含 rank 到达偏差、等待和 profiler 扰动，不是纯传输成本，更不是可全部删除的时间。** 这里能证明的是 gather→完整 GEMM 依赖确实存在；不能由此断言当前带宽不足、SM 已饱和或可省几十毫秒。MA18 改善的必要条件是：替换后的“暂存＋发布＋拉取＋软件提交”让后继计算在真实训练中更早到达。

## 3. 新机制：固定注册、双槽暂存、直接拉取

在预热前，八个 rank 用现有 `flux.create_tensor_list` 建立两个 IPC 暂存槽和 peer 映射。每槽每 rank 2 MiB；**64 个列投影模块共用一套双槽**。创建一个原 `flux.GroupBarrier(..., ring_mode=False)`，仍使用现有 `CudaIpcBarrierAllKernel` 的二值系统域 CAS 发布机制。

每次列投影的完整输入仍由原 MA8 `torch.empty` 独立分配。逻辑调用 `k` 在原计算流上提交：

```text
1. cudaMemcpyAsync：当前 input → 自己的 stage[k % 2]，2 MiB
2. 原二值 IPC 发布屏障：确认全部 rank 的本次暂存写入完成
3. C++ 一次调用提交八次 cudaMemcpyAsync：
      source = (my_rank + offset) % 8，offset = 0…7
      peers[source][slot] → total_input[source 对应的连续切片]
4. 原完整 GEMM → 原 bias → 原后继层
```

循环轮换读取顺序以避免所有 receiver 首先集中读 rank 0；**目的切片始终按 communicator rank 排列**。八次拉取在同一 stream 依次提交，不声称八个 DMA 同时传输。暂存复制和 peer 拉取使用独立的 native C ABI helper，避免在 Python 中逐次调用八个 copy。没有新的 payload CUDA kernel，也没有 CPU 逐调用同步。

实现为 [ma18_adapter.py](../../../../tools/h100/phase6/ma18_adapter.py)、[ma18_ipc_allgather.cu](../../../../tools/h100/phase6/ma18_ipc_allgather.cu) 和 [ma18_sources.py](../../../../tools/h100/phase6/ma18_sources.py)。对照 native 源码精确等于原 MA11 candidate；候选只增加独立 CUDA translation unit、CMake 注册和三个导出符号。原 row producer／decoder、packet ABI、量化、source 归约顺序、BF16 舍入以及 MA11 softmax 编译参数不变。

### 3.1. 为什么双槽可以复用，而输出不能共用

先有 `stage(k) → publish(k) → pull(k)` 的同流顺序，确保读到本次输入。任意 rank 开始覆写 `stage(k+2)` 之前，必须已通过 `publish(k+1)`。每个 peer 在自己的同一 stream 上只有完成 `pull(k)`，才能进入 `publish(k+1)`；所以此时所有 peer 都已读完槽 `k % 2`。

这依赖以下条件同时成立：所有 rank 的列投影调用顺序相同；一个共享 transport；两个不同的暂存槽；完整发布屏障；固定设备与计算流。单槽、跳过屏障、错序或跨流都会使证明失效。实现对固定 topology／shape／顺序／stream 作检查，出现异常后将实例置为失败，禁止继续复用。

暂存区只存输入分片，不能用它或一个共享 16 MiB gather buffer 代替 MA8 retained input。每次结果独立分配并保存到 autograd context，后续层／microbatch 的 gather 不会覆盖旧结果。窗口结束时在测量之外同步所有 GPU 工作，并跨 rank 确认完成；`close()` 关闭后续提交，但将暂存 allocation 和 IPC 映射保留到 fresh-process worker 退出，避免仍有 peer 读取时提前释放。它不是通用长驻服务的即时销毁 API。

CUDA IPC 将分配映射到接收进程的地址空间；普通跨进程裸指针不能直接传给 copy。实现沿用 Flux 的 IPC 分配／映射生命周期，不导出临时 PyTorch allocation。参见 [CUDA 12.4 IPC 文档](https://docs.nvidia.com/cuda/archive/12.4.1/cuda-c-programming-guide/index.html#interprocess-communication)和 [cudaMemcpyAsync API](https://docs.nvidia.com/cuda/archive/12.4.1/cuda-runtime-api/group__CUDART__MEMORY.html)。

### 3.2. 资源成本及适用范围

| 资源 | MA18 的实际成本 |
| --- | --- |
| 自己持有的 staging allocation | 每 GPU 4 MiB，另加发布屏障 metadata |
| 八 rank staging 的映射地址范围 | 每进程合计 32 MiB；不代表又分配 32 MiB 本地显存 |
| 每次本地暂存复制 | 2 MiB |
| 每次完整拉取 | 16 MiB，包含 2 MiB 本地复制和 14 MiB 远端数据 |
| 每 rank 每 step 的逻辑复制量 | 512 MiB 暂存＋4 GiB 拉取，其中 3.5 GiB 来自远端 |
| 新提交成本 | 每次两次 ctypes helper 调用、一次 pybind barrier 调用，native 内九次 memcpy API；全部计时 |
| 新 GPU 发布工作 | 每次一个原二值 barrier kernel；整步目标路径新增 256 次 |

这些是逻辑 copy 字节，不是实测 HBM／NVLink wire traffic，不能把读写各计一次后与 NCCL payload 比较。MA18 **没有减少 AllGather 必须交付的 BF16 字节数**；ring 和 direct 的逻辑有效通信量都需要计入。它还增加暂存和本地复制，完全可能更慢。

完整报告保留两臂 PyTorch allocated／reserved 峰值；IPC 原生分配不一定计入该 allocator，因此候选每 rank 的状态另保存初始化前后及窗口结束后的 `cudaMemGetInfo` 快照。快照不是峰值，也可能受其他设备活动影响。

支持范围限当前单机八 GPU、可互访的 IPC、固定 TP8／PP1／CP1、原 BF16 训练配置。构建禁用 NVSHMEM，并用 native protocol 检查拒绝另一种 barrier backend。CUDA Graph、CPU offload、重计算、其他形状和跨节点不是本版本支持路径；不能静默退回 NCCL 后仍报作 MA18。

## 4. 论文启发及本项目中的边界

- [Optimizing ML Concurrent Computation and Communication with GPU DMA Engines](https://arxiv.org/html/2412.14335v2) 的 ConCCL 用 DMA 承担 AllGather／AllToAll 搬运，改变通信与计算竞争的资源。论文主要研究 AMD MI300X 和并发计算通信；MA18 借用“无算术 collective 可交给搬运引擎”的设计方向，不移植其硬件配置或性能数字。
- [MSCCL++: Rethinking GPU Communication Abstractions for AI Inference](https://arxiv.org/html/2504.09014v4) 将传输、可见性通知和源缓冲复用确认拆开。MA18 相应区分 payload copy、完整发布和双槽复用证明，但不引入它的 proxy thread／request queue，也不声称复现其实现或收益。

当前选择的 column forward 本身串行等待 gather。因此，**“释放 SM 给计算”并不能单独证明它更快**；本版没有新增 GEMM／通信重叠。需要验证的是直接 peer 搬运和固定协议是否降低了这条串行到达路径的净成本。CUDA copy 的实际执行路径由驱动和设备决定，候选 profile 必须看到九个对应的 GPU memcpy activity，而不是只看到九个 CPU API 调用。

相对 MA17，MA18 还同时改变了 transport、staging、publication 和提交路径；主实验测量整个候选的净效果。若整步加速，不能仅凭 MA11／MA18 两组把所有收益都归因于 copy engine，亦不能把省去 ProcessGroup 的成本重复计入。

## 5. 可证伪目标与验证要求

目标设为相对同期 MA11 **至少 2%**。历史 450.6624015 ms 的量级下，这约为 9.013 ms/step，即每次目标 gather 平均净省 35.2 μs；若对照恰为历史值，候选需到约 441.649 ms。这是目标预算，**不是性能预测**。

正式接受正增量要求每个 trial 的配对点估计与 95% CI 下界都大于零；2% 目标要求两者都至少为 2%。区间跨零、显著退化或只有 profile 内核缩短，均不能算关键路径优化成功。所有八个平衡块和慢窗口保留，不通过追加配置扫描挑选最好结果。

验证必须同时覆盖：

1. **原 MA11 身份与数学结果**：两组共同 MA8-v2／MA9／MA11；原完整 GEMM、backward 和训练计时函数身份；loss／grad norm 轨迹、全部可训练参数的梯度／更新指纹和最终参数一致。
2. **IPC 数据与复用**：smoke 中与原 NCCL AllGather 逐字节对照；在额外排队自测中轮换延迟 rank，连续复用双槽并保留旧输出，全部提交完后再核对，避免每次 oracle 同步掩盖 race。
3. **真实执行路径**：[ma18_profile.py](../../../../tools/h100/phase6/ma18_profile.py) 按 autograd sequence 和 CUDA correlation 检查每次一个原二值发布 kernel、九个 2 MiB device memcpy、正确 GPU 依赖、同流原完整 GEMM；每步共 2304 次目标 memcpy，且保留原 column backward／row／head 路径。额外 payload kernel、缺 copy、host copy、错误 stream、NCCL fallback 或新 host sync 均拒绝。
4. **完整步墙钟**：不带 profiler 的完整 optimizer-step 窗口决定收益；独立 profile 只证明机制和解释变化。算子阶段只检查原 row projection，不能用其结果宣称 MA18 通信收益。
