# MA19：在 MA11 上用固定 GPU 描述符集中发布 BF16 模型权重

更新：2026-10-30。**MA19 改变 optimizer 完成后的权重发布机制：在原来的更新边界，用一个读取常驻描述符的 CUDA kernel，把全部 FP32 master weights 转换并写回原 BF16 model weights，替代每步 389 次独立 `copy_`。原 Adam、梯度累加、通信以及 MA8／MA9／MA11 均保留。已提供实现与同期对比启动器，尚未执行候选 H100 八卡实验，不能写成已经低于 450 ms。**

```bash
cd TempName-New
bash tools/h100/phase6/run_ma19.sh --execute
```

这是一项有明确边界的小收益实验。历史 profile 中目标 GPU 尾部跨度约 **2.78 ms**，而且复制的主机提交已被 Adam 覆盖；不能将约 4 ms 的 CPU 区间再加上去，也没有证据支持本机制单独节省 9 ms／达到 2%。选择它的理由是：它位于参数更新的实际依赖链上，具有固定生命周期，且可以独立验证，不需要重试此前失败的梯度队列或通信等待重排。

## 2. MA11 仍存在什么串行工作

冻结的 Megatron `Float16OptimizerWithFloat16Params` 在 BF16 模式下把 `_dummy_overflow_buf` 设为 `None`。因此 `_copy_main_params_to_model_params()` 调用的 `_multi_tensor_copy_this_to_that()` 实际走 Python 循环：

```python
for master, model in zip(master_weights, model_weights):
    model.copy_(master)  # FP32 -> BF16，原目标 storage 不变
```

它没有使用已有的 multi-tensor fast path。原路径是：

```text
原梯度归约、裁剪、MA9 零统计
  → 原 FP32 Adam 更新（当前配置 49 个 GPU kernel）
  → 389 次 FP32→BF16 copy kernel
  → 原两个梯度 buffer 清零
  → 后续 optimizer step 使用更新后的 BF16 权重
```

[analyze_ma19_baseline.py](../../../../tools/h100/phase6/analyze_ma19_baseline.py) 重新读取旧 MA11 八份完整 trace，通过 CUDA correlation、`aten::copy_` 所属区间、kernel 类型、stream 和 launch geometry 识别每 rank 的 389 次目标 copy。四个发生在 Adam 前的 vocabulary-head BF16 转换被排除。

| 历史指标 | 每 rank 汇总，再取八 rank 中位数 |
| --- | ---: |
| 目标 copy 数量 | 389／step |
| 目标 `aten::copy_` CPU 区间总和 | 3.025531 ms |
| 首次 copy CPU 开始至最后一次结束 | 4.048209 ms |
| 其中嵌套的 CUDA launch API 总和 | 1.587282 ms |
| 目标 copy GPU 工作量总和 | 2.220059 ms |
| 首次 copy GPU 开始至最后一次结束 | 2.782109 ms |
| 最后 Adam GPU 完成至最后 copy 完成 | 2.784302 ms |
| 最后 Adam GPU 完成时间减去最后 copy CPU 结束时间 | **+3.256755 ms** |

最后一项为正，说明原 copy 的整个 CPU 提交循环在 Adam GPU 完成前就已经提交完了。**约 4 ms 的 CPU 提交不是这个 profile 中暴露的额外关键路径。** GPU 首尾跨度与工作量之差也只有约 **0.562 ms**。MA19 可以减少主机工作，但历史数据支持关注的直接机会是设备端 389 次分散 launch 的尾部及其中间隙；不能把包含必要数据转换的 2.78 ms 全部当作可删除预算。

原记录的全部 389 个参数共有 **849,207,296 个元素**。每步逻辑读取 3,396,829,184 字节 FP32，写入 1,698,414,592 字节 BF16，总计 5,095,243,776 字节。候选仍要搬运这些数据；这是从参数形状推导的逻辑读写量，不是 HBM 计数器。描述符不会消除必要的权重转换或数据量。

逐 rank、逐 copy、输入 SHA256 与统计限制见 [baseline-analysis.json](../../../../outputs/h100/phase6/ma19-validation-20261030/baseline-analysis.json)。trace 只有一个 step，直接观察到的是 `Adam→copy→清梯度→profile结束`；下一 step 对新权重的依赖来自原 worker 源码与同流顺序，不能冒充 trace 已测得跨 step 延迟。

## 3. 新机制：固定发布计划，原位写入全部模型权重

实现位于 [ma19_adapter.py](../../../../tools/h100/phase6/ma19_adapter.py) 和 [ma19_param_copy.cu](../../../../tools/h100/phase6/ma19_param_copy.cu)。初始化时为原 child optimizer 的参数列表建立：

1. 每个 tensor 的 FP32 源指针、BF16 目标指针及元素数。
2. 每个 CUDA block 对应的 tensor 和分片偏移。每分片 32768 个元素，当前固定模型共 **26146 个分片**。
3. 常驻 GPU 的只读描述符／分片映射及保活的源、目标 storage 引用。

候选只对 optimizer 实例绑定 `_copy_main_params_to_model_params` 的替代方法。原 `step_with_ready_grads()` 仍先调用原 Adam，再在原来的位置调用该方法。当前固定模型只有一个非空 child optimizer；发布 kernel 使用 256 threads/block，在当前计算流一次提交：

```text
原 Adam 完成
  → 一个 ma19_parameter_publish_kernel
      每个 block 读取固定分片描述符
      读取 FP32 master 元素 → 按原规则舍入 BF16 → 写入原 model storage
  → 原清梯度及下一步
```

描述符和分片表合计每 rank **427672 字节**。没有额外 payload 暂存区，也没有先 flatten 全部参数再 scatter。正常对齐参数采用 `float4` 读取、四次原 BF16 舍入和 `uint2` 写回；不对齐或不足四元素的尾部走标量分支。不同 block 写入互不相交的目标区间；旧参数对象、顺序、优化器 state、checkpoint 键和 DDP bucket 不需要改变。每次发布都发生在自己的原 child 更新边界，不能收集多个 child 的写回后再延迟到新位置。

### 3.1. 为什么不是重试 MA10

MA10 在反向执行期间逐参数拦截梯度、构建队列、管理 pending 生命周期及 flush；原本分散的梯度完成事件被一个新的 Python 协议连接起来。它的 hook 成本实际增加。

MA19 使用**本来就存在的完整 optimizer 更新边界**，所有源权重在同一流上已由 Adam 产生。参数列表和分片映射只在初始化建立，正式发布没有逐参数 Python 遍历、队列、flush、额外 collective、CPU 同步或辅助 stream。训练中的 1556 次梯度累加 kernel 和原 DDP hook 继续保留；不把 MA10 的失败路径改名后再执行。

### 3.2. 数值与生命周期约束

- 只做 FP32→BF16 元素转换，没有浮点归约或参数间算术。使用 CUDA 的 round-to-nearest-even 转换，必须与安装的 ATen `copy_` 在 GPU 上逐字节一致，包含正负零、ties、有限极值和 subnormal。转换依据见 [PyTorch 2.6 Copy.cu](https://github.com/pytorch/pytorch/blob/v2.6.0/aten/src/ATen/native/cuda/Copy.cu) 与 [CUDA BF16 转换 API](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-math-api/cuda_math_api/group__CUDA__MATH____BFLOAT16__MISC.html)。数学等价不能替代 GPU smoke。
- 新 CUDA translation unit 单独注册精度编译选项，防止继承全局 fast-math 的 FTZ 行为；原 MA11 softmax 和原 Flux 源码、编译参数不改。
- smoke 对每次发布的全部目标权重与原 `copy_` 结果作字节核对，随后原完整模型门禁检查全部参数的梯度、更新和最终指纹。审计不进入正式 timing／profile。
- 安装时验证固定 BF16 模型、FP32 master、连续布局、原 optimizer 方法源码、非重叠 storage 及唯一模型参数集合。热路径只检查当前设备／stream 和失败状态。
- 为避免重新引入 O(389) 的逐步主机检查，固定 descriptor 的有效性依赖被钉住的训练／optimizer 源码不替换参数 storage。持有 detached storage aliases 防止旧地址提前释放；生成最终状态时再次逐参数核对对象、shape、指针和绑定方法，有漂移即拒绝该窗口。**不支持安装后的 `set_data`、resize、reload checkpoint、offload 或 optimizer 重建；这不是可热替换参数的通用 API。**
- 当前范围是原 TP8、PP/CP=1、四 microbatch、32层、BF16、无重计算／offload／CUDA Graph 的固定实验。异常必须失败，不能静默退回 389 次 copy 后仍报告 MA19。

## 4. 收益预算与可证伪结论

以历史 450.662 ms 为量级，2.784 ms 仅约 **0.62%**，并且必要的约 5.10 GB 逻辑读写仍存在。这不是无 profiler 性能的严格上界，但足以说明：**现有证据不支持 MA19 单独达到 2% 的预期**。不能把它包装成 450→440 ms 的方案。

该机制可能节省设备调度间隙、改善小 tensor 的发布开销，也可能因统一 kernel 的访存、索引或大分片调度而退化。固定描述符的 host 成本下降若仍被 Adam 隐藏，不应被计为整步收益。主结论必须来自完整 optimizer step，而非发布 microbenchmark。

| 报告字段 | 判据 |
| --- | --- |
| `increment_over_MA11_validated` | 每个请求的独立 trial 配对收益点估计及 95% CI 下界均 >0，并通过正确性与实际路径检查 |
| `target_point_observed` | 单独报告是否观察到 ≥2% 的点估计 |
| `target_validated` | 沿用现有框架的较高门槛：各 trial 点估计及 CI 下界均 ≥2%，且独立 profile 通过 |

2% 字段用于与既有实验协议一致地报告，**不是本方案根据历史路径承诺的收益**。区间跨零或整步退化时应记为“未验证正增量／失败”，不能因为 389→1 就宣布成功。默认一个 trial 只有探索性证据；不能通过只保留最快窗口或挑最好的一半来提高收益。
