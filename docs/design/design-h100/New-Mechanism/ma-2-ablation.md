## 1. 组合的实际含义

MA2-R 已在上一批两次比较中得到约 3.7% 的 R/A 整步收益，但这主要是固定配置提交与输出路径的联合改动，不能将其全部归给打包 decoder。C 本来就有实例配置与独立输出管理，因此 **不能把“C 的收益＋R 的收益”相加，也不能通过再次去 clone 获得同一份收益**。

本次 CR 保留 C 的生产、选择性量化和生命周期，把 R 继承自 MA2 的连续四系数布局、打包载入/转换/写回、下一来源预取适配到 C 的混合数据路径。相对于 C，声明改动仅为接收 runtime 与两个新增 decoder 头文件；C 的 GEMM、encoder、mask、到达表、Python/C++ 包装、双工作区和屏障逻辑保持原样。构建器会核对这些文件的哈希。

C 的 mask 仍为 Attention **53/3584**、MLP **50/3584** 个远端贡献被量化，合计 **103/7168（约 1.437%）**；不是全远端量化，也不替换成 1/16 或其他实验的 mask。未选中贡献与本地贡献继续使用 BF16。

## 2. 接收端如何适配 C

对每个 H128 输出组，先按照 C 的物理 tile 与源 rank 查询冻结 mask，分两条路径：

1. **全部来源为 BF16：** 保留 C 已有的连续四元素读取和 packed BF16 归约算法，不强制经过 FP8 解码。
2. **至少一个远端来源为 FP8：** 每 lane 负责 `4*lane+j` 四个连续系数。选中的来源读取四个 FP8 字节及两个 scale，未选中的来源直接读取对应 BF16 槽；在处理当前来源时提前读取下一来源。

来源顺序仍为 `(rank+1)%8,…,rank`，本地来源最后加入。对 FP8 来源保留原 Hadamard 阶段顺序、显式舍入的缩放乘法、解码后 BF16 舍入，以及每次来源相加后的 BF16 舍入；不合并来源、不改为 FP32 跨来源求和。未选中的 FP8 槽不读取，避免将旧 packet 内容当作当前数据。

C 的双工作区继续交替使用。每次调用保留原发布屏障，下一次调用的发布屏障按原 C 协议保护此前槽位的复用；CR 不添加新的到达标记、辅助 stream 或轮询 kernel，也不改变这一同步协议。R/A 则继续保留它们原有的两道屏障，不能为了让四组屏障数相同而改写对照组。

接收端实现见 [ma2_c_decode.cuh](../../../../tools/h100/phase6/ma2_c_decode.cuh) 与 [ma2_ablation_sources.py](../../../../tools/h100/phase6/ma2_ablation_sources.py)。C 的纯 BF16 算法虽然保留，整个 kernel 的寄存器分配和调度仍可能变化；静态指令减少不能直接证明所有路径更快。由于 C 的量化覆盖很小，组合的增量也可能很小或为负。

## 3. 四组对照能回答什么

| 对比 | 可以回答的问题 | 归因限制 |
| --- | --- | --- |
| **CR/C** | 在相同 C 框架、mask、到达表与生命周期下，新增接收端优化是否产生净收益 | 本实验最主要的组合增量 |
| **CR/R** | 组合是否比单独 MA2-R 更快 | 同时包含选择性量化、排序、双工作区和实现差异 |
| **CR/A** | 组合相对原交替实现的整体收益 | 不能单独归给某一个机制 |
| R/A | 同场复测已测过的 MA2-R | 不使用上一批约 3.7% 替代新样本 |
| C/A | 同场复测 baseline C | 不能单独解释成到达排序或量化覆盖收益 |
| R/C | 单独两个方案谁更快 | 两者的量化范围、数值轨迹和生命周期不同 |

这四组是“组合与两种已有方案的对照”，不是所有因素均独立切换的完整因子设计。若 CR/C 为正但 CR/R 不为正，只能说接收端改动改善了 C，不能说组合优于两个单独方案。

## 4. 源码、计划和环境冻结

[ma2_ablation_build.py](../../../../tools/h100/phase6/ma2_ablation_build.py) 从仓库固定 candidate 源码恢复 C，并逐文件匹配 `base-baseline.md` 所用 `baseline-taco-cuda-3x-50steps-20261021-162929-989672/compare1` 中登记的 C manifest。**C 的 351 个源码文件与该记录全部一致；A 的 351 个文件与原 A 一致，R 的 352 个文件等于原 MA2-R 变换。** CR 只相对 C 改动 `taco_runtime.cu`，并增加 `ma2_decode.cuh`、`ma2_c_decode.cuh`，共 353 个登记文件。

原角色计划、到达表和 mask 由该 baseline 的 `scripts/selection-plan.json` 冻结，构建器固定其文件摘要，不重做校准，也不以相同预算重新生成另一张 mask。默认重新编译四份隔离构建，不要求旧 C 动态库仍在；但仓库内固定 candidate 源码及上述 baseline 的来源记录必须完整，缺失或哈希不符会停止。

同场四组统一使用 `NCCL_NVLS_ENABLE=0`、`CUDA_DEVICE_MAX_CONNECTIONS=1`，其余通信环境捕获后核验。重新编译和统一环境意味着历史批次均值只能作背景，不与当前窗口混算，也不直接相减推导收益。

## 5. 正确性按两对检查

**只在等价量化范围内要求逐位一致：CR/C 一对、R/A 一对。** C 与 A 的历史训练轨迹原本不同，不能要求四组输出或 loss 全部相同，也不能因此放宽 CR/C 的一致性门槛。

- 四组输入、权重、模型初始化、RNG/token、软件与硬件身份一致；实际 mapping 分别符合各自冻结计划，CR/C 的 mapping 相同，R/A 的 mapping 相同。
- 算子覆盖零值、小值、离群值、随机输入、两 seed、多轮工作区复用以及 rank0/rank7 延迟；CR/C 使用原 selective mask 的独立 codec 参考，R/A 使用全远端参考。
- 保留原相对 BF16 5%、相对独立 codec 1% 的误差门槛，同时要求等价对内输出逐位一致；不根据新结果放宽阈值。
- 连续保留至少六次输出，检查独立存储与后续调用不覆盖；交错调用不同 K 的实例，检查工作区和配置隔离。
- 完整模型检查全部 64 个投影、有限 loss/gradient、零 skip/fallback、真实调用数；CR/C、R/A 对内逐 rank 的 loss/gradient 轨迹一致。各组正式 50 步平均 loss、末步 loss 与末步 grad norm 单列到报告。
- Profile 必须显示每臂实际 decoder。CR/C 每调用一道原发布屏障且零输出 clone；R 为两道屏障、零 clone；A 为两道屏障、一次 clone。CPU annotation 与 GPU 镜像 annotation 分开解析，避免重现旧启动报告问题。

报告字段使用 `bitwise_equal_within_pairs`、`identical_trajectories_within_pairs`，并保存 `equivalence_pairs=[["CR","C"],["R","A"]]`，不把局部等价表述为四组数值相同。

## 6. 两轮完整训练及判定

模型沿用 GPT6.7B：32 层、H4096/FFN16384、32 heads、S2048、TP8，BF16，micro batch1/global batch4，seed1234/token_seed4321，每 optimizer step 8192 token。每窗口独立初始化，10 步预热＋50 步正式；每次比较先做四个循环移位块，后四块反转块顺序与块内顺序，四组在每个位置出现次数相等。

| 项目 | 每次比较 | compare1＋compare2 |
| --- | ---: | ---: |
| 完整四组块 | 8 | 16 |
| 正式窗口 | 32 | **64** |
| 正式 rank 记录 | 256 | 512 |
| 正式 optimizer step | 1600 | **3200** |
| 正式窗口预热步 | 320 | 640 |

两次比较使用同一冻结配置、不同 run ID 与新进程；不是更换种子或数据的实验。算子阶段另有 32 个计时窗口、64 份 trace；完整模型共用预检，另采集 32 份完整 step trace，均不混入正式训练计时。

窗口指标为八 rank 最大墙钟除以 50。收益为 `100×[1−exp(mean(log(T候选/T参照)))]`；以完整四组块配对 bootstrap 10000 次，seed20261021。两次分别报告六项比较、前后半程、全量窗口及负收益，不把 rank 或窗口内 step 当独立样本，不删除慢窗口。

**组合通过条件：两次各自的 CR/C 与 CR/R 点估计、95% CI 下界均大于零，且正确性与执行路径检查通过。** CR/C 点估计是否达到 1%、其区间下界是否达到 1% 另列为更强诊断；本次“进一步优化”的主判定不把 1% 当作必需门槛。所有比较仍完整保留，即使算子性能为负也继续完整训练；正确性或执行证据失败则停止并保存现场。

## 10. CR2：固定形状的原生提交缓存（2026-10-23）

以下保留 CR2 的设计、实现和预注册判定；八卡批次已运行完成，最新结果见第 11 节。

### 10.1. 为什么 C、R 单独有效，组合没有继续变快

这次进一步解析了原批次的全部 **32 份训练 trace**，保留逐 rank 的 launch 关联、排队时间、后继操作提交时刻和类别耗时。重现脚本和统计口径见[诊断说明](../../../../outputs/h100/phase6/cr-profile-diagnosis-20261023/README.md)、[分析脚本](../../../../outputs/h100/phase6/cr-profile-diagnosis-20261023/analyze.py)、[逐 rank 结果](../../../../outputs/h100/phase6/cr-profile-diagnosis-20261023/analysis.json)。

**第一，已有收益重叠。** R 相对 A 改善了固定配置提交与输出管理，而 C 已有实例配置和独立输出。组合没有再次去掉同一份开销；CR 相对 C 新增的主要是 decoder。C 与 R 的整体差异也包含量化范围、生产排序及同步，不能把两个整体实现的加速百分比当成可相加的独立项。

**第二，decoder 的可见时间量级较小。** 每个 rank 的一整步 decoder 时长求和后，再取八 rank 中位数：C 为 **5.684 ms**、CR 为 **2.812 ms**、R 为 **3.736 ms**。C→CR 的差值约 **2.872 ms**，仅为正式约 516 ms 步时的 **0.56%**。即使继续缩短 CR decoder，当前 profile 中剩余总量也只有约 2.8 ms。因此下一步需要考察 decoder 之外的路径。这里是条件预算，不是正式收益预测或严格上界；rank 依赖和系统效应不能用这些总和完整描述。

**第三，局部节省可能被 rank 间提交差异和等待吸收。** CR 的 rank1，Attention/MLP GEMM 的 GPU 开始与 CPU launch 返回相隔中位数仅 **0.89/0.97 μs**；decoder 后继操作在 decoder 结束前提交完成的比例只有 **32.0%/37.5%**。rank0 的 GEMM 却已经排队约 **15.6/15.9 ms**。八 rank 中位数会掩盖少数供给较慢的 rank。这个现象支持“减少某些 rank 的主机提交开销可能降低整组等待”的假设，但尚未证明正式计时由 CPU 提交限制。

**第四，profile 本身不能替代正式计时。** 四组 profile 的 GPU 时间跨度约 **841–869 ms**，明显长于正式约 515–535 ms，且落后的 rank 会变化。因而不能简单把 CPU 区间当独占开销，或将通信等待和 decoder 节省相加。要达到 1%，需在正式整步上节省约 **5.16 ms**；若平均分摊到每步 256 次目标投影，约为 **20.2 μs/次**。这也是 CR2 必须接受完整训练对照、不能只看短算子的原因。

### 10.2. CR2 的实现

代码见 [ma2_cr2_sources.py](../../../../tools/h100/phase6/ma2_cr2_sources.py)。旧 CR 每次调用在 GEMM 入口查找 metadata/hparams/operator，进入接收归约时又查找一遍；随后为固定布局构造 `slice → view → select`，才分配输出并调用 decoder。CR2 针对这些重复操作建立固定形状路径：

1. **每个工作区的原生实例只建立一次缓存。** 首次调用按原规则选取相同的 GEMM 实现与参数，缓存 operator、固定参数及工作区。两个槽分别持有缓存，Attention/MLP 的 K=512/2048 不共享实例状态。
2. **每次更新动态指针并重新初始化 CUTLASS。** input、weight 的地址可随调用变化，权重内容也可被 optimizer 更新；缓存不保存可复用的旧输出或旧 launch 参数。原有 CUTLASS 初始化、必要的 workspace 清零和实际 GEMM 仍逐次执行。
3. **直接执行固定布局的归约输出路径。** 在原发布屏障之后，每次分配新的 `[256,4096]` BF16 输出，以原 `output_buffer` 首地址调用同一个 CR decoder，省去第二次 registry 查找与原生中间视图。在固定 nnodes=1、node_idx=0 的布局中，该地址与旧视图首地址相同。
4. **保留拒绝错误用法的检查。** 核对 rank/world、device/stream、BF16、精确 M/N/K、固定 option，拒绝 graph capture 和未经显式 autograd adapter 的用法；任意 forward 异常后整对工作区禁止重试，TLS 配置在退出时恢复。

CR2 相对 CR 只改六个登记文件：runtime 的主机绑定接口、runtime header、C++ wrapper 及其 header、pybind 绑定、Python frontend。**GEMM/encoder/decoder 算法、Hadamard/BF16 舍入、到达表、冻结 mask、双工作区、每调用一道发布屏障均沿用 CR**。公共训练 adapter 为输入/输出形状转换所用的 reshape/view 也保留；移除的是原生接收路径内部的中间视图。

新增 `cr2_submission_state()` 暴露每个槽的初始化次数、成功调用次数、绑定 K、packet 地址和失败状态，读取在正式计时范围之外。报告器要求每槽只初始化一次、两槽调用数平衡、总调用数与实际预热/正式步完全对应，并验证 packet 地址与原工作区记录一致。Profile 同时核对原 GEMM→发布屏障→decoder 路径，拒绝 CR2 再走原生 slice/view；允许公共 adapter 的嵌套 reshape/view，避免把合法形状转换误判为失败。

### 10.3. 新四组、两轮及 1% 判定

| 组 | 本轮用途 | 与原实现的关系 |
| --- | --- | --- |
| **CR2** | 新的固定形状提交缓存与直接归约路径 | 在原 CR 上修改主机提交与输出视图路径 |
| **CR** | 隔离 CR2 本次改动的净增量 | 保留本批已测原 CR，逐文件验证 |
| **C** | 验证是否比原 baseline C 快 1% | 原 C，逐文件验证 |
| **R** | 验证是否比 MA2-R 快 1% | 原 MA2-R，逐文件验证 |

构建器 [ma2_cr2_build.py](../../../../tools/h100/phase6/ma2_cr2_build.py) 从旧四组生成器重建控制组，并检查源码摘要。原 CR/C/R/A 工具、协议和回传数据保留；本轮使用独立 `h100-ma2-cr2-v1` 协议。本轮用原 CR 替代 A 作为第四组，以直接测量这次干预，不复用历史 A 的耗时计算新收益。

完整训练保持原 GPT6.7B、TP8、seed、输入、通信环境、每窗口 10 步预热＋50 步正式；**两次比较各 8 个平衡四组块，共 64 窗口、512 份正式 rank 记录、3200 正式步**。另有 32 个算子计时窗口、64 份算子 trace 和 32 份完整训练 trace。所有正、负和不确定结果均保留。

数值检查要求 **CR2/CR/C** 的算子输出逐位一致、逐 rank 完整 loss/gradient 轨迹一致；R 仍按自身全远端 codec 参考、模型数值与执行覆盖检查，不要求它与 selective 三组数值相同。

主判定遵循“比 C **或** R 提升 1%”：

- `one_percent_over_C_validated`：两次各自 CR2/C 点估计 ≥1%，且 95% CI 下界 >0。
- `one_percent_over_R_validated`：两次各自 CR2/R 满足同样条件。
- `target_validated`：上述任一项成立。**必须是同一个对照在两轮都通过**；不能用 compare1 赢 C、compare2 赢 R 拼成通过。
- `beats_both_one_percent_validated`：同时比 C、R 都通过 1%，作为更强结果；CI 下界本身 ≥1% 另列严格诊断。主判定“点估计达到 1% 且确认有正收益”不等于“以 95% 区间确认至少 1%”。
- `increment_over_CR_validated`：两次 CR2/CR 的点估计和区间下界均为正，检验本次改动是否确有增量。

六项比较为 CR2/C、CR2/R、CR2/CR、CR/C、CR/R、R/C，均按完整块配对 bootstrap；两轮分别报告均值、95% CI、前后半程与完整样本。

### 11.4. 实际缓存与 profile：提交工作减少，GPU 算法时间接近

所有 CR2 正式记录共 **128 份 rank JSON、8192 个模块记录、16384 个槽状态记录**。每槽 `initializations=1`、`successful_calls=120`、`failed=false`，绑定 K 为 512 或 2048；两槽合计每模块 **240 次**，等于 `(10 预热 + 50 正式) × 4 microbatch`。报告器逐项核对缓存计数、slot、K 和 packet 地址，确认真实执行了新路径，并非只加载了带新名称的库。

训练 profile 每 rank、每角色包含 128 次投影。CR2 的 `output_slice_view_count=0`，原 CR/C/R 均为 256；公共 autograd adapter 的 `adapter_view_count` 各组仍为 256，说明只移除了原生中间视图。CR2/CR/C 每角色 128 道发布屏障，R 为 256 道屏障；所有组均零输出 clone。
