# MA20：编码成本前置的到达顺序与选择性量化联合计划

更新：2026-10-30。以完整 **MA11** 为基线，重新决定“哪些远端贡献量化，以及它们在 producer 中何时提交”。旧 BF16 正分候选池不再限制新选择；量化数和重排数一起变化，最终配置由当前机器上完整算子路径的独立校准确认。**本页包含实现与启动入口；尚无 MA20 八卡性能结果，不能声称已经低于 450 ms。**

## 1. 先澄清“预算提高，最终 tile 数固定”

原选择器实际执行的是：

```text
P_s = 两遍 BF16 采样中都 near-critical，且 score > 0 的远端 tile 集合
q_s = min(floor(448 × budget), |P_s|)
```

源码依据是 [priority()](../../../../tools/a800/arrival/plan.py)、[select()](../../../../tools/a800/phase5/plan.py) 和 [ablation5_plan.py](../../../../tools/h100/phase6/ablation5_plan.py)。预算只是 `P_s` 内的截断上限，无法让 `P_s` 外的 tile 获得资格。到达表又在量化预算选择之前生成；消融5明确固定了这张表。

旧仓库已有消融5 GPU 数据，虽然[消融5文档](../消融实验/消融实验5-选择性量化.md)仍写“尚无 GPU 计时结果”。本次读取旧批次的 [budget-plan.json](../../../../../TempName/logs/h100/phase6/ablation5-then4-60steps-20261018-230611-029519/ablation5/budget-plan.json)、[compare1](../../../../../TempName/logs/h100/phase6/ablation5-then4-60steps-20261018-230611-029519/ablation5/compare1/report.json)、[compare2](../../../../../TempName/logs/h100/phase6/ablation5-then4-60steps-20261018-230611-029519/ablation5/compare2/report.json)，核验全部 800 份正式 rank 记录、51,200 项模块选择记录、102,400 项双槽 mask 登记及报告登记的文件哈希。

| 原预算 | 每来源预算上限 | Attention 总贡献数 | MLP 总贡献数 |
| --- | ---: | ---: | ---: |
| 1/64 | 7 | 53 | 50 |
| 1/32 | 14 | 89 | 98 |
| 1/16 | 28 | 140 | 151 |
| 1/8 | 56 | 224 | 235 |
| 1/4 | 112 | 392 | 364 |

这里的单位是 **`[source, physical tile]`**；每角色共 3584 个远端贡献。整体登记集合并非完全不变，真正固定的是每来源的候选资格集合：

```text
Attention 正分候选数：[186, 21, 151, 8, 4, 16, 160, 7]
MLP       正分候选数：[235, 19,  73,17, 1, 17, 115,13]
```

因此 source 4 在所有预算下始终是 Attention 4 个、MLP 1 个；多处来源从 1/16 起已经饱和。这确实是旧选择机制的限制。对所有预算，运行对象登记的 mask 哈希均匹配各自计划，没有发现统一退回 Q64 的证据。但旧哈希来自 CPU mask，`wire_bytes` 也是由 CPU mask 推算的逻辑字节数，GPU 侧只登记指针，**不能据此声称已核验实际编码指令的执行次数**。

两次消融5的完整步时如下，所有更大预算相对 Q64 的主要配对 95% 区间均跨零：

| 原 C 批次 | Q64 | Q32 | Q16 | Q8 | Q4 |
| --- | ---: | ---: | ---: | ---: | ---: |
| compare1，ms/step | 515.413 | 514.757 | 515.586 | 516.380 | 515.879 |
| compare2，ms/step | 515.812 | 515.658 | 516.560 | 516.928 | 516.581 |

可支持的结论是“扩张旧正分集合内的预算没有验证收益”。这不能证明选择性量化整体无用，也不能将原 C 的约 515 ms 结果直接当作 MA11 的结论。

## 2. MA11 的真实依赖决定优化目标

[MA11 原始整步报告](../../../../../TempName/logs/h100/phase6/ma11-v1-causal-softmax-1x-50steps-20261027-121342-060643/fullstep/report.json)为同期 MA89 **459.638 → MA11 450.662 ms**，八块配对收益 **+1.952%［1.711%, 2.271%］**。本次须重新计时同期 MA11，不将历史 450.662 ms 作为实验分母；[baseline](baseline.md)是跨批次汇总。

MA11 的 row 投影仍沿用 [CR2 native submission](../../../../tools/h100/phase6/ma2_cr2_sources.py) 与 [MA4-F 消费融合](../../../../tools/h100/phase6/ma4_f_sources.py)：

```text
producer GEMM + 远端写出/选择性编码
    → 全 rank publication barrier
    → 原 mixed BF16/FP8 decoder + bias + residual
    → 下游 LayerNorm
```

decoder 不能因为某几个 tile 早到就先开始。旧评分使用两遍 BF16 观察的 `median(max(arrivals))`，既包含原顺序造成的晚到，也没有扣除 H128/E4M3 编码和解码代价。MA11 所沿用的原计划在 heldout pass 上，near-critical 命中比例仅 Attention 33.96%、MLP 22%；这不是当前 mixed-codec 路径的净收益预测器。

MA20 的工作假设是：选中贡献的编码 epilogue 更重，把这种工作留在 producer 的后部可能拖长全体可消费的时间；前移这些工作有机会缩短 producer 完成到下游消费的关键路径。量化数同时影响网络写出、编码与解码，须以完整 `forward_consumer()` 的实测净结果选择。

**逻辑 slot 不等于实际 CTA 波次。** 当前 CUTLASS StreamK 有自己的任务映射与 occupancy；实现没有用 `512 / 132` 推算“最后一波”，也没有从不同 GPU 的时钟相减得到 slack。前置能否兑现，必须由实际映射、独立 profile 和无 profiler 的整步时间确认。

## 3. 新机制：全远端资格、必要交换、净收益选择

[ma20_plan.py](../../../../tools/h100/phase6/ma20_plan.py)先生成一组预先登记的联合计划。每个来源的本地 64 个贡献保持 BF16，全部 **448 个远端贡献均有资格**，不读取旧 `score > 0` 条件。

对一个候选量化数 `q`：

1. 在来源自己的 MA11 顺序中，分别取七个远端目的地的末端 tile；按目的地循环取一个，直到取满 `q`。当前档位均为 7 的倍数，每目的地选择 `q/7` 个。各来源按自己的顺序选取，没有强制把多个来源集中在同一接收 tile 上。
2. 在原 destination/window 约束内，将选中的尾部位置与前部未选中位置一一交换。选中 tile 优先提交，中间无需移动的 BF16 tile 保持原位。这里减少的是无关重排，不改变 GEMM 或 codec 算术。
3. 由最终 mask 推导最终映射，并生成设备表和 host 检查表。两者是同一个联合计划，不能只改 JSON 或只改变 mask 后继续使用旧到达表。
4. 上机测量完整路径，选择和确认一个配置；正式训练只使用冻结结果。计时期间没有 Python tile 决策、采样、逐步重排或 mask 更新。

| 配置 | 每来源量化贡献数 | 每角色总量化贡献数 | 每来源相对 MA11 改变的逻辑位置数 |
| --- | ---: | ---: | ---: |
| MA11 | Attention 原 `[7,7,7,7,4,7,7,7]`；MLP 原 `[7,7,7,7,1,7,7,7]` | 53 / 50 | 0 |
| Q0 | 0 | 0 | 0 |
| Q7 | 7 | 56 | 14 |
| Q14 | 14 | 112 | 28 |
| Q28 | 28 | 224 | 56 |
| Q56 | 56 | 448 | 112 |
| Q112 | 112 | 896 | 224 |

上述重排数量由当前 MA11 的 destination/window=64 计划实际推导，属于 CPU 计划统计。Q7→Q112 的 mask 嵌套但与原消融5的 mask 不同；原来 source 4 的 4/1 个候选上限不会限制这些新计划。所有配置保留同样的目的地序列、合法窗口和完整物理 tile 双射。

旧 `selection-plan.json` 的 parent/config 继续记录历史 1/64 校准身份；新数量以 `ma20-plan.json/configurations` 的实际 mask、`selected_per_source` 和设备回读为准。运行时不再用这个历史 fraction 重选或截断新 mask。

**这六档是受控干预，不是六个必须用满的部署预算。** 部署量由新测量选择，允许 Q0 或没有候选。若 Q0 胜出，只能说明这组负载下关闭编码更好，不能声称验证了“非零量化前置”的收益。冻结后每步选择数恒定是本版本的设计；本版本解决固定旧候选资格与顺序脱节，不宣称按每层、每步在线自适应，也没有覆盖所有可能的 mask 或每来源不等额分配。

原逻辑字节公式仍是 `14,680,064 − 15,360 × q_s` 字节/来源/投影。这是载荷估算，不能当作 NVLink 链路计数或节省时间。

## 4. 与既有尝试的边界

[ma20_build.py](../../../../tools/h100/phase6/ma20_build.py)复制 MA11 的完整 candidate 源码作为对照，各候选的 native 源码差异仅允许两个映射文件：`threadblock_swizzle.hpp` 和 `phase6_host.hpp`。量化 mask 是各实例的冻结运行参数。构建校验重新推导表内容，拒绝改源码后只重算哈希冒充新计划。

两臂均保持 MA8-v2 激活复用、MA9 零统计、MA11 causal softmax、原双工作区、BF16 GEMM/STE backward、原 publication barrier 和原 decoder/bias/residual 消费链。已有代码中的 kernel 几何和编译配置也保持相同。

| 既有方向 | MA20 的区别 |
| --- | --- |
| 消融5扩大旧正分 top-k | 解除旧候选资格限制，mask 与提交顺序共同生成，以当前完整路径校准 |
| MA6 接收布局/packed mask | 不修改 decoder 布局或分支实现 |
| MA7、MA10 主机队列/提交合批 | 热路径不增加队列、hook、逐次 Python 调度 |
| MA12、MA14 发布/屏障协议 | 不增加 ready/done/epoch，不改变全 rank barrier |
| MA13 及 MA15–19 其他计算/通信优化 | 不叠加未验证机制，不改变 softmax、column、optimizer 参数发布路径 |
| arrival_op3 分片发布、arrival_op4 reduction closure | 不让 decoder 提前运行，不构造跨来源 FP8 fan-in 闭合组 |

这仍是需要验证的调度假设。新资格范围能让预算真正改变 mask，并不自动意味着更多量化会更快。

## 5. 对比协议与拒绝条件

[ma20_probe.py](../../../../tools/h100/phase6/ma20_probe.py)在同一机器上比较七个配置的两个实际 shape。先做每配置独立 codec 数值预检，再运行七臂 Latin 顺序的 7 个训练块，随后用反转顺序的 7 个独立确认块。每臂在每一阶段的七个位置各出现一次。

每个校准块的目标值为 `Attention 的八 rank 最大完整 forward 时间 + MLP 的八 rank 最大完整 forward 时间`。两角色在模型内各调用 128 次/step，因此此值可用于等权筛选，但不能乘以 128 宣称整步节省。只使用训练块选择一次候选；确认块只接受或拒绝，不换成确认集表现更好的第二名。确认通过才进入正式训练；否则保留所有负结果，批次记为 `no_candidate`，不伪造完整训练收益。

正式比较由 [ma20_experiment.py](../../../../tools/h100/phase6/ma20_experiment.py) 和 [ma20_worker.py](../../../../tools/h100/phase6/ma20_worker.py)执行：

- 原 GPT6.7B、32 层、H4096/FFN16384、TP8、S2048、micro batch1/global batch4，种子与 MA11 相同。
- 同期 MA11 与冻结候选，默认 1 个 trial；每 trial 8 个平衡配对块、16 个窗口，每窗口 10 步预热＋50 步正式，合计 800 个正式 optimizer step、128 份 rank 记录。
- 每窗口步时为八 rank 最大墙钟除以 50。全部窗口保留，按完整配对块对数耗时比做 10,000 次 bootstrap；点估计及 95% 区间下界均大于零，才验证性能增量。
- smoke、profile、正式计时分开。完整参数覆盖、原 MA8/MA9/MA11 安装、调用数量和实际消费链沿用原验证。新增设备 mask 回读放在计时之外。

**量化 mask 改变后，不要求两臂训练轨迹逐位相等。** 各臂前向须满足相对 BF16 L2≤5%、相对独立 codec 参考 L2≤1%，完整模型的 loss/grad norm 必须有限；报告另列两臂 loss/grad norm 漂移与最终参数指纹。该门槛只支持 codec 实现和短程训练检查，不支持精度等价或长期收敛结论；`accuracy_equivalence_validated` 保持 false。

新增证据包括每个目标模块、每个双槽的真实 CUDA `selected` 张量回读哈希与每来源计数，并同冻结 mask 比对；另运行各编译臂的 `check_mapping` 核对两角色全部 rank/slot。设备 mask 回读证明 native 分支使用的选择缓冲内容，不等于硬件链路计数或编码动态指令计数。算子 smoke、训练校准块、确认块和正式模型比较均核验同一主机、GPU UUID 顺序与软件版本。

`fullstep/profile-summary.json` 的 `profiles[arm/rank][role].path_distribution_us` 记录 128 条实际 launch 关联路径上的 `producer_us`、`barrier_us`、`producer_start_to_layernorm_end_us`，各自给出 median/p95/max/sum。结合原 decoder 和 LayerNorm 消费链指标，判断编码前置是否缩短目标路径；不跨 rank 相减 GPU 时间戳，也不将 profile 工作量之和当作正式整步节省。

## 6. 一键启动

在 **TempName-New 仓库根目录、配置好的八卡 H100 环境**执行：

```bash
# 预览：不创建实验目录、不查询 GPU、不构建或训练
bash tools/h100/phase6/run_ma20.sh

# 构建七臂 → 数值/映射预检 → 独立校准确认 → MA11/MA20 完整训练比较
bash tools/h100/phase6/run_ma20.sh --execute

# 保持前台，便于检查日志
bash tools/h100/phase6/run_ma20.sh --foreground --execute

# 两个独立完整训练 trial，共1600个正式 optimizer step
bash tools/h100/phase6/run_ma20.sh --trials 2 --execute
```

启动入口是 [run_ma20.sh](../../../../tools/h100/phase6/run_ma20.sh) 与 [detach_ma20.py](../../../../tools/h100/phase6/detach_ma20.py)。沿用 MA11 的运行环境约定；解释器可用 `MA20_PYTHON` 指定，运行 CUDA 与编译 CUDA 分别指定。候选改变了编译时映射，第一次必须构建新 bank，不能只把原 MA11 动态库改名。

```bash
MA20_PYTHON=/path/to/flux-h100/bin/python \
  bash tools/h100/phase6/run_ma20.sh \
  --megatron /path/to/Megatron-LM \
  --cuda-home /usr/local/cuda-12.4 \
  --build-cuda-home /usr/local/cuda-12.8 \
  --out /path/to/new-ma20-batch --execute
```

自动新建独立批次，拒绝覆盖旧实验。后台启动仅表示监督进程建立；查看 `batch-state.json` 和 `handoff/container-supervisor.log`，以校准选择结果及最终 `fullstep/report.json` 判定完成和收益。没有通过校准的候选时，`no_candidate` 是合法负结果，不会把 MA11 自身改名为 MA20 继续报成功。

`no_candidate` 具体对应 `status=completed, stage=no_candidate, fullstep_executed=false`；构建、数值或身份检查失败则记为 `failed`，保留错误记录。可用 `--ma20-build /path/to/verified-bank` 复用完整 bank 后重新校准；`--ma11-build` 只复用原 MA11 源码参考，仍须编译新的候选表。

已实现计划生成、真实映射构建、设备 mask 审计、算子校准和完整训练对比入口。CPU 测试覆盖候选资格、递增嵌套 mask、必要交换、窗口/双射约束、运行路由、篡改拒绝和原 MA11 训练循环保留；host mapping 检查实际调用 C++ 编译器，逐项比较两个 shape 的 4096 个来源/位置。
