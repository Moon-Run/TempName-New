# H100 改进路线：原融合路径上的交替顺序、到达优先与选择性量化

更新：2026-10-17。本文承接 [当前思路](idea.md)、[消融实验3](消融实验/base-phase6-ablation3.md) 和 [Attention/MLP实测](base-phase6-mlp-attention.md)。**当前 Phase7 直接改进原融合 GemmV2 的静态到达映射；代码入口为 [fused.py](../../../tools/h100/phase7/fused.py)。新的映射已经实现，实际 H100 性能收益仍待验证。** 实现与验证状态见 [base-phase7.md](base-phase7.md)。

首版保持交替目标顺序、融合编码、物理选择性量化 mask、IPC 传输、屏障和固定归约路径一致，先回答一个范围明确的问题：**利用真实 receiver 观测生成的新到达映射，能否优于原本的到达映射。** 后续再在新顺序上重采样、重新选择量化对象；分块就绪后消费属于之后的融合内核改造。

## 1. 当前收益有限的原因与首版边界

消融3中，增加到达置换的 B 相对 A，完整 step 耗时变化很小；已有正收益的置信区间跨零，不能确认稳定增益。双模块相对单模块的收益属于作用范围扩展，不能归因于到达优先。

原实现还有三项约束：

- 到达优先使用离线固定置换。重排发生在同一 destination 的合法槽位内，不根据本次执行的就绪情况动态调度。
- 顺序与量化对象来自基础 BF16 校准。改变顺序和编码以后，原先的拖尾标签可能不再对应实际瓶颈。
- 当前调用仍经过 `forward_gemm_impl → forward_barrier → forward_reduce_scatter_impl`。中间 tile 提前到达，只有改变最终生产或等待时间，才可能缩短整个算子；当前并没有“到一块就立即解码一块”的消费者。

因此，本版先控制改动范围。[fused_build.py](../../../tools/h100/phase7/fused_build.py) 从原实测融合候选派生三份构建，逐文件检查三种顺序之间只能改变：

| 文件 | 改动内容 |
| --- | --- |
| `src/gemm_rs/tile_scheduler/threadblock_swizzle.hpp` | CUDA 逻辑槽位到物理 tile 的查表映射 |
| `phase6_host.hpp` | 与 CUDA 表一致的主机映射，用于校验 |

GEMM 算法、epilogue 编码、codec runtime、IPC 工作区、双缓冲、全组屏障、解码归约及 Python 算子封装保持同一实现。每个角色的物理 mask 在三种顺序间完全相同；未选中的模型投影仍走原生 Megatron BF16。

这个约束使新旧顺序的比较可以归因于映射变化，也保留了限制：仅改变同一批 CTA 的顺序，不保证减少总工作量或最终完成时间。

## 2. 已实现：从真实 receiver 样本拟合静态映射

实现位于 [fused_plan.py](../../../tools/h100/phase7/fused_plan.py)。Attention 与 MLP 分别建表，完整形状为 `[2048,4096,4096]` 和 `[2048,4096,16384]`，TP8 本地 K 分别为512和2048。两者不能互换校准数据。

### 2.1 观测来源与时间语义

从父计划的 `inputs` 读取原始 `b0-interleaved-instrumented-rank*.json`，通过 [resolve_input](../../../tools/h100/phase6/ablation_plan.py) 按路径与 SHA256 定位文件，核对八个 receiver、运行身份、设备顺序和完整 shape。拟合使用原始观测，而不是把旧 `coords` 的槽位序号当成到达时间。

对 receiver d 的物理 tile t、来源 s、采样 pass p，使用：

```text
A[p,s,t] = (该来源八个 fragment 的最大 observed_ns − 同次调用的 receiver 起始 marker) / 1000
ε[p,t]   = 2 × max_poll_cycle_ns / 1000
```

`A` 的单位为微秒；保留合法的负相对偏移，不把它裁剪成零。绝对 GPU 时间戳不能跨设备或跨调用直接相减。不同 tile 来自不同采样调用，拼接这些观测并不构成一次真实调用的完整联合时间线。

pass0/1用于拟合；pass2只在方案确定后生成留出诊断，不能重新拟合斜率、选顺序或调门槛。若某个 destination 的64个 tile 中任意一个缺少训练 pass，该 destination 整体保留原 `legacy` 映射。

### 2.2 剥离槽位趋势，再形成稳定优先级

对每个 destination、source 和训练 pass，按基础交替映射中的逻辑位置拟合非负 Theil–Sen 中位斜率：

```text
b[p,s]   = max(0, 成对到达差 / 成对槽位差的中位数)
R[p,s,t] = A[p,s,t] − b[p,s] × base_slot[s,t]
Q[s,t]   = min(R[0,s,t], R[1,s,t]) − max(ε[0,t], ε[1,t])
```

最后一式等价于实现中的“残差均值 − 两 pass 差值绝对值的一半 − 最大轮询不确定度”。它降低只在一个 pass 中偏晚的贡献的优先级。**`Q`是静态排序启发式，不是统计置信下界，也不是已测得的可节省时间。**

在同一 destination 内生成两个候选：

1. **共享残差顺序**：按 `max_source Q[s,t]` 降序排列物理 tile，所有来源使用同一粗顺序。
2. **共享顺序加来源微调**：先采用上述共享顺序，再在每个固定的8 tile组内按本 source 的 `Q` 微调。8是预登记常数，不用pass2选择。

每个 source 仍把这些物理 tile 放回该 destination 原有的合法逻辑槽位。目标 rank 的交替节奏、每个目标的槽位数量及完整映射双射保持不变；微调不跨越共享的8 tile组。量化对象继续绑定 `[source, physical_tile]`，不随逻辑槽位移动。

### 2.3 用代理门槛筛选，不把代理结果写成加速

实现以基础到达观测和槽位趋势构造候选诊断：

```text
预测到达 = 基础观测 A + b × (候选槽位 − 基础槽位)
预测汇合 = max_source(预测到达)
```

每个候选与 `legacy` 使用同一代理模型比较。两个训练 pass 的预测汇合 p95 和最大值都不得变差，且至少一个 pass 的一项指标必须改善超过该 destination 训练轮询不确定度的中位数。若两个候选均通过，按两 pass 的 p95 之和、最大值之和及固定名称顺序选择；均不通过则保留 `legacy`。

代理模型假设槽位成本可近似线性、残差可在重排后迁移。这些假设尚未在新量化顺序上验证。真实 CTA 并行波次、缓存行为、编码成本和远端争用可能改变结果；门槛通过并不证明实际耗时改善，更不能把代理 p95 当成算子或 step 的 p95。

生成的计划明确保留 `not_recalibrated=true`、`measured_performance=false`。父计划具有真实 GPU 校准来源，只说明历史 BF16 输入真实，不表示新顺序已经完成 GPU 验证。`verify --refit` 可从冻结原始记录重建映射及诊断，检查其来源一致性。

## 3. 当前主实验：三种顺序 × 三种作用范围

[协议定义](../../../tools/h100/phase7/fused_protocol.py)固定九组，三种顺序分别为：

| 顺序 | 基础交替顺序 | 到达映射 | 量化 mask |
| --- | --- | --- | --- |
| `base` | 保留 | 不加到达置换 | 原选择性物理 mask |
| `legacy` | 保留 | 原 Phase6 到达映射 | 与base相同 |
| `improved` | 保留 | 新拟合映射；不满足条件的destination回退legacy | 与base相同 |

每种顺序分别作用于 MLP、Attention、Attention＋MLP，共九组。`base`只关闭到达置换；它仍然使用选择性 mask，因此不等同于消融3中使用全远端量化的 A 组。

**主比较是同作用范围的 `improved / legacy`。** `legacy / base`和`improved / base`用于辅助判断旧、新到达映射的作用。同顺序不同scope的比较单独报告，不能解释为调度增益。

每个scope复用相同的角色映射和mask，不分别调参。默认每轮9个完整块，每块九组各一次，共两轮；执行位置循环平衡，第二轮反转块与块内顺序。准备时可显式指定 `--rounds 1 --blocks 9`，只运行原第一轮的81个正式窗口，仍保留18个预检窗口和12项映射检查；默认两轮行为不变。轮数在准备时冻结，不能通过中断两轮实验或删记录改成单轮。计时、运行身份和完整性检查由 [fused_prepare.py](../../../tools/h100/phase7/fused_prepare.py)、[fused_run.py](../../../tools/h100/phase7/fused_run.py) 与 [fused_report.py](../../../tools/h100/phase7/fused_report.py)管理。

性能比较使用采样关闭的正式完整 step，按同场完整配对块统计，不把rank、微批或单步当作独立重复，也不以旧批次均值充当同期分母。当前九组默认固定选择性量化；量化预算和mask变化放入后续独立实验。

## 4. 验证顺序与当前可得出的结论

| 阶段 | 要确认的内容 | 不能据此声称的内容 |
| --- | --- | --- |
| 计划与源码检查 | 数据哈希、训练/留出隔离、回退规则、映射双射、目标槽位不变、mask一致、仅两份映射文件改变 | GPU正确性或性能收益 |
| 主机映射和CUDA对象编译 | 两种shape的host/device表及编译接口一致 | 完整动态库已链接、GPU路径已执行 |
| H100预检 | 实际V2融合路径、模块路由、mask和库身份、数值误差、有限梯度及零意外回退 | 正式性能改善或长期收敛 |
| 独立正式计时 | `improved / legacy`完整step配对收益及不确定性 | 仅凭代理诊断推断的收益 |
| 专项机制诊断 | GEMM/发布、屏障、解码及完整算子耗时如何变化 | 只凭部分tile提前就认定算子更快 |

诊断采样与正式计时分开。若只有代理指标改善，或局部到达更早而最终耗时没有稳定改善，应保留原映射。若门槛使新映射全部回退，也应如实报告，不为产生变化而放宽规则。

固定合成token上的短程训练loss继续只用于该工作负载的数值记录，不能代替真实验证集、多随机种子或长期训练质量。原版保存与复现位置见 [Phase6原版记录](base-phase6-mlp-attention.md#phase7-开发前的原版保存与复现2026-10-17)；本地快照须另行携带，不假设克隆仓库自动包含。

## 5. 下一步：在新顺序上真实重采样，再重新选择mask

完成固定mask的顺序比较后，下一阶段才解决校准与实际执行不匹配的问题：

1. **固定新顺序，重采集真实到达。** 校准必须登记实际shape、CUDA映射、内核/codec实现、物理mask、设备和输入身份。当前历史BF16采样未覆盖新顺序及量化分支，不能仅换计划标签称为重校准。
2. **分别评估计算、发布与等待。** 所有时间差使用同设备的合法时钟域。需要低干扰观测和重复测量；不把不同tile的稀疏调用拼成单次完整时间线，也不预设编码、传输和解码可以简单相加。
3. **按完整算子净收益选择mask。** 到达标签先筛候选，再测固定顺序下的完整候选mask，包含编码、传输、解码和资源竞争的全部影响。并列拖尾来源可以作为组合一起评估，不能累加未经联合测量的单项收益。
4. **量化预算是上限。** Attention和MLP分别设置预算及数值约束；没有正净收益时允许少选或不选。报告实际选中数量、逻辑字节变化及实测完整耗时。
5. **加入匹配随机mask。** 保持每来源实际数量、远端物理约束和预登记随机种子，用于判断收益来自选择位置还是压缩数量。
6. **冻结后独立评价。** 调序、选mask、选预算使用的数据均属于拟合或调参集；最终性能与真实训练质量使用未参与选择的数据。每轮只改变一个因素，不覆盖历史计划或实测记录。

当前原mask分别选择Attention 45/3584、MLP 39/3584个远端贡献。完整H128组从256字节BF16变为128字节FP8加两个FP32 scale，共136字节；相应逻辑远端字节减少仅约0.589%与0.510%。这不是链路实测流量或加速比，因此位置选择必须经过实际等待与净收益验证。

## 6. 后续融合结构项目：完整就绪的分块提前消费

若实测确认屏障后的解码归约或生产等待仍有足够优化空间，再在同一融合路径内加入分块发布与消费。它不是本版静态映射更新已经实现的功能。

后续协议必须覆盖完整fragment，而不是把一个Stream-K回调完成视为整个tile可读；量化分支只有payload和两个scale均发布后才能标记就绪。消费者保持当前来源归约次序与舍入规则，并保证每个分块只被处理一次。

| 必需机制 | 要保证的条件 |
| --- | --- |
| 完整贡献ready及epoch | 不读取未完成的数据，不把旧调用状态当成新调用 |
| 消费完成确认或等效依赖 | 所有读取完成前不能复用IPC槽位 |
| 生产/消费资源约束 | 等待中的消费者不能阻止生产者继续运行 |
| 输出完成依赖 | 下游只能在本算子所有输出写完之后使用结果 |

当前双缓冲的安全性依赖现有屏障，不能直接删除它。新协议建立后，才比较相同融合计算、codec、物理mask和归约规则下的“全量就绪再消费”与“分块就绪即消费”；同时保留无新增标记的原版，单独计入发布、轮询、确认和资源调整成本。

只有确认同一路径的最终算子/step收益、正确性、前进性和长期复用安全，才继续研究乱序就绪队列、角色或层组计划以及低频更新。当前交付保持在原融合路径内，所有性能结论以新的H100实测为准。
