# H100 GPU监控与自动测试队列

更新：2026-10-12。本文维护GPU空闲检查、运行中监控策略及队列切换说明；完整测试流程和数据交付要求见 [instruction-h100.md](instruction-h100.md)。

## 自动队列的GPU检查时机

2026-10-12按用户要求，当前 `gpt67-tp8-fusedv2-20261012-205424-queue` 队列采用**每套测试开始前检查，运行后停止GPU状态查询**的方式：

1. 第一套开始前由 `queue.py` 检查相同八卡UUID/顺序、计算进程、显存和利用率。忙时每600秒检查；空闲后间隔10秒确认，连续3次满足条件才启动，任一次忙则计数归零。
2. `run-one.sh` 先完成启动前环境/设备及来源记录，再调用维护入口 [execute_queued.py](../../../tools/h100/phase6/execute_queued.py) 执行prepare、smoke/profile预检、72窗口计时和报告。执行器不再每30秒调用 `nvidia-smi`，也不在失败路径补查GPU占用；运行中仅更新进程和阶段进度。模型的必要设备、正确性与CTA内核校验仍保留。
3. 第一套全部完成并通过结果完整性核验后，队列重新进入同样的“忙600秒、空闲10秒、连续3次”检查，再启动第二套。这里的一套包含六策略、两轮、72个窗口；两套之间检查，不在一套内部的策略/窗口之间反复查询占用。执行失败时队列停在失败状态，不自动推进第二套。
4. 新会话 `handoff/repeat-inputs.json`及`execution.json`记录 `gpu_monitoring=before_each_run_only`，驱动哈希包含新执行器。启动前检查保存在队列 `gpu-checks.jsonl`，启动前环境记录仍会调用 `nvidia-smi`；这不属于计时期间监控。本模式不生成执行器的连续 `handoff/gpu-occupancy.jsonl`，交付时注明“运行中采样已关闭”，不将其误报为漏传文件，也不据此声称全过程独占。

当前队列的 [run-one.sh](../../../outputs/h100/phase6/gpt67-tp8-fusedv2-20261012-205424-queue/run-one.sh) 已改用新入口；新融合基线仍为 `a800-fused-v2-cta-v1`，构建/计划和测试协议不变。此前会话的 `execute.py`保留原样用于追溯，仍具有旧的运行中采样行为，勿手动调用它代替新入口。

H100端需要同步本次代码。**已启动的旧执行器不会因pull自动切换行为**；只有后续经更新后`run-one.sh`启动的测试使用新模式。若旧队列尚处等待阶段、还未启动本套`run-one.sh`，它下次会读到更新后的启动脚本。不要为了更改监控方式删除状态文件或覆盖已经开始的会话；当前已有`watchdog-state.json`时，直接重复启动同名队列会被拒绝。

## 监控数据交付

当前自动队列按用户要求只记录启动前GPU状态，不采集运行中及失败后的占用快照；其他启用监控的会话回传其实际记录。交接时注明采样模式，不能用启动前或事后空闲状态证明计时期间没有干扰。
