# H100 op4 v2 实测：算子收益未确认，模型数值门禁未通过

更新：2026-10-21。回传批次为 [`arrival-op4-v2-2x-50steps-20261021-115709-698211`](../../../../logs/h100/phase6/arrival-op4-v2-2x-50steps-20261021-115709-698211)，对应 [op-4.md](op-4.md) 的“归约组闭包量化”四组实验。本文依据回传原始记录和离线复算，不混入旧op4工程方案或op3的计时。

## 1. 结论与完成范围

**本批次尚不能支持“闭包量化＋共享逆变换带来有效训练加速”。算子实验完成，但所有预注册性能对比的95%置信区间均跨零；模型实验在正式计时之前因数值轨迹不满足预注册门槛而停止。**

- 主对照CM/SM的算子下降率为Attention **2.672% [-1.565, 8.546]**、MLP **0.803% [-0.425, 2.011]**，尚未确认正收益。
- 同闭包mask下，仅改变逐源/合并解码的CM/CP，算子下降率仅 **0.446%**、**0.095%**，区间均跨零。解析逆H128次数从7168降到1024，没有兑现为同等级的解码耗时下降。
- 模型预检中，CM/CP的梯度范数比较在 **8/8个相位**失败，loss比较在 **6/8个相位**失败。两组量化mask相同，不能仅用“量化对象不同”解释这些差异。
- **正式训练计时为0个窗口、0个正式optimizer step。** 没有实测整步速度，也没有完成模型profile；不能写成“已测得训练无收益”“训练发散”或“达到1%”。

| 阶段 | 实际完成 | 可支持的判断 |
| --- | --- | --- |
| 算子正式计时 | 16个四组配对块、64个TP8窗口、512份rank记录 | 本批算子耗时和配对区间 |
| 独立算子profile | 32份rank记录、64份trace | 指定解码路径确实执行及局部耗时诊断 |
| 模型smoke | 8相位×4组＝32窗口、256份rank记录 | 单窗口检查通过，跨组数值门禁失败 |
| 正式模型计时 | **0/128窗口，0/6400个计划正式step** | 无整步性能结论 |
| 正式模型之后的profile | 未执行 | 无完整模型执行路径验收结论 |

每个smoke窗口只有2步预热＋3步记录，合计64个预热step、96个记录step；这些是短程数值预检，不是两次50步正式比较。6400是计划中多个独立初始化窗口的累计正式工作量，并非一个模型连续训练6400步。

[`batch-state.json`](../../../../logs/h100/phase6/arrival-op4-v2-2x-50steps-20261021-115709-698211/batch-state.json) 中 `status=failed`、`stage=fullstep-run`、`target_validated=false`、`mechanism_validated=false`。其中 **`precision_control_passed=true`来自已完成的算子阶段，不表示模型数值门禁通过**；1%整步目标没有进入评估，不能将false解释为已经测得加速低于1%。

## 2. 四组确实固定了量化预算，但数值语义不同于旧C

| 组别 | 量化布局 | 解码方式 | 每rank每投影解析逆H128次数 |
| --- | --- | --- | ---: |
| SP | 散布：56个接收tile各有1个量化远端来源 | 逐来源逆变换 | 7168 |
| CP | 闭包：8个接收tile各有7个量化远端来源 | 逐来源逆变换 | 7168 |
| SM | 与SP相同 | 合并系数后逆变换 | 7168 |
| CM | 与CP相同 | 合并系数后逆变换 | **1024** |

四组每来源均量化56/448个远端tile贡献，即 **1/8预算**；每来源—目标链路恰量化8个tile，每rank每投影逻辑远端载荷均为 **13,819,904字节**。生产侧每轮编码数量也匹配。**本批四组的差异不是减少量化贡献数量，而是改变贡献在接收tile上的分布，以及是否共享逆变换。** 逆变换数是mask和算法推导的计数，不是硬件指令计数；逻辑载荷也不是实测NVLink流量。

四组共用warp布局、一个工作区、两次barrier和一次输出clone，并统一采用FP32累加、最终一次BF16输出。因此本批比较没有把删clone、换工作区或只给候选提高累加精度混进去。不过，这个统一协议已经改变了旧路径逐来源BF16舍入的语义，且预算不同于 [消融3中的原C](../消融实验/消融实验3.md) 的1/64，**不能把跨批次的旧C耗时当成本批SP/SM基线，也不能称为原C数值语义下的纯调度优化。**

## 3. 算子：点估计略快，但收益与机制交互都未确认

每个fresh-process窗口、每角色100次预热＋200次正式 `forward().clone()`；计时包含末尾同步，取八rank最大墙钟后除以200。下表是16个块的算术均值，共25,600次正式分布式算子调用，不再乘rank数。

| 组别 | Attention μs/次 | MLP μs/次 |
| --- | ---: | ---: |
| SP | 135.849 | 214.445 |
| CP | 133.836 | 212.043 |
| SM | 137.702 | 213.588 |
| CM | 133.295 | 211.865 |

下降率使用 `100×[1−exp(mean(log(T_candidate/T_control)))]`，正数表示更快；以16个完整四组配对块bootstrap 10,000次，seed20261020。没有把八rank或单窗口200次调用当作独立样本。

| 对照及作用 | Attention下降% [95% CI] | MLP下降% [95% CI] |
| --- | --- | --- |
| **CM/SM：合并实现下改变预算布局，主对照** | **2.672 [-1.565, 8.546]** | **0.803 [-0.425, 2.011]** |
| CP/SP：逐源实现下仅改变布局 | 1.088 [-2.016, 5.869] | 1.044 [-0.438, 3.169] |
| CM/CP：闭包mask下仅改变合并方式 | 0.446 [-1.784, 2.180] | 0.095 [-0.804, 0.856] |
| SM/SP：没有多源复用机会的合并控制 | -1.174 [-9.062, 5.595] | 0.338 [-1.588, 2.844] |
| CM/SP：完整候选相对散布逐源控制 | 1.530 [-0.177, 4.360] | 1.138 [-0.054, 2.672] |

原始 [operator/report.json](../../../../logs/h100/phase6/arrival-op4-v2-2x-50steps-20261021-115709-698211/operator/report.json) 已离线复算，数值完全一致。各相位仅有两个块，Attention的CM/SM仅4/8相位为正，phase5为+19.21%、phase4为−4.93%；这些只说明波动，不能选择有利相位替代整体统计，全部慢样本均保留。

离线审计额外计算四组交互量 `100×(1−exp(mean(log(CM/SM)−log(CP/SP))))`：Attention **1.602% [-7.621, 9.283]**，MLP **−0.244% [-3.549, 2.213]**。这是事后补充诊断，按完整块bootstrap、seed20261021；也未确认“闭包组织激活合并解码收益”的稳定正交互。

原报告按每step每角色128次投影外推，`128×Σ(SM_us−CM_us)/1000` 为 **0.7847 ms/step，95% CI [-0.3406, 2.3148]**。这是算子差值外推，既不是实测整步收益，也不是训练准入门槛；本次终止原因是数值门禁，与这个性能估算无关。

## 4. 独立profile：逆变换次数下降没有变成大幅解码加速

以下来自独立phase0 profile：先取每rank四次kernel调用耗时中位数，再取八rank中位数。它不等于正式计时估计量，kernel中位数也不能直接相加还原墙钟。

| 组别 | Attention GEMM / decode，μs | MLP GEMM / decode，μs |
| --- | ---: | ---: |
| SP | 75.136 / 16.568 | 148.333 / 18.200 |
| CP | 74.520 / 17.904 | 143.015 / 19.232 |
| SM | 75.632 / 16.808 | 148.039 / 17.760 |
| CM | 74.992 / 17.296 | 143.373 / 18.672 |

CM的decode相对CP仅快 **3.40% / 2.91%**，相对SM反而慢 **2.90% / 5.14%**。这说明在本实现、shape和profile条件下，解析逆H128数量减少6/7并未产生相应幅度的decode缩短。仅凭这些trace不能确定具体是访存、尺度处理、执行组织还是其他成本占主导，也不能将独立profile差异直接归因成整步收益。

64份trace均验证每次共同GEMM→barrier→指定decoder→barrier及一次clone，未走旧到达解码路径。原始 [profile-summary.json](../../../../logs/h100/phase6/arrival-op4-v2-2x-50steps-20261021-115709-698211/operator/profile-summary.json) 离线复算一致；这验证了算子机制执行，**不等于验证机制产生性能收益**。

## 5. 算子局部正确性通过，模型轨迹仍失败

正式算子窗口共完成12,288次独立codec检查、12,288次实际packet oracle检查、6,144次保留输出检查；6,144组同mask P/M配对的实际packet哈希一致。profile另有768次codec检查、768次packet检查和384次保留输出检查。所有既定算子门禁通过。

| 算子计时窗口的误差指标 | 最大值 | 预注册上限 |
| --- | ---: | ---: |
| 相对BF16参考的relative L2 | 0.94733% | 5% |
| 与独立codec oracle之差 / BF16参考范数 | 0.01072% | 1% |
| 相对实际packet oracle的relative L2 | 0.16660% | 0.5% |
| 同mask P/M固定512点输出采样relative L2 | 0.01117% | 0.5% |

实际packet指标的分母使用`max(||oracle||, source_norm_sum×1e-3, 1e-20)`，避免来源抵消时分母过小。误差分布也发生变化：SP/SM最大tile relative L2为 **1.0372%**，CP/CM为 **2.5074%**。闭包布局集中量化误差，不能只因整体L2相近就称数值影响等价；tile指标在本协议中仅作记录，没有单独验收门槛。512点同mask采样也不能替代全输出oracle或模型轨迹比较。

模型smoke的32个窗口经冻结controller原始窗口校验器复验，均通过单窗口检查；256份rank记录的硬件/软件、输入、初始参数和RNG身份一致，无worker `failed.json`。16,384项模块forward检查全部通过：相对BF16最大relative L2为 **0.98927% < 5%**，与codec oracle之差按BF16参考范数归一化后为 **0.01330% < 1%**。这些检查仍不足以保证经过多层和optimizer更新之后的训练轨迹在容限内。

跨组门禁逐记录step比较，公式为 `|x−y|≤atol+rtol×max(|x|,|y|)`。跨mask的loss门槛为`atol=0.01,rtol=0.02`，grad norm为`atol=0.001,rtol=0.05`；同mask分别为`atol=1e-4,rtol=1e-3`和`atol=1e-4,rtol=1e-2`。本次没有修改这些预注册值。

| 对照 | loss失败相位数 | grad norm失败相位数 | 解释范围 |
| --- | ---: | ---: | --- |
| CP/SP，跨mask | 0/8 | **7/8** | 改布局后梯度轨迹超限 |
| CM/SP，跨mask | 0/8 | **6/8** | 完整候选相对散布逐源控制超限 |
| SM/SP，同mask | 0/8 | 0/8 | 所有相位三步loss和grad norm记录完全相同 |
| CM/CP，同mask | **6/8** | **8/8** | 七源共享解码改变后的轨迹超限 |

例如phase0第2个记录step，CM/CP的grad norm为 **8.88189429 / 7.07567832**，差值 **1.80621597**，允许差值只有 **0.08891894**；loss为12.43064880 / 12.41131973，差0.01932907，也超过允许的0.01253065。phase2第2个记录step的CM/CP梯度差达到 **3.33653723**，允许值 **0.11226193**。这里的“记录step”指2步预热之后的三步smoke记录。

原controller收集完32窗口后，在phase0配对比较时抛出：

```text
ValueError: Paired training trajectories exceed the pre-registered numerical limits
```

位置见 [fullstep-run.log](../../../../logs/h100/phase6/arrival-op4-v2-2x-50steps-20261021-115709-698211/fullstep-run.log) 第33–48行，以及冻结 [fullstep-controller.py](../../../../logs/h100/phase6/arrival-op4-v2-2x-50steps-20261021-115709-698211/fullstep/scripts/fullstep-controller.py) 的`run→preflight→numerical_comparisons`。离线对全部相位复算后，八个相位均有失败。顶层`CalledProcessError`只是该失败的包装；日志未显示CUDA/OOM/环境异常导致中止。

## 6. 对当前想法的判断

本批验证了同预算实验和共享解码路径可以执行，但没有验证其作为性能改进的有效性。**目前不应将op4作为已经成立的新加速点，也不应把“逆变换次数降至1/7（减少6/7）”写成已兑现的性能贡献。** 相比继续扩大性能实验，若保留此方向，首先需要定位同mask CM/CP在真实模型中最早出现的数值差异及其传播。

两类证据需要同时保留：独立算子oracle和模型逐模块forward门禁通过，说明现有检查未发现明显的局部解码错误；同mask训练轨迹仍显著超限，说明数值接受条件没有满足。现有短轨迹不能区分“浮点运算顺序扰动在训练中被放大”与“现有检查尚未覆盖的实现问题”，也不能据此证明所有闭包量化方法不可行。进一步诊断应比较相同初始状态、输入、packet下的逐层输出及梯度，保留当前门槛；不能通过放宽门槛或拿smoke计时代替正式结果来完成验收。
