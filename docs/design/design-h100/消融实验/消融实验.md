## 2. 原生Megatron参照与七组算法消融

先固定一种基础顺序B，例如 `remote_first`，完成下表；再用 `interleaved` 独立重复。两种基础顺序分别解释，不将它们的有利窗口拼成一组。G0在实现、配置和时段条件一致时可作为共同参照，但仍须纳入相应配对测量。

| 组别 | 基础顺序 | 到达优先重排 | 量化方式 |
| --- | --- | --- | --- |
| 原生Megatron（`native`） | Megatron原生执行路径，不采用候选tile重排 | 不适用 | 原生BF16，无TACO量化 |
| G0 | 原始顺序 | 关闭 | 全BF16传输 |
| G1 | B | 关闭 | 全BF16传输 |
| G2 | B | 开启 | 全BF16传输 |
| G3 | B | 关闭 | 当前选择性量化 |
| G4 | B | 开启 | 当前选择性量化，即完整候选 |
| G5 | B | 开启 | 同数量、同目的分区分布的随机选择性量化 |
| G6 | B | 开启 | 全部远端贡献量化，本地仍为BF16 |

**G0–G6全部使用同一套候选代码。** 固定GEMM版本、tile尺寸、解码实现、工作区生命周期及模型适配，仅改变表中对应因素。这里的GemmV2是候选内部使用的Flux矩阵乘法实现，模型仍由Megatron训练；在H100上使用重新编译的SM90代码。G0是这套实现下的原始顺序、全BF16内部对照，与原生Megatron的 `native` 组不同。关闭量化时保持同一计算路径，不切换到原生Flux的Hopper GemmV3或其他通信后端。

这些比较各自回答一个明确问题：

| 比较 | 可以解释的贡献 |
| --- | --- |
| G0–G6各组对 `native` | 相对原生Megatron的完整step性能差距，作为总体参照，不单独归因于某一项算法 |
| G1对G0 | 在全BF16条件下，仅改变基础顺序是否有效 |
| G2对G1 | 未启用量化时，到达优先的增量 |
| G4对G3 | 已启用选择性量化时，到达优先的增量 |
| G3对G1 | 仅有基础顺序时，选择性量化的增量 |
| G4对G2 | 已有到达优先时，选择性量化的增量 |
| G4对G5 | 到达评分是否选中了更有价值的贡献，而不是任意少量量化都同样有效 |
| G4对G6 | 少量定向量化相对全远端量化，是否改善通信量与编解码成本之间的取舍 |

G1–G4包含“到达优先开/关×选择性量化开/关”的全部四种组合，可分析二者交互。这是两个因素的[全因子设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri333.htm)。例如G2对G1的增益与G4对G3明显不同，说明到达优先的效果依赖量化条件；不要将各项加速百分比直接相加。

G1对G0反映基础顺序在BF16条件下的贡献，不自动推广为完整候选中相同大小的贡献。上表共八组：一个原生Megatron参照和七个算法消融组；G0–G6编号保持不变，不扩展其他算法组合。

## 3. 校准、重排和mask必须怎样固定

### 3.1 开关到达优先时不重新选择量化对象

同一种B下，G3与G4使用完全相同的**物理tile量化mask**；G3只恢复基础顺序，G4使用冻结的到达置换。mask按“来源rank、物理tile”索引，不能在重排后按逻辑执行位置重新解释它。

同理，G1/G2、G3/G4各自只改变到达重排；G2/G4/G5/G6使用相同的到达表。比较到达开关时如果重新拟合mask，就同时改变了调度和选择对象，无法单独归因。

每种基础顺序先使用对应的真实H100 BF16校准，冻结训练pass 0/1生成的计划，pass 2仅用于留出诊断。纯消融从该计划派生新文件，记录父计划SHA256及变换规则，不覆盖原计划。若设备、shape、SM数、tile映射或到达语义改变，重新校准；不使用A800计划代替H100证据。

### 3.2 随机选择匹配实际数量，而不只是预算

1/64是上限，实际mask可能未用满。当前冻结计划的选择数量为：

| 基础顺序 | 各来源rank实际选择tile数（rank 0–7） |
| --- | --- |
| `remote_first` | `[2, 6, 7, 3, 4, 7, 7, 3]` |
| `interleaved` | `[7, 7, 7, 0, 7, 7, 7, 3]` |

G5应匹配G4每个来源rank、每个目标分区的实际选择数量，仅随机替换合法远端物理tile的位置；本地贡献始终不量化。预先登记多个随机种子，例如至少3个，逐个报告并汇总，不能测完后只保留最有利的随机mask。若匹配条件导致某些位置没有选择自由，也如实记录。

G4优于G5才支持“定向选择关键贡献有价值”。若二者接近，收益可能主要来自减少量化操作数量；不能仅凭G4优于全量化证明选择算法有效。

### 3.3 无量化与全量化各自是显式模式

G0/G1/G2定义为远端BF16，必须正确旁路量化并保留相同V2算法路由。G6定义为所有远端贡献量化，不能将“选择器预算设为1”当作等价实现：当前选择器仍只选择有正评分的tile，即使预算放宽，也不保证选满所有远端贡献。

原H100配置校验仍要求 `fraction > 0`。新增消融入口使用独立 `quantization_mode`，不修改原配置约束：`bf16` 生成并验证全零物理mask，`all_remote` 显式枚举全部远端tile；选择器预算仍保持1/64。候选实例配置保持启用，使BF16 MLP仍走V2；原接收kernel对全零mask执行BF16归约，不进行FP8编解码。双工作区、计算实现与生命周期保持一致，不能手改旧manifest绕过约束。

## 4. 固定模型条件与完整step测量

| 项目 | 默认固定值 |
| --- | --- |
| 模型 | GPT 6.7B，32层，H4096/FFN16384，32 heads |
| 并行与设备 | 单节点8×H100，TP8/DP1/PP1/CP1；沿用已核验设备UUID顺序及132 SM配置 |
| batch与序列 | S2048、micro batch1、global batch4，每step累计4个微批 |
| MLP shape | 全局 `[M,N,K]=[2048,4096,16384]`，每rank本地K=2048 |
| 数据与初始化 | 固定合成token规则、seed1234、token_seed4321；记录实际初始化/RNG/token指纹 |
| 精度与范围 | BF16 GEMM，本地BF16；量化组用H128/E4M3；保持BF16 STE反向与现有误差要求 |
| 算法参数 | 到达窗口64，选择性量化预算上限1/64；G5匹配实际选择量，G6为显式全远端量化 |
| 计时 | 每窗口10步预热＋20步完整optimizer step，八rank最大elapsed除以20 |

先完成所有组的映射、smoke和执行路径验证，再进行计时。保持初始模型/随机状态/输入一致，但不要求量化组与BF16组的训练轨迹逐位相等；数值、loss及梯度按预先固定的正确性要求检查。

本轮统一比较GPT 6.7B的完整optimizer step，计时包含前向、反向、通信/同步、参数更新和清梯度。每组报告ms/step、tokens/s、相对指定对照组的配对收益及95%区间。

正式计时不混入采样或profiler；预检沿用现有正确性和执行路径核验流程。每个正式窗口保留全部rank记录、命令、进程日志及对应组别、配置和库哈希。

## 5. 顺序、重复与慢窗口处理

同一配对块内完成需要比较的组，预先固定随机种子和调度表，采用随机化或平衡顺序，避免先测完一个组再隔很长时间测另一个组。[分块实验设计](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)用于控制时段等干扰因素，随机化用于降低剩余顺序影响。

沿用两轮完整训练计时的含义：round1、round2都包含前向、反向和optimizer更新；若采用原有正反调度，反转的是配对块及块内策略的执行顺序。新增组数后，窗口数必须按实际调度表计算，不再硬套原六策略的72窗口。

重复次数依据预跑方差、目标精度与预算确定，并在正式统计前固定。需要跨独立会话重复，不把同一窗口的20步或8个rank当作160个独立重复样本。既有4%是完整候选对必须baseline的验收门槛；单项消融允许小于4%，重点是增量大小、区间和可重复性。

对两个组X与Y，沿用配对几何平均耗时下降：

```text
gain(X 对 Y) = 100 × [1 − exp(mean_b(log(T_X,b / T_Y,b)))]
```

正值表示X更快。按完整配对块bootstrap给出95%区间，报告各会话结果与预先定义的汇总；同时保留绝对耗时和全部块值，不用中位数相除替代配对收益。若区间跨零，应写“尚未确认正增益”，不能只取最好轮次。

a–h已经出现过基线和候选各自偶发慢窗口，正式消融需要遵守：

1. 主结果保留全样本。此前聊天中“超过该轮该策略中位数10%则排除”的计算属于事后敏感性分析，不作为主要验收结果。
2. 若预先定义测量无效条件，明确整块或整套判废/补测规则，并对所有组统一执行；不能仅按收益正负删除窗口，也不能只删一侧后错配另一侧。
3. 可另列双边慢窗口筛选敏感性表，明确阈值、排除的block、保留数量及理由。存在长尾时保留完整记录，不能直接断定都是外部干扰。
4. 运行方式沿用 [watcher.md](../watcher.md)：启动前检查，正式运行期间不周期查询GPU状态。本方案不自动恢复GPU轮询。
